# BOLA AI — Architecture

## Overview

BOLA AI is a local-only security analysis stack that runs in Docker. It combines a small local LLM (e.g., Qwen 2.5 Coder), a vector store for RAG over documentation, and an API + minimal UI. No outbound traffic is required at runtime; the container can use an ephemeral volume that is wiped when the analysis is done.

## Components

### 1. LLM — Ollama + Qwen 2.5 Coder

- **Role:** Answer questions, summarize docs, and generate BOLA hypotheses and verification steps.
- **Model:** Qwen 2.5 Coder (e.g., 1.5B or 3B for balance of quality and size). Smaller variants (0.5B) reduce image size and memory.
- **Deployment:** Runs inside the same container or as a sidecar; no internet needed after the image is built if the model is baked in or loaded from a local volume.
- **API:** Ollama exposes `http://localhost:11434` (or internal hostname); the app calls `/api/chat` for completion.

### 2. Vector DB — ChromaDB

- **Role:** Store embeddings of documentation (system info, schemas, API specs) for RAG.
- **Persistence:** Uses a path under the container volume (e.g., `./data/chroma`). Wiping the volume removes all ingested data.
- **Embeddings:** Generated by a local embedding model (e.g., `sentence-transformers` or Ollama embedding API if available) so the stack stays offline.

### 3. Application — FastAPI

- **Role:** Orchestrate ingestion, RAG retrieval, and LLM calls; expose REST API and serve a minimal UI.
- **Endpoints:**
  - `POST /ingest` — Upload or paste documentation; chunk and embed into ChromaDB.
  - `POST /ingest_shared` — Ingest UTF-8 documentation from the shared Docker docs path (`/shared-docs`) by relative filename.
  - `POST /analyze` — Run BOLA-oriented analysis: RAG context + prompt → LLM → structured findings + verification steps.
  - `GET /health` — Health check (app + optional Ollama/Chroma checks).
  - `GET /` — Simple HTML UI for upload and analysis.
- **CLI:** A Python CLI (e.g., `python -m bola_ai.cli`) that calls the same API so the tool can be driven from the terminal and scripts.

### 4. Agent / RAG Pipeline

- **Ingest:** Parse docs (text, JSON, YAML, OpenAPI); chunk by section or token limit; embed with local model; upsert into Chroma.
- **Analyze:** Build a prompt that includes: (1) BOLA/system prompt, (2) retrieved chunks, (3) user query or “analyze for BOLA”. LLM returns structured text (e.g., markdown) with:
  - Suspected issues (e.g., “endpoint X may not check object ownership”).
  - Rationale (e.g., “parameter `userId` is not mentioned in authorization section”).
  - Verification steps (e.g., “Call GET /api/users/{id} with two different user tokens and compare”).
- **Output:** JSON or markdown suitable for reports and for auditors to execute tests.

### 5. Training and Adaptation

- **RAG knowledge base:** Preload Chroma with BOLA patterns, OWASP notes, and synthetic examples (see `training/`). No fine-tuning required for initial POC.
- **Training data generator:** Scripts in `training/` generate JSONL (and optionally other formats) from BOLA scenarios and public patterns for future fine-tuning (e.g., with Ollama or external tools). Training runs are optional and can be done offline on a separate machine.
- **Fine-tuning (optional):** Documentation and scripts to fine-tune a small model on BOLA examples; not required for the first working POC.

## Docker Strategy

- **Single service (all-in-one):** One Docker image runs FastAPI, ChromaDB, and Ollama. The model can be baked in at build time (larger image) or mounted from a volume that is populated once and then reused.
- **Ephemeral volume:** Mount `./data` (or similar) for Chroma and optional model cache. Documentation states that this volume should be wiped before use (clean state) and after use (no residual sensitive data).
- **Shared docs path:** Mount `./shared_docs` to `/shared-docs` so users can copy test docs into a host folder and ingest by filename (`/ingest_shared`) during E2E and audit workflows.
- **Network:** Default run can use `--network=host` for simplicity; for strict “no outbound” policy, run with `--network=none` and ensure the model and any base images are already present.

## Memory Management (target &lt;10 GB)

Design goal: the full stack (Ollama + embedder + app) should consume **less than 10 GB** RAM. See [MEMORY.md](MEMORY.md) for breakdown and env vars.

- **Fake embedder:** Set `BOLA_AI_FAKE_EMBEDDER=1` to skip loading sentence-transformers (and thus torch). Use for tests, CI, or low-memory dev; RAG still runs but similarity is deterministic, not semantic.
- **Smaller LLM:** Use `OLLAMA_MODEL=qwen2.5-coder:0.5b` (or similar) to reduce Ollama memory.
- **RAG context:** Limit retrieved chunks with `BOLA_AI_N_CONTEXT` (default 10); lower values reduce prompt size and memory. Optional `BOLA_AI_MAX_CONTEXT_CHARS` caps total context length.
- **Chunking:** Default chunk size is ~512 chars; avoid ingesting very large single documents in one shot on constrained hosts.
- **One process:** Run only the API process; avoid running training (e.g. `load_knowledge`) in the same process as the server if memory is tight.

## Security and Disposability

- **No telemetry or outbound calls** from the application or LLM at runtime.
- **No persistence of inputs** beyond the lifecycle of the container/volume; users are instructed to destroy the container and wipe the volume when done.
- **Secrets:** No API keys or cloud credentials required; all processing is local.
