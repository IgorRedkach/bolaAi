# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** StayPro Property API
**Document Version:** 2.8.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Hospitality / Hotel PMS
**Architecture:** REST + OTA standards + GraphQL
**Training Example ID:** BOLA-0030

## 1.0 Executive Summary
StayPro Property API is a hospitality / hotel pms platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v1/nodes endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 5.2 — Resolver/graph traversal injection

## 3.0 Database Schema
```sql

-- Node table
CREATE TABLE nodes (
    node_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_node_tenant ON nodes(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 5.2 — Resolver/graph traversal injection (Injection)

The `GET/PATCH/DELETE /api/v1/nodes/:id` endpoint accepts a `node_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-B99B` can access objects owned by `ORG-B340`.

_Specific exploitation for Pattern 5.2:_ The `/api/v1/nodes` handler does not enforce tenant/owner boundaries for Pattern 5.2.
