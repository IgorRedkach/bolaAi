# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** TeleCare Consultation API
**Document Version:** 2.3.9 (FINAL)
**Classification:** SENSITIVE
**Domain:** Telemedicine / Remote Care
**Architecture:** FHIR + WebRTC + GraphQL
**Training Example ID:** GQL-0086

## 1.0 Executive Summary
TeleCare Consultation API is a telemedicine / remote care platform that exposes a GraphQL API to authorised consumers.
The platform manages data records partitioned by tenant (`tenantId`). The architecture uses
JWT-based OAuth2 authentication, and the JWT carries both the `sub` (user ID) and `tenantId` claims.
Authorization is expected to be enforced per-resolver on the GraphQL server.

## 2.0 Architecture Overview
- **API Layer:** GraphQL single endpoint (`POST /graphql`) served via Apollo Server
- **Auth:** OAuth2 JWT issued by internal IdP; claims include `sub`, `role`, `tenantId`
- **Database:** PostgreSQL with row-level security policies; each table has a `tenant_id` column
- **Caching:** Redis cache keyed by `resourceId` (NOTE: no user dimension in cache key)

## 3.0 GraphQL Schema
```graphql

type Resource {
  resourceId: ID!
  tenantId: ID!
  ownerId: ID!
  status: String!
  data: ResourceData
  items: [Item!]
}

type ResourceData {
  title: String
  sensitiveField: String      # PII / business-sensitive
  internalNotes: String       # Internal-only field
  auditLog: [AuditEntry!]
}

type Query {
  getResource(id: ID!): Resource
  listResources(tenantId: ID, status: String): [Resource!]
  getResourceWithChildren(id: ID!): Resource
}

type Mutation {
  updateResource(id: ID!, input: ResourceInput!): Resource
  deleteResource(id: ID!): Boolean
  bulkResourceLookup(ids: [ID!]!): [Resource!]
}

```

## 4.0 Known Architectural Notes
- **RISK-GQL-086:** The `getResource` resolver fetches by `resourceId` only.
  The resolver does NOT verify that the fetched object's `tenantId` matches the JWT's `tenantId`.
  Tracked internally as a known gap pending remediation.
- The `bulkResourceLookup` mutation accepts an arbitrary array of IDs without
  per-ID ownership filtering.

## 5.0 Vulnerability Context
**Pattern:** 10.1 — ID swap in own request (Single-User)

The `resourceId` field is used as the object identifier across all resolvers.
A single authenticated user substitutes their own valid `resourceId` with a victim's `resourceId`. With one token, data belonging to another user is accessible.

## 7.0 API Contract (Partial)
```
POST /graphql
Authorization: Bearer <JWT>
Content-Type: application/json

Body: { "query": "..." }

Authenticated user's tenantId is extracted from JWT.
Resolver MUST cross-check tenantId against fetched object's tenantId.
```
