# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** PatientCore EHR API
**Document Version:** 3.2.6 (FINAL)
**Classification:** SENSITIVE
**Domain:** Healthcare / EHR Platform
**Architecture:** FHIR R4 + GraphQL gateway over clinical records
**Training Example ID:** GQL-0351

## 1.0 Executive Summary
PatientCore EHR API is a healthcare / ehr platform platform that exposes a GraphQL API to authorised consumers.
The platform manages PHI records partitioned by tenant (`tenantId`). The architecture uses
JWT-based OAuth2 authentication, and the JWT carries both the `sub` (user ID) and `tenantId` claims.
Authorization is expected to be enforced per-resolver on the GraphQL server.

## 2.0 Architecture Overview
- **API Layer:** GraphQL single endpoint (`POST /graphql`) served via Apollo Server
- **Auth:** OAuth2 JWT issued by internal IdP; claims include `sub`, `role`, `tenantId`
- **Database:** PostgreSQL with row-level security policies; each table has a `tenant_id` column
- **Caching:** Redis cache keyed by `patientId` (NOTE: no user dimension in cache key)

## 3.0 GraphQL Schema
```graphql

type Patient {
  patientId: ID!
  tenantId: ID!
  ownerId: ID!
  status: String!
  data: PatientData
  records: [Record!]
}

type PatientData {
  title: String
  sensitiveField: String      # PII / business-sensitive
  internalNotes: String       # Internal-only field
  auditLog: [AuditEntry!]
}

type Query {
  getPatient(id: ID!): Patient
  listPatients(tenantId: ID, status: String): [Patient!]
  getPatientWithChildren(id: ID!): Patient
}

type Mutation {
  updatePatient(id: ID!, input: PatientInput!): Patient
  deletePatient(id: ID!): Boolean
  bulkPatientLookup(ids: [ID!]!): [Patient!]
}

```

## 4.0 Known Architectural Notes
- **RISK-GQL-351:** The `getPatient` resolver fetches by `patientId` only.
  The resolver does NOT verify that the fetched object's `tenantId` matches the JWT's `tenantId`.
  Tracked internally as a known gap pending remediation.
- The `bulkPatientLookup` mutation accepts an arbitrary array of IDs without
  per-ID ownership filtering.

## 5.0 Vulnerability Context
**Pattern:** 10.2 — Parameter escalation (own session scope extension) (Single-User)

The `patientId` field is used as the object identifier across all resolvers.
The resolver handling `patientId` does not enforce ownership or tenancy boundaries, enabling Pattern 10.2 exploitation.

## 7.0 API Contract (Partial)
```
POST /graphql
Authorization: Bearer <JWT>
Content-Type: application/json

Body: { "query": "..." }

Authenticated user's tenantId is extracted from JWT.
Resolver MUST cross-check tenantId against fetched object's tenantId.
```
