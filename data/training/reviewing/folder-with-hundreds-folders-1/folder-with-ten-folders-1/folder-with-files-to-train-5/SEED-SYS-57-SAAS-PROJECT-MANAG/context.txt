# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** TaskFlow Project Management API
**Document Version:** 6.0.0 (FINAL)
**Classification:** CONFIDENTIAL / CORPORATE IP SCOPE
**Domain:** SaaS / Project Management / Work Tracking

## 1.0 Executive Summary
TaskFlow is a multi-tenant project management platform used by hundreds of corporations to organize their engineering, marketing, and sales workflows. The core data model revolves around `Project` objects, which contain highly confidential competitive information.

The platform exposes a GraphQL API to power its modern web and mobile applications. Due to the high volume of project creation, the backend has implemented simple sequential integer IDs for internal objects to improve database indexing performance, assuming the API's authentication layer would prevent enumeration.

## 2.0 Comprehensive Network Topology & GraphQL Processing
The architecture implements a standard, centralized GraphQL entry point.

### 2.1 The Ingress Layer & GraphQL Router
* **API Gateway (Node.js):** Handles all routing, ensuring all traffic goes to the single `/graphql` endpoint.
* **Apollo Server (Schema Stitching):** The centralized hub that routes field requests to the appropriate microservices.

### 2.2 The Backend Core Services
* **Project Service (Python Django):** Utilizes a PostgreSQL database where the primary key for the `Project` object is an auto-incrementing integer (`project_id`).
* **Authorization Middleware:** Custom middleware enforces that the authenticated user must be listed in the `Project.members` array before the resolver is executed.

## 3.0 Identity, Sessions, and Object Authorization
The security model relies on strict membership lists for project-level BOLA enforcement.

### 3.1 User Authentication (JWT)
Users authenticate via corporate SSO, and their session JWT contains the `user_id`.

### 3.2 The BOLA Enforcement Flaw
When a user attempts to query a project, the top-level `project(id: Int)` resolver is executed. The resolver is correctly configured to check the user's membership. However, if the query fails this check, it returns a soft `null` instead of a hard `403 Forbidden` error. This behavior allows attackers to probe for the existence of unauthorized projects without being blocked by API rate limiters on failed requests.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: We intentionally used simple sequential IDs (Pattern 1.8) for the Project table for historical reasons. The core authorization check returns a soft `null` on failure to prevent verbose error leakage (Pattern 6.2), but this inadvertently enables large-scale enumeration via GraphQL alias batching. Tracked as RISK-GRPH-903.*

### 4.1 Vulnerability A: GraphQL Alias Enumeration on Sequential IDs (BOLA)
**Taxonomy Pattern:** 9.1 (GraphQL Operations / Batching) & 1.8 (Predictable IDs)
**Sub-system:** Project Service Resolver (`Query: project`)

**The Deep Architectural Flaw:**
This attack chains three vulnerabilities: predictable IDs, soft authorization failure, and GraphQL's batching capability.

1. **Predictable IDs (Pattern 1.8):** The use of auto-incrementing integers (e.g., `10001`, `10002`, `10003`) makes the target space trivial to enumerate.

2. **GraphQL Alias Batching (Pattern 9.1):** The attacker is authorized to send a single HTTP POST request to `/graphql`. They can leverage GraphQL aliasing to request thousands of sequentially numbered projects simultaneously in that single request (e.g., `p1: project(id: 10001)`, `p2: project(id: 10002)`, ... `p5000: project(id: 15000)`).

3. **Soft Failure Evasion:** Because the resolver returns `null` for unauthorized projects and returns the Project object for authorized ones, the attacker only needs to scan the response JSON for non-`null` entries. This single request effectively allows the attacker to horizontally enumerate thousands of project details for which they were never authorized, fully bypassing rate limits enforced at the HTTP layer.

**The Exploitation Path:**

1. **The Foothold:** An attacker registers a standard user account (`user_attacker_1`) and obtains a valid JWT.
2. **Discovery:** The attacker queries one of their own projects and notes the sequential ID (e.g., Project ID `12450`). They deduce the adjacent IDs will follow a predictable integer pattern.
3. **The Enumeration Query:** The attacker crafts a single GraphQL query containing 2,000 aliases, ranging from Project ID `10000` to `12000`, requesting a sensitive field (e.g., `confidential_notes`).
4. **The Execution:** The Apollo Server processes the single HTTP request, but the Project Service executes 2,000 internal database queries. Authorization checks are performed on all 2,000.
5. **The Impact:** In the single response, the attacker identifies hundreds of projects belonging to other corporations. They extract confidential notes from those non-`null` entries, causing a massive cross-tenant data breach.

# SYNTHETIC ARTIFACT: GRAPHQL ALIAS ENUMERATION (HAR TRACE)
**Applies to Architecture:** TaskFlow Project Management API v6.0.0
**Vulnerabilities Referenced:** Section 4.1 (Pattern 9.1 & Pattern 1.8)

This HTTP Archive (HAR) trace captures the execution of the large-scale cross-tenant enumeration attack. The attacker submits a single HTTP POST request containing a GraphQL query with thousands of aliased fields (`p10001`, `p10002`, etc.), targeting sequential, guessable Project IDs.

The single request bypasses the WAF's rate limit. The Apollo Server resolves all 2,000 sub-queries, and the soft authorization failure (`return None`) allows the non-owned results to return as `null`.
