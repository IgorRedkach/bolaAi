## Analysis reasoning

I reviewed two specification/schema artifacts for Tri-State HIE-Core v4.2.1: `step_function.txt` (developer guide and API reference) and `dynabodb.txt` (GraphQL schema and DynamoDB consistency rules). No HAR trace exists in this folder — evidence is entirely specification-grounded.

1. **GraphQL reverse-edge traversal**: the schema annotation in `dynabodb.txt` at `Practitioner.activePatients` directly labels the vulnerability: the resolver uses a system service account and does not re-evaluate the caller's JWT. The BOLA class is clear — a Patient traversing `me -> encounters -> participants -> practitioner -> activePatients` bypasses per-object authorization because the resolver substitutes a privileged identity for the request context. The consistency rule in section 5.3 mandates role-level authorization at every mutation; the same principle applies to query resolution. The GraphQL section 6.1 reverse-edge safety rule (referenced in `step_function.txt`) states resolvers must re-authorize at each relationship edge, confirming the gap.

2. **`_sync` confused deputy**: the `step_function.txt` section 2.3 is the primary evidence — "API Gateway permits any authenticated user to hit this endpoint." Section 6.2 specifies that internal pipeline transition events require HMAC signature validation and `runner_service` identity, not end-user JWT. These two descriptions are in conflict: the gateway policy allows end-user JWTs; the integrity rule requires non-user service identity. Any authenticated patient or practitioner JWT can queue an asynchronous sync job for any `EncounterID` without ownership check. Section 5.4 states Kafka consumers must verify auth envelope signature before mutating state — but the gap is at the enqueue step, not consumption.

3. **URL/body patient mismatch**: the Security Engineering Note (Ref 9.3) in `step_function.txt` is direct documentation of the implementation gap: "backend database writes the record using the `subject.reference` string provided inside the JSON body, NOT the `{PatientID}` provided in the URL." The OPA authorization check uses the URL `PatientID` — the attacker provides an authorized URL target and a different body target. The persistence layer honours the body value. Section 6.3 states that state advancement requires a matching artifact digest from a trusted runner identity; this is the equivalent invariant for the write path: the authorized subject and the persisted subject must match.

4. **Vulnerability class clarification**: finding 1 is BOLA via graph traversal; finding 2 is a confused deputy / missing access control on async endpoint; finding 3 is a write-path identity mismatch. These are three independent vulnerabilities with different root causes and different remediation paths.

5. **HIPAA relevance**: unauthorized access to another patient's identifiers, telecom, and encounter context (finding 1) is ePHI exposure. Writing clinical Observations to the wrong patient chart (finding 3) is unauthorized ePHI modification with potential patient safety impact. Both trigger HIPAA breach notification obligations.
