HIE-CORE: DEVELOPER INTEGRATION & API REFERENCE
Document Version: 3.0.2
Applies to Architecture: Tri-State HIE-Core v4.2.1
Target Audience: Front-end Portal Developers, Mobile App Engineers, B2B Integration Partners

1.0 Authentication & Authorization
All API requests must be authenticated using an Okta-issued JSON Web Token (JWT). The HIE-Core Kong API Gateway enforces strict validation of the JWT signature, expiration (exp), and audience (aud).

1.1 Acquiring a Token
Mobile Clients: Must use the OAuth 2.0 Authorization Code Flow with PKCE.

B2B Services / Automated Workers: Must use the Client Credentials Grant via mutual TLS (mTLS) to the /oauth2/v1/token endpoint.

1.2 Required HTTP Headers
Every request to the RESTful tier must include the following headers:

HTTP
Authorization: Bearer eyJhbG...<truncated_for_brevity>
Accept: application/fhir+json
Content-Type: application/fhir+json
X-Request-ID: <Client-Generated-UUIDv4>
Note: If X-Request-ID is omitted, the API Gateway will generate one, but this breaks end-to-end distributed tracing in Splunk. Always generate a UUID on the client side.

2.0 RESTful Core Endpoints (FHIR R4 Compliant)
The Base URL for all production API calls is: https://api.hie-core.internal/api/v1

2.1 Retrieve Patient Profile
Endpoint: GET /Patient/{PatientID}
Description: Fetches the demographic core of a Patient resource.
Authorization: OPA checks if the JWT fhirUser matches {PatientID}, OR if the JWT role is practitioner and an active CareContext exists in the encounters table.

Example Request:

HTTP
GET /api/v1/Patient/P-449102 HTTP/1.1
Host: api.hie-core.internal
Authorization: Bearer {{VALID_JWT}}
X-Request-ID: req-abc-123
Accept: application/fhir+json
2.2 Create Clinical Observation (Practitioners Only)
Endpoint: POST /Patient/{PatientID}/Observation
Description: Writes a new clinical observation (e.g., Blood Pressure, Heart Rate) to the patient's record.
Authorization: 1. The API Gateway validates the JWT.
2. The OPA sidecar intercepts the request. It extracts the {PatientID} from the URL path.
3. OPA checks the encounters table. If the Practitioner (Actor) has an active encounter with {PatientID} (URL parameter), the request is ALLOWED to pass to the backend microservice.

Request Payload Schema (FHIR JSON):
The body must be valid FHIR R4 JSON. It must include a subject.reference mapping.

Security Engineering Note (Ref 9.3): The backend database writes the record using the subject.reference string provided inside the JSON body, NOT the {PatientID} provided in the URL. Ensure these two values match when constructing your requests.

Example Request:

HTTP
POST /api/v1/Patient/P-449102/Observation HTTP/1.1
Host: api.hie-core.internal
Authorization: Bearer {{VALID_PRACTITIONER_JWT}}
X-Request-ID: req-def-456
Content-Type: application/fhir+json

{
  "resourceType": "Observation",
  "status": "final",
  "category": [
    {
      "coding": [
        {
          "system": "http://terminology.hl7.org/CodeSystem/observation-category",
          "code": "vital-signs",
          "display": "Vital Signs"
        }
      ]
    }
  ],
  "code": {
    "coding": [
      {
        "system": "http://loinc.org",
        "code": "85354-9",
        "display": "Blood pressure panel with all children optional"
      }
    ],
    "text": "Blood pressure systolic & diastolic"
  },
  "subject": {
    "reference": "Patient/P-449102"
  },
  "effectiveDateTime": "2026-04-08T16:30:00Z",
  "component": [
    {
      "code": {
        "coding": [
          {
            "system": "http://loinc.org",
            "code": "8480-6",
            "display": "Systolic blood pressure"
          }
        ]
      },

        "value": 120,

      }
    }
  ]
}

2.3 Force Legacy Database Sync
Endpoint: POST /Encounter/{EncounterID}/_sync
Description: Drops a priority event onto the Kafka fhir.sync.priority topic to trigger an immediate data pull from legacy on-premise systems for the specified Encounter.
Authorization: Requires a valid JWT. The API Gateway permits any authenticated user to hit this endpoint, as it only queues an asynchronous task.

Example Request:

HTTP
POST /api/v1/Encounter/Enc-33190/_sync HTTP/1.1
Host: api.hie-core.internal
Authorization: Bearer {{VALID_JWT}}
X-Request-ID: req-ghi-789
Content-Length: 0


6.2 Webhook Integrity and Transition Guard
Internal webhook events must satisfy all of the following before state advancement:
- source route must be non-public and canonicalized before routing evaluation
- HMAC signature must validate against rotating runner key
- event actor role must be runner_service identity, not end-user JWT
- transition request must match currently active pipeline step

6.3 State Safety Invariant
READY_FOR_DEPLOY is only reachable from SCANNING when scanner result hash matches signed artifact digest from trusted runner identity.
Any mismatch must force FAILED and trigger security incident event.

schema {
  query: Query
  mutation: Mutation
}

type Query {
  # Authenticated user context resolution
  me: UserContext!
  
  # Direct object lookups (Protected by OPA at the resolver level)
  patient(id: ID!): Patient
  practitioner(id: ID!): Practitioner
}

# --- IDENTITY SUBGRAPH ---

union UserContext = Patient | Practitioner

type Patient @key(fields: "id") {
  id: ID!
  active: Boolean!
  name: [HumanName!]!
  telecom: [ContactPoint!]
  
  # Forward-edge resolution
  encounters(last: Int, status: String): [Encounter!]!
  observations(category: String): [Observation!]!
}

type Practitioner @key(fields: "id") {
  id: ID!
  npi_number: String!
  name: [HumanName!]!
  specialty: String
  
  # REVERSE-EDGE RESOLVER (VULNERABILITY VECTOR 9.1)
  # This resolver uses the system service-account and fails to re-evaluate 
  # the requester's JWT if the requester is a Patient traversing the graph.
  activePatients: [Patient!]!
}

type HumanName {
  use: String
  family: String!
  given: [String!]!
}

type ContactPoint {
  system: String!
  value: String!
  use: String
}

# --- CLINICAL SUBGRAPH ---

type Encounter @key(fields: "id") {
  id: ID!
  status: String!
  period: Period!
  participants: [EncounterParticipant!]!
}

type EncounterParticipant {
  type: String # e.g., 'primary-performer', 'consultant'
  practitioner: Practitioner!
}

type Period {
  start: String!
  end: String
}

type Observation @key(fields: "id") {
  id: ID!
  status: String!
  category: String!
  code: CodeableConcept!
  valueQuantity: Quantity
  subject: SubjectReference!
}

type SubjectReference {
  reference: String! # e.g., "Patient/P-449102"
}

type CodeableConcept {
  text: String!
}

type Quantity {
  value: Float!
  unit: String!
}


5.3 Consistency Constraints for Authorization
Although tenant_id is partitioned in PK, write-path authorization must still validate:
- caller tenant matches entity tenant
- caller role is authorized for requested state transition
- asynchronous worker receives immutable auth context envelope (subject, role, tenant, decision_id)

5.4 Worker Input Validation
Kafka consumer must verify auth envelope signature and expiration before mutating pipeline state.
Messages without valid auth envelope are quarantined to dead-letter queue with incident tag AUTH_CONTEXT_MISSING.
