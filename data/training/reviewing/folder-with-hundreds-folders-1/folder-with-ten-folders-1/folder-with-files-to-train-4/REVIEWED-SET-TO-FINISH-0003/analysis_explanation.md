## Analysis reasoning

I reviewed four specification artifacts: `architecture.txt` (sections 4.0–4.1), `mapping.txt` (section 7.3), `grpc.txt` (section 5.3), and `kafka.txt` (section 6.3). No HAR trace is present in this folder. Evidence is entirely specification-grounded.

1. **BFLA at the HTTP-to-gRPC mapping layer**: the authorization boundary analysis starts with `architecture.txt` section 4.0 — the Edge BFF handles "authentication and coarse route controls" but "each privileged backend gRPC method must also enforce role-level checks." This establishes a two-layer model. The risk materializes when layer one (BFF route) is weak: `mapping.txt` section 7.3 states missing auth middleware on `/api/v1/admin/*` is a deployment blocker, confirming the middleware is not always present. If absent, a retail JWT reaches the gRPC invocation path without role verification at the HTTP tier. The combination of a documented gap and an explicit safety rule creates the BFLA surface.

2. **gRPC trust-boundary deferral is unsafe per explicit design guidance**: `architecture.txt` section 4.0 states "Trust in transport identity (mTLS peer) must not replace user-level authorization for admin operations." This is the precise anti-pattern that creates finding 2 — if the gRPC service trusts the mTLS peer (the BFF) and does not re-check the forwarded user role, it inherits any upstream authorization failure. `grpc.txt` section 5.3 confirms the required server-side enforcement for `ForceClearTransfer` and specifies that `PERMISSION_DENIED` must be returned "regardless of BFF route result" — an explicit defence-in-depth requirement.

3. **Kafka event provenance as downstream safeguard**: `kafka.txt` section 6.3 introduces the third layer of defence. Even if findings 1 and 2 both fail, the event consumer can still block the downstream effect of an unauthorized force-clear by rejecting events that lack signed authorization fields. The specification states: "if absent, event consumer must reject event and emit SECURITY_EVENT_INVALID_ADMIN_ACTION." An unauthorized force-clear would produce an event without valid `verified_authorization_decision_id` because the authorization service never issued a decision for the retail role invoking the admin method.

4. **Compound risk model**: the three findings form a layered BFLA with no single-point redundancy. All three protective layers (HTTP middleware, gRPC role check, event provenance) must be active simultaneously for the system to be secure. Any one layer failing results in a successful privilege escalation.

5. **Regulatory context**: `ComplianceAdminService.ForceClearTransfer` is an AML compliance action — unauthorized execution would mean AML holds can be cleared by retail-role users, directly violating regulatory mandates (FinCEN, FATF). This gives the BFLA finding systemic compliance impact beyond the technical severity.
