**Domain:** DevOps / Infrastructure-as-Code (IaC) / CI-CD

## 1.0 Executive Summary
InfraBuild CloudOps is an internal developer portal that wraps Terraform CLI operations to standardize cloud deployments across the organization. Instead of developers running `terraform apply` on their local machines, they trigger deployments via the InfraBuild web dashboard.

To track the current state of the deployed AWS infrastructure, Terraform requires a state file (`.tfstate`). Because state files contain a complete map of the cloud environment—including raw, unencrypted database master passwords, API keys, and private subnets—they are stored in a centralized, highly restricted Amazon S3 bucket (`s3://infrabuild-tf-state-prod`).

## 2.0 Network Topology & Storage Architecture
The system acts as a middleware broker between developers and the AWS cloud environment.

### 2.1 The Control Plane (API Gateway & Backend)
* **Ingress:** API Gateway handling requests from the React frontend.
* **Backend:** A Node.js microservice (`WorkspaceService`) that manages project configurations, environment variables, and AWS role assumptions.
* **Worker Nodes:** Ephemeral containers that pull down the Terraform code, download the state from S3, execute the deployment, and push the updated state back to S3.

### 2.2 The Storage Backend (S3 & DynamoDB)
* **S3 Bucket:** Stores the actual `terraform.tfstate` JSON files. Segmented by project folders.
* **DynamoDB:** Used for state locking (to prevent concurrent deployments from corrupting the state file).

## 3.0 Identity, Projects, and Authorization
Access to infrastructure is strictly compartmentalized by Project Teams.

### 3.1 Developer Authentication
Developers authenticate using GitHub Enterprise SSO, receiving a JWT.

### 3.2 Workspace Authorization (RBAC)
Every infrastructure environment is mapped to a `workspace_id`. The Node.js backend maintains a mapping in PostgreSQL of which developers belong to which workspaces.
* **Example:** User `dev_77` is assigned to `workspace_frontend_dev`. They are strictly prohibited from viewing or triggering deployments for `workspace_core_db_prod`.

## 4.0 Service Behavior Notes

## 5.0 PostgreSQL RBAC Schema (The Intended AuthZ)

```sql
-- 1. Workspaces Table
CREATE TABLE workspaces (
    workspace_id VARCHAR(100) PRIMARY KEY, -- e.g., 'workspace_core_db_prod'
    environment VARCHAR(20) NOT NULL,
    aws_account_id VARCHAR(12) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. Workspace Memberships (The Access Control List)
CREATE TABLE workspace_members (
    workspace_id VARCHAR(100) REFERENCES workspaces(workspace_id),
    user_id VARCHAR(50) NOT NULL, -- Extracted from GitHub SSO JWT
    role VARCHAR(20) DEFAULT 'viewer',
    PRIMARY KEY (workspace_id, user_id)
);
```

## 6.0 Implementation Notes (Node.js / Express)

### 6.1 ALTERNATE Storage API Route
```javascript
const AWS = require('aws-sdk');
const s3 = new AWS.S3();

// GET /api/v2/workspaces/:workspace_id/state
app.get('/api/v2/workspaces/:workspace_id/state', requireAuth, async (req, res) => {

    // 1. The user provides the target workspace in the URL path
    const targetWorkspace = req.params.workspace_id;
    const userId = req.user.id; // e.g., 'dev_77'

    // The code FAILS to query the PostgreSQL `workspace_members` table.
    // It should execute: SELECT * FROM workspace_members WHERE user_id = userId AND workspace_id = targetWorkspace;

    // 2. Blindly construct the S3 Path based on user input
    const params = {
        Bucket: 'infrabuild-tf-state-prod',
        Key: `${targetWorkspace}/terraform.tfstate`
    };

    try {
        // 3. Fetch from S3 using the Backend's IAM Role
        const data = await s3.getObject(params).promise();

        // 4. Return the highly sensitive JSON state file to the user
        res.setHeader('Content-Type', 'application/json');
        res.send(data.Body.toString('utf-8'));
    } catch (err) {
        res.status(404).send({ error: "State file not found" });
    }
});
```

## 8.0 Platform Operations Addendum
### 8.1 Pipeline Reliability Objectives
- Build-to-deploy target tracks end-to-end duration for standard release classes.
- Queue depth and worker saturation metrics control autoscaling for CI workloads.
- Artifact integrity checks run before deploy-stage promotion.

### 8.2 Runtime Telemetry
- Control-plane APIs expose latency, error-rate, and transition-rate dashboards.
- Webhook intake includes replay detection and source-identity trace correlation.
- On-call views correlate release events with production SLO deviations.

### 8.3 Release Discipline
- High-risk flow changes require staged rollout and rollback simulation evidence.
- Change windows are aligned with dependency maintenance calendars.
- Release notes include operational guardrails and post-release verification tasks.
