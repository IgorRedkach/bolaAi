## Findings

1. **Safety interlock workflow bypass on `POST /vendor-api/breaker/{id}/execute`**: the `ExecuteBreakerOperation` Go handler checks only that the caller's JWT role is `grid_operator` or `maintenance_tech`. The code explicitly omits validation of the `execution_token` that should be generated by the preceding `/validate` and `/acknowledge` steps (section 6.1 comment: "The code NEVER checks for the presence or validity of the 'execution_token'"). A caller can invoke `/execute` directly — skipping steps 1 and 2 of the three-step safety interlock — with any payload, including a missing or fabricated `execution_token`.

2. **Vendor API route exposes breaker execute endpoint from public internet**: the `/vendor-api/` path is intended for external maintenance contractors to upload diagnostic logs (section 2.1) and is accessible without the corporate Intranet/VPN restriction that protects `/api/v1/`. The HAR confirms the request originated from public IP `203.0.113.45` (outside the corporate network) via the vendor API route to the execute endpoint — combining the network exposure with the workflow bypass into a direct remote physical command path.

3. **Physical consequence confirmed**: `BRK-09-MAIN` is a 138 kV breaker in `CLOSED` state (electricity actively flowing, load 450.5 A per digital twin section 5.0). The dispatched `TRIP` / `LATCH_OFF` command physically opens the breaker circuit — interrupting 138 kV transmission. The `x-ot-gateway-latency-ms: 315` response header and `"edge_acknowledgement": true` confirm the DNP3 command reached the Edge Gateway and was sent to PLC node 14, point index 04.

## Evidence

- **HAR POST request** (`startedDateTime: 2026-04-08T19:15:33.001Z`, elapsed 420 ms): `POST https://api.voltguard.energy/vendor-api/breaker/BRK-09-MAIN/execute`; JWT encodes `sub: maint_user_44`, `role: maintenance_tech`; `x-forwarded-for: 203.0.113.45` (public IP); body `{"operation": "TRIP", "reason_code": "MANUAL_OVERRIDE"}` — no `execution_token` present.
- **HAR response**: HTTP 200 OK, `x-ot-gateway-latency-ms: 315`, `{"status": "COMMAND_DISPATCHED", "edge_acknowledgement": true}` — physical DNP3 CROB `LATCH_OFF` dispatched to PLC node address 14, point index 04 over the IPsec VPN to `SUB-TX-DALLAS-NORTH`.
- **Missing validation in handler** (section 6.1): the commented-out block `if !isValidExecutionToken(req.ExecutionToken, assetID)` is never executed. The function proceeds directly from role check to `OTGatewayClient.SendControlCommand(assetID, req.Operation)`.
- **Vendor API route scope** (section 2.1): `/vendor-api/` is described as "intended for external maintenance contractors to upload diagnostic logs" — it should not expose breaker execute endpoints.
- **Digital twin confirms pre-trip state** (section 5.0): `"physical_state": "CLOSED"`, `"voltage_kv": 138.0`, `"load_amps": 450.5` — a live, loaded high-voltage breaker was tripped.

## Reproduction

Step 1 — confirm the `/api/v1/` execute path requires the full workflow (control):

```bash
# Without execution_token — should return 412 Precondition Failed if workflow is enforced
curl -i -X POST "https://api.voltguard.energy/api/v1/breaker/BRK-09-MAIN/execute" \
  -H "Authorization: Bearer <JWT_maint_user_44_maintenance_tech>" \
  -H "Content-Type: application/json" \
  -d '{"operation": "TRIP", "reason_code": "MANUAL_OVERRIDE"}'
```

Step 2 — use the vendor API path to bypass the interlock workflow:

```bash
curl -i -X POST "https://api.voltguard.energy/vendor-api/breaker/BRK-09-MAIN/execute" \
  -H "Authorization: Bearer <JWT_maint_user_44_maintenance_tech>" \
  -H "Content-Type: application/json" \
  -d '{"operation": "TRIP", "reason_code": "MANUAL_OVERRIDE"}'
```

Expected secure outcome: HTTP 412 (Precondition Failed) — no valid `execution_token` from the completed `/validate` → `/acknowledge` workflow; or HTTP 403 — the `/vendor-api/` path does not expose the execute endpoint.  
Observed vulnerable outcome: HTTP 200 `{"status": "COMMAND_DISPATCHED", "edge_acknowledgement": true}` — breaker `BRK-09-MAIN` at `SUB-TX-DALLAS-NORTH` physically tripped, 138 kV circuit opened.

## Remediation

- **Implement `execution_token` validation in `ExecuteBreakerOperation`**: uncomment and implement `isValidExecutionToken(req.ExecutionToken, assetID)` — the token must be cryptographically signed by the server after a successful `/acknowledge` step, time-limited (e.g., 5 minutes), single-use, and bound to the specific `assetID`. Reject any request without a valid token with HTTP 412.
- **Remove breaker control endpoints from the `/vendor-api/` route in Kong/AWS API Gateway**: the vendor API should only expose diagnostic log upload paths, not any `/breaker/{id}/execute` route. Add an explicit route blocklist for `/vendor-api/breaker/*/execute`.
- **Restrict `/vendor-api/` to source IP allowlist**: even for legitimate diagnostic uploads, the vendor API should be limited to known contractor IP ranges or VPN exit nodes — reject requests from public IPs such as `203.0.113.45`.
- **Require `grid_operator` role for breaker execute**: a `maintenance_tech` should not have execute-command authority for live HV breakers. Change the role check in `ExecuteBreakerOperation` to `if userRole != "grid_operator"` and require a dual-operator confirmation for live 138 kV assets.
