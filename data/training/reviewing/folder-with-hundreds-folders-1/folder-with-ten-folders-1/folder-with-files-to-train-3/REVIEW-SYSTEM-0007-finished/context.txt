## 1.0 Executive Summary
VoltGuard is a hybrid IT/OT (Information Technology / Operational Technology) platform. It allows regional grid operators to monitor substation telemetry and execute remote switching operations (e.g., opening/closing high-voltage breakers) without dispatching a technician in a truck.

To bridge the gap between cloud infrastructure and physical hardware, VoltGuard utilizes a Cloud-to-Edge architecture. A web-based Human-Machine Interface (HMI) talks to a RESTful API Gateway in AWS. This gateway communicates over a site-to-site IPsec VPN to an Edge Gateway located inside the substation DMZ, which translates the JSON payloads into DNP3 commands for the physical Programmable Logic Controllers (PLCs).

## 2.0 Network Topology & IT/OT Boundaries
Strict network segmentation is mandated by NERC CIP (North American Electric Reliability Corporation Critical Infrastructure Protection) regulations.

### 2.1 The IT Cloud Plane (Control Center)
* **Primary Web HMI:** Only accessible via the corporate Intranet/VPN. 
* **Cloud API Gateway:** Routes all frontend JSON requests to the backend Go microservices.
* **Vendor API (The Exposure Point):** A secondary, heavily restricted API path (`/vendor-api/`) intended for external maintenance contractors to upload diagnostic logs. 

### 2.2 The OT DMZ & Physical Substation Edge
* **Edge Gateway:** A hardened industrial PC sitting in the substation. It drops all traffic except verified payloads originating from the IT Cloud Plane over the IPsec tunnel.
* **The PLC Network:** Completely air-gapped from the internet. PLCs communicate via serial or local Ethernet using the DNP3 protocol.

## 3.0 Identity, Safety Logic, and Authorization
Controlling physical power grids requires strict identity verification and multi-step safety validations.

### 3.1 Operator Identity
Grid Operators authenticate using hardware MFA (YubiKey) via PingIdentity. They receive an OAuth2 JWT containing their role (`grid_operator` or `maintenance_tech`).

### 3.2 The Multi-Step Safety Interlock Workflow
To prevent accidental power outages or arc flashes, opening a live breaker requires a strict, three-step software workflow modeled in the API:
1.  **Validate Safety Interlock (`POST /api/v1/breaker/{id}/validate`):** The system queries physical sensors to ensure load levels are safe for switching. Returns a `validation_token`.
2.  **Acknowledge Warning (`POST /api/v1/breaker/{id}/acknowledge`):** The operator signs off on the hazard warning, submitting the `validation_token`. Returns an `execution_token`.
3.  **Execute Command (`POST /api/v1/breaker/{id}/execute`):** The final endpoint that actually sends the DNP3 `TRIP` command to the PLC.

## 7.0 OT Translation Contract (Cloud to Edge to PLC)
This maps how a standard JSON web request is translated into a physical hardware action.

### 7.1 The REST Execution Payload (Cloud API)
**Target Endpoint:** `POST /api/v1/breaker/BRK-09-MAIN/execute` (or maliciously via `/vendor-api/breaker/BRK-09-MAIN/execute`)
**Expected Payload:**
```json
{
  "operation": "TRIP",
  "reason_code": "EMERGENCY_LOAD_SHED",
  "execution_token": "ext_99182a" // Backend ignores this field entirely
}
```

### 7.2 The DNP3 Translation (Edge Gateway to PLC)
When the Edge Gateway receives the validated JSON payload from the Cloud API over the IPsec tunnel, it translates it into a DNP3 **Control Relay Output Block (CROB)**.

* **Protocol:** DNP3 (IEEE 1815) over TCP/IP (Port 20000)
* **Target Device:** RTU/PLC Node Address 14
* **Object Group:** 12 (Control Relay Output Block)
* **Variation:** 1
* **Point Index:** 04 (Mapped to physical relay controlling BRK-09-MAIN)
* **Control Code:** `LATCH_OFF` (Physically opens the breaker circuit)
