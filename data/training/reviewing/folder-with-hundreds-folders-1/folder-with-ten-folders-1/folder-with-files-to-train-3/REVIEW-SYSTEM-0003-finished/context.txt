# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** VitaStream Telehealth Data Lake
**Document Version:** 2.4.1 (FINAL)
**Classification:** HIPAA SENSITIVE / EPHI (Electronic Protected Health Information)
**Domain:** Healthcare / Telemedicine / Clinical Aggregation

## 1.0 Executive Summary
VitaStream is a high-performance clinical aggregation platform used by telehealth physicians. Because assembling a patient's complete medical history (labs, imaging reports, past encounters) from various siloed Electronic Health Record (EHR) systems takes 3–5 seconds, VitaStream implements an aggressive Edge Caching and Data Lake architecture to bring response times under 100 milliseconds.

The system relies on an AWS API Gateway sitting in front of a distributed Redis Cache cluster. If a clinical summary has been recently compiled, it is served directly from memory, completely bypassing the heavy backend FHIR (Fast Healthcare Interoperability Resources) data lake.

## 2.0 Network Topology & Caching Infrastructure
To achieve sub-100ms latency, the network intercepts read-heavy requests at the boundary.

### 2.1 The Edge & API Gateway
* **Ingress:** All web and mobile traffic hits the external API Gateway (`api.vitastream.health`).
* **Caching Middleware:** Before a request is routed to the backend microservices, an ElastiCache (Redis) lookup is performed.
* **Backend Data Lake:** A cluster of Python FastAPI microservices that query an Amazon S3 Data Lake and an Aurora PostgreSQL metadata database to assemble FHIR clinical documents.

### 2.2 The Cache Key Strategy
When the backend generates a Clinical Summary, the API Gateway caches the JSON response.
* **Cache Expiration (TTL):** 15 minutes.
* **Cache Key Formulation:** The caching middleware generates the Redis lookup key using a hash of the HTTP Method and the URI Path. 
  * *Example Key:* `SHA256("GET" + "/api/v2/patients/P-7712/clinical-summary")`

## 3.0 Identity and Access Control
VitaStream enforces strict HIPAA compliance regarding who can view a patient's data.

### 3.1 Authentication
Physicians authenticate via Okta using SAML 2.0, receiving an OAuth2 Bearer Token (JWT). The token contains their National Provider Identifier (NPI) and their assigned clinic.

### 3.2 Backend Authorization (The "Care Team" Check)
When the backend FastAPI service receives a request, it performs a strict "Care Team" check. It queries the PostgreSQL database to ensure that the requesting Doctor has an active, documented clinical relationship with the requested Patient ID. If no relationship exists, the backend returns a `403 Forbidden`.

System behavior, data contracts, and operational sequencing are described in subsequent sections.

```yaml
# Gateway Routing & Cache Policy
routes:
  - match:
      prefix: "/api/v2/patients/"
    route:
      cluster: backend_data_lake
    typed_per_filter_config:
      envoy.filters.http.cache:
        "@type": type.googleapis.com/envoy.extensions.filters.http.cache.v3.CacheConfig
        # It hashes ONLY the :path and :method. 
        # The Authorization header (JWT) is NOT part of the cache signature.
        cache_key_builder:
          exclude_scheme: true
          exclude_host: true
          exclude_query_string_parameters: []
          headers_to_include: [] # CRITICAL implementation detail: Should include "Authorization"
        allowed_vary_headers:
          - "Accept"
        max_age_in_seconds: 900 
```

## 7.0 Expected API Contract 
The REST contract intended for the mobile application and web portal.

### 7.1 Retrieve Patient Summary
**Endpoint:** `GET /api/v2/patients/{patient_id}/clinical-summary`
**Description:** Fetches the aggregated 360-degree view of a patient.
**Authorization Verification (Intended):** Backend FastAPI service queries `SELECT count(*) FROM care_teams WHERE provider_npi = $1 AND patient_id = $2`.

**Required Headers:**
```http
Authorization: Bearer <Okta OAuth2 JWT>
Accept: application/json
X-Request-Trace: <UUID>
```






# SYNTHETIC ARTIFACT: CACHE-KEY POISONING / AUTHZ MISMATCH (HAR TRACE)
**Applies to Architecture:** VitaStream Telehealth Data Lake v2.4.1


First, Dr. Smith (the authorized provider) requests the patient's data, resulting in a cache `MISS` and a backend fetch. 45 seconds later, Dr. Jones (an unauthorized provider) requests the exact same URL. The API Gateway sees a cache `HIT` and serves Dr. Smith's cached response directly to Dr. Jones, completely bypassing the backend database's "Care Team" authorization check.

## 8.0 Clinical Operations Addendum
### 8.1 Care Delivery Performance Targets
- Clinical summary retrieval target: p95 under 1.8 seconds during outpatient peak windows.
- Encounter synchronization jobs are rate-limited to protect downstream EHR connectors.
- Batch export windows are scheduled to avoid physician shift-change periods.

### 8.2 Data Governance and Audit
- Access logs retain provider identity, tenant marker, and data-access purpose codes.
- Audit exports are retained under healthcare record retention policy baselines.
- Data correction workflows require immutable append-only revision history.

### 8.3 Incident Readiness
- Joint operations bridge includes API, integration, and compliance teams.
- Playbooks define degraded-mode behavior for cache outage and connector latency spikes.
- Post-incident reviews track control drift and compensating-control effectiveness.
