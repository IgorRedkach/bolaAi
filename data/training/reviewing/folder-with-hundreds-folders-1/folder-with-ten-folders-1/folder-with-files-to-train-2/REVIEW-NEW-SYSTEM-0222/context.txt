## 1.0 Executive Summary
SocialLoop is a large, public social network. The Trust & Safety Gateway manages the entire lifecycle of abuse reports, content takedowns, and user bans. Due to massive scale (millions of posts per hour), the post deletion process is handled by a dedicated, highly privileged microservice that is only meant to be called by the internal moderation queue.


## 2.0 Comprehensive Network Topology & Workflow Core
The system is built as a complex, multi-stage workflow to separate the human review process from the final, irreversible database deletion.

### 2.1 The Edge & Ingress Layer
* **Edge Proxy (Envoy):** Handles TLS termination and basic rate limiting.

### 2.2 The Internal Workflow & Identity Mesh
* **Moderation Service:** A Python/Django service that manages the queue of flagged content and requires explicit human approval before deletion.
* **Final Deletion Service:** A highly restricted Java microservice that executes the final SQL `DELETE` command against the production database. It has an internal endpoint, `/internal/v1/posts/{id}/force-delete`, which is **only** intended to be called by the Moderation Service. It uses a simplistic identity propagation model.

## 3.0 Identity, Trust, and Workflow Authorization
The security flaw resides in the assumption that the source of an internal request can be trusted.

### 3.1 External Identity (OAuth 2.0)

### 3.2 Internal Identity Drift (The Flaw)
The Final Deletion Service uses an internal `X-Internal-User-ID` header for audit logging (Pattern 1.10). Crucially, it **also uses the presence of this header as a proxy for authorization**. If the request comes from within the Service Mesh and contains a valid internal token (which is easily guessable or found in debug logs), the service assumes the request is legitimate and executes the deletion without re-verifying if the post owner is the current caller.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The `force-delete` endpoint was created to handle mass cleanup after a platform outage. It uses an internal system token that was never rotated. Tracked as RISK-TS-500.*

**Taxonomy Pattern:** 3.2 (Workflow Decoupling) & 1.10 (Identity Propagation Drift)
**Sub-system:** Final Deletion Service (`/api/v1/posts/{id}/delete`)

**The Deep Architectural Flaw:**
This attack chains a lack of workflow integrity with a spoofable internal identity context.


2. **Identity Propagation Drift (Pattern 1.10):** The Final Deletion Service requires two security elements to execute: a known, internal `X-Service-Token` (which the attacker discovers) and an `X-Internal-User-ID` header for auditing. The service blindly trusts the `X-Internal-User-ID` header as the deletion initiator. The attacker simply sets this to their own user ID, bypassing the need to verify ownership of the content ID passed in the URI.


1. **Reconnaissance:** An attacker (`user_8819X`) finds a low-traffic API endpoint that reflects a successful post ID (`post_target_A`) belonging to a high-profile user (`user_991B`). They also discover the internal `X-Service-Token` (e.g., `trust-service-a1b2c3d4e5f6`) via a verbose error message on another endpoint.


3. **The Execution:** The request hits the Final Deletion Service. Because the service sees the required `X-Service-Token`, it assumes the request originated from the trusted Moderation Queue (bypassing Step 2 of the workflow). The service executes the SQL `DELETE` based on the post ID in the URI.

4. **The Impact:** The attacker, a standard user, successfully deletes a post belonging to any other user on the entire platform. The audit trail simply logs: `Post post_target_A deleted by user_8819X`.

## 5.0 Core Content Database Schema (PostgreSQL)
The core content database stores all user-submitted posts. Deletion must be strictly audited.

```sql
-- Core User Content Table
CREATE TABLE user_posts (
post_id VARCHAR(50) PRIMARY KEY, -- The URI Path variable
content_text TEXT NOT NULL,
status VARCHAR(20) DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'DELETED', 'PENDING_REVIEW')),
created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP

CREATE INDEX idx_author_lookup ON user_posts(author_user_id);

-- Audit Log for Takedowns

audit_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
post_id VARCHAR(50) REFERENCES user_posts(post_id),
initiating_service VARCHAR(50) NOT NULL, -- e.g., 'MODERATION_SERVICE'
initiating_user_id VARCHAR(100) NOT NULL, -- The user ID from the header (THE SPOOF TARGET)
executed_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
```

## 6.0 The Flawed Implementation (Java / Spring Boot)

```java
package com.socialloop.deletion.controllers;

import org.springframework.web.bind.annotation.*;
import javax.servlet.http.HttpServletRequest;

@RestController
@RequestMapping("/api/v1/posts")
public class DeletionController {
// DELETE /api/v1/posts/{id}  
@DeleteMapping(value = "/{id}")  
public ResponseEntity<String> deletePost(@PathVariable("id") String postId, HttpServletRequest request) {  
    
    String internalToken = request.getHeader("X-Service-Token");  
    if (!"trust-service-a1b2c3d4e5f6".equals(internalToken)) {  
        // The service assumes ONLY the Moderation Service will have this token.  
        return ResponseEntity.status(401).body("{\"error\": \"Unauthorized Service Token\"}");  
    }  
    
    // Attacker-controlled header is used for logging and assumed to be the deletion authority.  
    String internalUserID = request.getHeader("X-Internal-User-ID");  
    
    if (internalUserID == null) {  
        return ResponseEntity.badRequest().body("{\"error\": \"Missing audit context\"}");  
    }  
    
    // The code should verify if internalUserID owns 'postId' before deletion.  
    // Instead, it relies on the presence of the internal token as a proxy for authority.  
    if (db.deletePost(postId, internalUserID)) {  // Executes DELETE FROM user\_posts WHERE post\_id = postId
        // Log the action using the spoofed ID
        auditLog.logDeletion("DELETION\_SERVICE", postId, internalUserID);
        return ResponseEntity.ok("{\"status\": \"Post deleted successfully\"}");
    } else {
        return ResponseEntity.status(404).body("{\"error\": \"Post not found or already deleted\"}");
    }
} 
}
```

This contract illustrates how the attacker forces a low-privileged request to be treated as a highly privileged, internal system action by injecting the required internal headers.
