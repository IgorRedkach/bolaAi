## 1.0 Executive Summary
RailGrid ROMS is the primary Operational Technology (OT) platform used to manage all aspects of rail movement, including automated train control, Positive Train Control (PTC) monitoring, and, crucially, the remote actuation of track switches (or "points"). This system operates under strict regulations requiring redundant, multi-step safety interlocks to prevent unauthorized or unsafe movements.


## 2.0 Comprehensive Network Topology & Signaling Core
The architecture maintains a strict, high-security barrier between the IT client layer and the physical OT execution layer.

### 2.1 The HMI & IT Ingress
* **Edge Load Balancer:** Handles mTLS termination for authenticated HMI clients (desktop web browsers).
* **ROMS API Gateway (Node.js/HAPI):** The Policy Enforcement Point (PEP). It validates the JWT for signature integrity and user role.

### 2.2 The OT Control Mesh
* **Switch Management Service (SMS - Python/Django):** A highly restricted microservice. It manages the state machine for all track switches and exposes internal endpoints for actuation.
* **PLC Communications Layer:** A hardened Go-lang service that translates internal API commands (e.g., set_state(REVERSE)) into proprietary industrial control protocols (e.g., Modbus TCP or GE-specific protocol) sent to the physical PLCs controlling the switches.

## 3.0 Identity, Geographic Zones, and Safety Interlocks
Authorization is based on a combination of user role and geographic operational zone, as mandated by safety regulations.

### 3.1 Operator Identity (OAuth 2.0 & Role Claims)
Rail operators authenticate via their operational terminal. Their JWT contains their employee_id and their assigned operational zone (zone_id), e.g., ZONE-YARD-A (low-priority maintenance yard) or ZONE-MAIN-LINE-C (high-priority passenger line).

Switch actuation is a mandatory three-step workflow designed to prevent unauthorized or concurrent changes:
LOCK: Operator requests a lock on the target switch to establish exclusive control (/lock).
VALIDATE: System verifies that the switch is available and not part of an active PTC route (/validate-safety).
EXECUTE: System sends the final command to the PLC (/actuate).
The critical RBAC failure occurs because the system only checks the zone_id during the initial LOCK request (Step 1).

## 4.0 Known System Debt & Theoretical Attack Surfaces
Internal Security Engineering Note: The validate-safety service was recently refactored to check a new X-PTC-Status header before querying the slow PTC mainframe. The Python SMS service was deployed with a default "fail-open" setting when it cannot parse critical request headers. Tracked as RISK-RAIL-007.

**Taxonomy Pattern:** 1.13 (IoT/SCADA Device ID Manipulation), 3.5 (Unsecured Critical Workflow), & 8.3 (Fail-Open)
**Sub-system:** Switch Management Service (SMS) (`POST /api/v3/switches/{id}/actuate`)

**The Deep Architectural Flaw:**

2. **Unsecured Workflow (Pattern 3.5):** The SMS service, responsible for Steps 2 and 3, fails to re-verify the zone_id claim from the JWT in subsequent requests. The attacker only needs to pass the initial, low-stakes LOCK check. They can then jump directly to the highly privileged ACTUATE endpoint, substituting the switch ID with the high-value target.
3. **Fail-Open on Security Check (Pattern 8.3):** The ACTUATE endpoint requires a proprietary header, X-PTC-Verified, to be present. If this header is missing or malformed, the SMS service defaults to ALLOW (fail-open) instead of DENY (fail-close), assuming the front-end failed to send the header but the core safety was handled elsewhere.

1. **The Foothold:** A low-privileged operator (`user_yard_1004`) authenticates with a JWT scoped to ZONE-YARD-A.
3. **The Fail-Open Injection:** The operator omits the mandatory X-PTC-Verified header (or injects an invalid value).
4. **The Cascade:** The ROMS API Gateway passes the request (lacking a functional RBAC check for this path). The SMS service receives the request, sees the switch ID is a high-value asset, but proceeds:
*   PTC Check: Fails to read X-PTC-Verified (omitted header), defaults to ALLOW.
5. **The Impact:** The SMS service executes the final PLC command, forcing the track switch SW-MAIN-001 to change position (e.g., from NORMAL to REVERSE), creating an immediate derailment risk for any active trains on the main line.

## 5.0 Core Switch Asset Registry (PostgreSQL)
The database enforces the geographical boundary of rail assets. The predictable naming scheme of the asset IDs makes them easily enumeratable.

```sql
-- 1. Track Switch Asset Inventory
CREATE TABLE rail_switches (
zone_id VARCHAR(50) NOT NULL,      -- e.g., 'ZONE-MAIN-LINE-C' (THE RESTRICTED ZONE)
location_coords POINT NOT NULL,
current_state VARCHAR(10) CHECK (current_state IN ('NORMAL', 'REVERSE', 'UNKNOWN')),
is_locked BOOLEAN DEFAULT FALSE,   -- Set during Step 1 (LOCK)
last_ptc_check TIMESTAMP WITH TIME ZONE
);

-- 2. Operator-to-Zone Mapping (RBAC Context)
CREATE TABLE rail_operators (
employee_id VARCHAR(100) PRIMARY KEY,
zone_id VARCHAR(50) NOT NULL,      -- e.g., 'ZONE-YARD-A' (THE ATTACKER'S ZONE)
role VARCHAR(20) CHECK (role IN ('YARD_OPERATOR', 'MAIN_LINE_DISPATCHER', 'MAINTENANCE'))
);

CREATE INDEX idx_switch_zone ON rail_switches(zone_id);
```

### Why this payload is critical for training a 3B model (Expanded Analysis):

* **Irreversible Physical State Change:** The model learns to prioritize the irreversible consequences. The ACK_SW_001_RVR header and ACTUATION_SUCCESS status confirm the physical rotation of a track switch, a critical safety violation.

2. **Fail-Open Security Logic (Pattern 8.3):**
* **Omitted Header Proof:** The absence of the X-PTC-Verified header in the request is the attacker's deliberate action. The response explicitly contains the warning, `PTC check header was missing in request.`, yet the status is 200 OK. This combination is the definitive proof of a system defaulting to an unsafe ALLOW state when faced with a missing security parameter.

3. **Workflow Decoupling (Pattern 3.5):**
* The attacker only needed to pass the initial, low-stakes LOCK check. They bypassed the entire VALIDATE-SAFETY step by abusing the fail-open logic in the final ACTUATE step. The model learns that security controls must be fully re-validated at every step of a critical multi-step workflow.

4. **Contextual Latency:**
* The high latency of 780ms is expected in this context, teaching the model that in OT systems, high latency is normal (due to PLC command execution time) but confirms the malicious command successfully left the low-latency IT domain and entered the slower, high-stakes physical control domain.
