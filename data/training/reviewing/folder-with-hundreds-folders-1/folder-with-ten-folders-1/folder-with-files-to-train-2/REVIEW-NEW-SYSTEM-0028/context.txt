## 1.0 Executive Summary
StreamVerse is a global VOD platform that hosts content from thousands of independent studios and creators ("Content Partners"). The platform’s core function is to manage the lifecycle of these assets, from ingestion and encoding to distribution and monetization (ad placement, subscription tiers).


## 2.0 Comprehensive Network Topology & Content Lifecycle
The architecture is designed to handle high-volume write operations for asset metadata while maintaining robust control over intellectual property rights.

### 2.1 The Asset Management Ingress
* **Edge Load Balancer:** Standard L7 load balancing.
* **Metadata API Gateway (Python/Django):** The primary interface for Content Editors. It enforces JWT validation and usage throttling. All metadata updates flow through a single, high-traffic `PATCH` endpoint.

### 2.2 The Backend & Monetization Core
* **PostgreSQL Master Asset Registry:** The source of truth for all content metadata, including the highly sensitive `content_owner_id` used for revenue calculation.
* **Monetization Engine (Java):** An internal service that consumes the `content_owner_id` to calculate and remit monthly revenue shares. This engine trusts the ownership record stored in the PostgreSQL database implicitly.
* **DRM Service:** Handles encryption keys; its access controls are derived directly from the `content_owner_id` metadata field.

## 3.0 Identity, Roles, and Ownership Boundaries
The security model is based on functional roles, but the integrity flaw allows a horizontal privilege escalation via data manipulation.

### 3.1 Role Definitions (The Functional Pivot Target)
| Role | Access Scope | Write Access to Critical Fields |
| :--- | :--- | :--- |
| CONTENT_EDITOR (Low Privilege) | Write metadata (title, tags, description). | No access to `content_owner_id`. |
| EXECUTIVE_PRODUCER (High Privilege) | All writes; can update `content_owner_id`. | Restricted function via separate API endpoint. |

### 3.2 Ownership Enforcement (The Flaw)
The Content Editor's primary endpoint, `/api/v1/assets/{id}/metadata`, should only accept and update fields defined in the Content Metadata Data Transfer Object (DTO) (e.g., `title`, `description`). The critical flaw is the backend Python service's failure to implement this DTO, allowing the attacker to inject and overwrite the restricted `content_owner_id` field (Pattern 1.12). This silent overwrite enables the attacker to commit a write operation without a specific ownership check on the restricted field (Pattern 1.6).

## 4.0 Known System Debt & Theoretical Attack Surfaces
Internal Security Engineering Note: The core metadata update endpoint was built using Django REST Framework's generalized `ModelViewSet`, which automatically binds all fields in the database model to the inbound JSON payload for convenience. Epic: CMM-301 to implement `serializer.fields.only` was deferred. Tracked as RISK-MEDIA-009.

**Taxonomy Pattern:** 1.12 (Mass Assignment) & 1.6 (Write operations without ownership check)
**Sub-system:** Metadata API Gateway (`PATCH /api/v1/assets/{id}/metadata`)

**The Deep Architectural Flaw:**

1. **Mass Assignment (Pattern 1.12):** The Django ORM layer receives the HTTP `PATCH` request body. It uses a dynamic update method that maps every key in the incoming JSON payload directly to the corresponding column in the `content_assets` table, regardless of the calling user's role.

2. **Ownership Transfer (Pattern 1.6):** An attacker (Content Editor, `user_editor_A`) targets a high-value asset (`asset_id: VID-BLOCKBUSTER`) owned by a major studio (`owner_id: STUDIO_HOLLYWOOD`). The attacker crafts a payload that includes legitimate metadata fields (e.g., `"description": "Updated tags"`) but injects the administrative field `"content_owner_id": "user_editor_A"`.

3. **The Execution:** The low-privileged user's request is accepted because it uses an authorized endpoint. The ORM executes the update, silently overwriting the ownership field. The attacker has effectively executed a write operation (`PATCH`) on a security-critical field without the server ever checking if the `CONTENT_EDITOR` role is authorized to modify the `content_owner_id`.

4. **The Impact:** The ownership record is permanently transferred to the attacker. The next cycle of the Monetization Engine calculates revenue for the blockbuster asset and remits 100% of the funds to the attacker's affiliated payment account, resulting in financial fraud and IP theft (Persistence Poisoning, Pattern 4.2).

## 6.0 The Flawed Implementation (Python / Django REST Framework)

```python
# File: api/cmm/views.py
from rest_framework.viewsets import ModelViewSet
from rest_framework.response import Response
from .serializers import AssetMetadataSerializer
from .models import ContentAsset

class AssetMetadataViewSet(ModelViewSet):
queryset = ContentAsset.objects.all()
serializer_class = AssetMetadataSerializer
lookup_field = 'asset_id'

# PATCH /api/v1/assets/{id}/metadata
def partial_update(self, request, *args, **kwargs):
asset = self.get_object() # Fetches ContentAsset based on asset_id

# Check 1: Ensures user has a role allowed to edit metadata (passes for CONTENT_EDITOR)
if request.user.role not in ['CONTENT_EDITOR', 'EXECUTIVE_PRODUCER']:
return Response({"error": "Role unauthorized to modify metadata."}, status=403)

# The serializer is initialized with partial=True, allowing PATCH, and uses request.data.
# The underlying serializer allows all fields from the model by default (including content_owner_id).
serializer = self.get_serializer(asset, data=request.data, partial=True)
serializer.is_valid(raise_exception=True)
# The serializer.save() method blindly commits all fields present in the request payload.
# If 'content\_owner\_id' is in request.data, it is silently overwritten.
serializer.save()  

return Response(serializer.data, status=200)  
```

### 6.2 The Unrestricted Serializer Definition (The Technical Root Cause)
The default Django REST Framework `ModelSerializer` uses `fields = '__all__'`, meaning it automatically exposes and allows write operations for every column in the `ContentAsset` model, including the restricted `content_owner_id`.

```python
# File: api/cmm/serializers.py
from rest_framework import serializers
from .models import ContentAsset

class AssetMetadataSerializer(serializers.ModelSerializer):
class Meta:
model = ContentAsset
fields = '__all__' # CRITICAL FLAW: Exposes and allows updates to content_owner_id
read_only_fields = ['total_views', 'last_updated'] # Fails to include 'content_owner_id'
```

## 7.0 REST API Contracts (The Ownership Injection)
The contract illustrates how the attacker uses the Mass Assignment flaw to change the financial ledger's ownership record without any special privileges.

### 7.1 Intended Safe Payload (Metadata Update)
A low-privileged editor updates the description of a video asset they are working on.

**Target URI:** `PATCH /api/v1/assets/VID-BLOCKBUSTER/metadata`
**Expected Request Payload:**
```json
{
"description": "Final cut version. Approved for premium tier."
}
```

### 7.2 The Mass Assignment Injection Payload (Attacker)
The attacker (`user_editor_A`) targets the high-value asset and injects the `content_owner_id` field, setting its value to their own user ID, effectively transferring the digital rights and revenue stream.

**Target URI:** `PATCH /api/v1/assets/VID-BLOCKBUSTER/metadata`
**Malicious Request Payload:**
```json
{
"description": "Final cut version. Approved for premium tier.",
"content_owner_id": "user_editor_A",
"last_audited_by": "user_editor_A" # Secondary injection to cover tracks
}
```
*Behavior:* The ORM executes the database update, changing ownership from `STUDIO_HOLLYWOOD` to `user_editor_A`.
