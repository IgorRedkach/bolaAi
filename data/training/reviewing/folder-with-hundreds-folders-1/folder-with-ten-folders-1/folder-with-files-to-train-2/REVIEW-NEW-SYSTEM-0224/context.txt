## 1.0 Executive Summary
QuantEX is a modern brokerage platform designed for high-frequency algorithmic traders. It provides a REST API that allows clients to submit orders (buy/sell) for various financial assets (stocks, options, derivatives). The platform requires near-zero latency, as trade speed is a critical competitive advantage.

When a user submits a market or limit order, the system must perform a critical authorization step: a **Net Liquidity Check** (i.e., verifying the user has enough cash to buy or enough stock to sell). To maximize throughput, this check is designed to be highly parallel, but this concurrency comes at the cost of transactional integrity due to missing database locks.

## 2.0 Comprehensive Network Topology & Execution Core
The architecture is optimized for speed, prioritizing throughput over traditional, slower locking mechanisms.

### 2.1 The Edge & Ingress Layer
* **Edge Load Balancers (L4):** Handles raw TCP connections for market data streaming (WebSockets).
* **Order Submission API (Java/Quarkus):** A lightweight, low-latency microservice that handles all inbound REST trade requests (`/api/v1/orders/submit`).

### 2.2 The Backend Ledger & Matching Engine
* **PostgreSQL (The Ledger):** The primary source of truth for user balances (cash and asset inventory).
* **Transaction Engine (Go-lang):** Executes the final state changes (deduct cash, add shares) and routes the order to the high-speed matching engine (FIX Protocol).

## 3.0 Identity, Authorization, and Financial Integrity
The system's core integrity relies on the financial safety check being unbreakable.

### 3.1 Trader Authentication (OAuth 2.0)
Traders authenticate using their personal private keys/passwords, receiving a standard JWT containing the `trader_id` and their associated `brokerage_account_id`.

Before executing any trade, the Order Submission API runs a check: `IF user.balance >= requested_amount THEN PROCEED`. This logic is a classic Time-of-Check (ToC). The critical Time-of-Use (ToU) is the database update that occurs after the order is successfully submitted to the matching engine. The gap between the ToC and the ToU is the race window.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The performance team removed all transactional row-level locks (`SELECT ... FOR UPDATE`) from the order validation query in Q2 2025 (PR-HFT-404) to reduce DB contention during peak volume events. This decision was accepted with a note to re-evaluate the risk of double-spending via concurrency. Tracked as RISK-FIN-009.*

**Sub-system:** Order Submission API (`/api/v1/orders/submit`)

**The Deep Architectural Flaw:**

1. **Race Condition (Pattern 8.1):** The Order Submission API reads the user's current share inventory (`shares_owned`) to check if they can execute a sale. It then immediately routes the order to the high-speed execution engine (which takes ~50-100ms) before returning to update the user's inventory in the database. During this 50-100ms window, the user's balance is stale.


1. **The Setup:** An attacker acquires exactly 1,000 shares of a high-volatility stock (`TSLA`).
2. **The Concurrency Strike:** The attacker submits two simultaneous HTTP POST requests to `/api/v1/orders/submit`. Both requests instruct the system to `SELL 1,000 shares of TSLA`.
3. **The Collision:**
* *Request 1 (Thread A):* Queries DB. Reads `shares_owned = 1000`. Passes check. Proceeds to execution.
* *Request 2 (Thread B, 5ms later):* Queries DB. Reads `shares_owned = 1000` (Thread A hasn't updated the balance yet). Passes check. Proceeds to execution.
4. **The Drain:** Both Thread A and Thread B successfully execute their orders. The HFT platform sells 2,000 shares of TSLA on the market, but the attacker only owned 1,000.
5. **The Result:** The attacker extracts the cash from the sale of 2,000 shares, and the brokerage platform's ledger records a negative inventory of 1,000 shares for the attacker, forcing the brokerage to cover the shortfall at a loss.

## 5.0 Trading Ledger Schema (PostgreSQL)

```sql
-- 1. Trader Accounts Table (The Cash Balance)
CREATE TABLE trader_accounts (
account_id UUID PRIMARY KEY,
trader_id VARCHAR(100) NOT NULL,
cash_balance DECIMAL(38, 8) DEFAULT 0.00000000,
margin_enabled BOOLEAN DEFAULT FALSE,
created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. Asset Inventory Table (The Shares Balance)
CREATE TABLE asset_inventory (
inventory_id SERIAL PRIMARY KEY,
account_id UUID REFERENCES trader_accounts(account_id),
ticker VARCHAR(10) NOT NULL,
avg_cost DECIMAL(38, 8),
UNIQUE (account_id, ticker)
);
CREATE INDEX idx_account_ticker ON asset_inventory(account_id, ticker);
```

## 6.0 The Flawed Implementation (Java / Quarkus Framework)

```java
// File: com.quantex.api.OrderController

@POST
@Path("/submit")
@Produces(MediaType.APPLICATION_JSON)
@Transactional // Standard JTA/JDBC Transaction (DOES NOT include row locks)
public Response submitOrder(OrderRequest request) {
String accountId = securityContext.getAccountId();
String ticker = request.getTicker();
BigDecimal amount = request.getAmount(); // Amount of shares to sell
// Step 1: Time of Check (ToC) - Reading the balance without locking the row.  
// In a race, the initial balance is read by multiple threads simultaneously.  
BigDecimal currentShares = db.query(  
    "SELECT shares\_owned FROM asset\_inventory WHERE account\_id = ? AND ticker = ?",  
    accountId, ticker  
).getResultList().get(0);  

if (currentShares.compareTo(amount) < 0) {  
    return Response.status(Response.Status.BAD\_REQUEST).entity("Insufficient shares for sale.").build();  
}  

// Step 2: Handoff to Matching Engine (The Race Window - \~50-100ms delay)  
// The thread yields during this network call, allowing other threads to perform Step 1.  
ExecutionResult result = executionEngine.submitOrder(accountId, request);  

// Step 3: Time of Use (ToU) - Updating the balance after the sale is confirmed.  
// Only the last thread to update the DB will reflect the true negative state.  
db.exec(  
    "UPDATE asset\_inventory SET shares\_owned = shares\_owned - ? WHERE account\_id = ? AND ticker = ?",  
    amount, accountId, ticker  
);  

// Log the transaction audit.  
auditLog.recordTransaction(accountId, ticker, amount, result.executionPrice());  

return Response.ok(result).build(); 
}
```
