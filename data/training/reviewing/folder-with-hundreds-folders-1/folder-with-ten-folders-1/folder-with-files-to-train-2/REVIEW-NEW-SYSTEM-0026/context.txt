## 1.0 Executive Summary and Compliance Mandate
AML Sentinel is the mandatory internal platform used by a major digital bank to monitor, investigate, and adjudicate high-value and potentially fraudulent transactions. The platform is regulated by the Bank Secrecy Act (BSA) and must adhere to strict Know Your Customer (KYC) and transaction monitoring policies. Any transaction over $$ 10,000$ or flagged by the automated risk engine must immediately enter a review workflow.

The core requirement is that once a transaction is flagged (`STATUS: FLAGGED`), it must be instantly frozen (`IS_FROZEN: TRUE`) to prevent settlement. Only a Level 3 AML Administrator, following a mandatory three-step review process and physical sign-off, is allowed to unfreeze and approve the transaction. A systemic architectural flaw (a concurrency gap) allows a Level 1 Compliance Officer to shortcut this entire workflow.

## 2.0 Comprehensive Network Topology & Workflow Engine
The architecture is partitioned into high-throughput transaction processing and low-latency compliance review.

### 2.1 The Transaction Core (High Velocity)
* **Payment Processor API:** Handles the initial request (e.g., ACH, Wire Transfer). All new transactions are immediately created in the ledger with `STATUS: PENDING`.
* **AML Risk Engine (Fuzzy Logic):** A Python service that scores every transaction. If the score exceeds a threshold (e.g., $9.0$ on a $10.0$ scale), it initiates the freezing process by calling the Gateway.

* **AML Sentinel Gateway (Java/Spring Boot):** The central microservice for human compliance review. It exposes endpoints to modify the transaction status (`FLAG`, `FREEZE`, `APPROVE`) and enforces RBAC based on the user's role.
* **PostgreSQL Ledger:** The source of truth for all transactions. The primary table includes columns for the transaction state, the freeze flag, and the review metadata.

## 3.0 Identity, Role-Based Access Control (RBAC), and Critical State Management
Authorization is strictly governed by the hierarchy of roles, and integrity relies on the proper transition of the transaction state machine.

### 3.1 Role Definitions (The Functional Pivot Target)
| Role | Access Scope | Critical Transaction Operations |
| :--- | :--- | :--- |
| TIER_1_SUPPORT | Read-only access to customer data. | None |
| COMPLIANCE_OFFICER (Low Privilege) | Read/Write status (FLAG/REJECT) and add notes. | `POST /transactions/{id}/flag` |
| AML_ADMIN (High Privilege) | Unfreeze, Approve, and execute settlement. | `POST /transactions/{id}/approve` |

### 3.2 The Critical State Transition (The Race Condition Window)
The system mandates the following security-critical sequence for high-risk transactions:
RISK DETECTED: AML Risk Engine sets `STATUS: FLAGGED` and `IS_FROZEN: FALSE`.
FREEZE COMMAND (ToC): AML Sentinel Gateway receives the freezing request. It reads the current status.
FREEZE COMMAND (ToU): The transaction record is updated to `IS_FROZEN: TRUE`.

## 4.0 Known System Debt & Theoretical Attack Surfaces
Internal Security Engineering Note: The performance team implemented asynchronous messaging for transaction freezing (using Kafka) to prevent the web service from blocking during high-volume periods. This refactoring was done without implementing a row-level database lock, creating the TOCTOU window. Tracked as RISK-AML-019.

**Taxonomy Pattern:** 8.1 (Race Condition / TOCTOU), 2.1 (Functional Pivot), & 8.5 (State Corruption)
**Sub-system:** AML Sentinel Gateway (`POST /api/v3/transactions/{id}/approve`)

**The Deep Architectural Flaw:**
This is a three-part critical failure involving concurrency, RBAC, and business logic trust.

1. **Functional Pivot (Pattern 2.1):** The RBAC logic on the `APPROVE` endpoint is incorrectly implemented. Instead of checking `IF user.role == AML_ADMIN`, it checks `IF user.role != TIER_1_SUPPORT AND IS_FROZEN == FALSE`. This faulty logic allows the low-privileged `COMPLIANCE_OFFICER` to attempt the high-privilege `APPROVE` operation, provided the transaction is not frozen.

2. **Race Condition (Pattern 8.1):** When a transaction is automatically flagged, the AML Sentinel Gateway spawns two threads: Thread A (Freezing Logic) and Thread B (Approval Check). The attacker (a Compliance Officer who is monitoring the flow) uses a concurrent request immediately upon seeing the transaction is $F L A G G E D$. The attacker's request (Thread B - Approval) hits the system just before the automated freezing request (Thread A) commits its database change.

3. **TOCTOU Gap:**
*   Time-of-Check (ToC) by Attacker: Attacker (Thread B) queries DB. Reads `IS_FROZEN: FALSE`. Proceeds to Approval.
*   Time-of-Use (ToU) by Attacker: Attacker's approval logic runs and commits `STATUS: APPROVED`.
*   The later-arriving AML Freeze (Thread A) then runs and attempts to set `IS_FROZEN: TRUE`, but the transaction status is now already `APPROVED`, which invalidates the freeze command, locking the transaction in an approved state.

1. **The Setup:** A $$ 500,000$ wire transfer is submitted and is instantly flagged by the AML Risk Engine. It is now `STATUS: FLAGGED`, `IS_FROZEN: FALSE`.
2. **The Concurrency Strike:** The Compliance Officer (`user_comp_991X`) immediately submits a synchronous, high-priority `POST /transactions/TX-991A/approve` request, exploiting the functional pivot flaw.
3. **The Collision:** The approval request hits the database and checks `IS_FROZEN`. Since the asynchronous freeze command hasn't executed the database write yet, the approval passes the check.
4. **The Result:** The attacker's thread commits `STATUS: APPROVED`. The asynchronous AML freeze command arrives microseconds later, sees the transaction is no longer `PENDING` or `FLAGGED` but `APPROVED`, and silently fails its update, or updates the obsolete state. The malicious transaction is permanently settled, bypassing the entire regulatory review workflow.

## 6.0 The Flawed Implementation (Java / Spring Boot)

```java
package com.amlsentinel.gateway.controllers;

import org.springframework.web.bind.annotation.*;
import org.springframework.transaction.annotation.Transactional;
import javax.servlet.http.HttpServletRequest;

@RestController
@RequestMapping("/api/v3/transactions")
public class TransactionController {
// POST /api/v3/transactions/{id}/approve
@PostMapping(value = "/{id}/approve")
@Transactional // Standard transaction isolation (NOT serializable, NO row lock)
public ResponseEntity<String> approveTransaction(@PathVariable("id") String txId, HttpServletRequest request) {
    
    String userId = request.user.getUserId();
    String userRole = request.user.getRole(); // e.g., 'COMPLIANCE\_OFFICER'
    
    // The role check is weak, allowing COMPLIANCE\_OFFICER access to this high-privilege function.
    if ("TIER\_1\_SUPPORT".equals(userRole)) {
        return ResponseEntity.status(403).body("{\"error\": \"Role is read-only.\"}");
    }
    
    TransactionRecord record = transactionRepo.findById(txId);
    
    if (record == null || "APPROVED".equals(record.getStatus()) || "REJECTED".equals(record.getStatus())) {
        return ResponseEntity.status(409).body("{\"error\": \"Transaction already finalized.\"}");
    }
    
    // Reads the state WITHOUT 'SELECT FOR UPDATE' database lock. 
    // In a race, the concurrent AML freeze thread has not yet updated IS\_FROZEN to TRUE.
    if (record.isFrozen()) {
        // This check is the primary defense, but it fails in the race window.
        return ResponseEntity.status(403).body("{\"error\": \"Transaction is currently frozen and requires AML Admin override.\"}");
    }
    
    // Check passes because IS\_FROZEN is still FALSE in the concurrent read.
    
    // --- Step 3: Time of Use (ToU) ---
    // The irreversible state change is committed.
    record.setStatus("APPROVED"); 
    record.setApprovedBy(userId);
    transactionRepo.save(record);
    
    // Asynchronous settlement is triggered by the status change event.
    eventBus.publish(new TransactionApprovedEvent(txId));

    
    return ResponseEntity.ok("{\"status\": \"APPROVED\", \"txId\": \"" + txId + "\"}");
}
}
```
