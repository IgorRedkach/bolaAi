## 1.0 Executive Summary
Project Sentinel is a critical, multi-tenant platform utilized by various US government agencies and authorized DIB contractors (referred to as "Tenants") to manage and audit their secure cloud deployments (AWS GovCloud, Azure Government). Every deployment requires a secure artifact registry to store versioned immutable deployment assets, including Docker images, compiled binaries, and, critically, the sensitive operational configuration files (e.g., IaC state files, environment variable configuration files).

The platform's security relies on absolute logical segregation between these tenants. A flaw in the artifact retrieval API, coupled with a verbose error handling mechanism, allows a low-clearance contractor from one tenant to exfiltrate the raw environment variables of a high-clearance tenant, compromising critical operational security controls.

## 2.0 Comprehensive Network Topology & Automation Core
The architecture is strictly segregated by logical tenant context, with a central API managing access to distributed file storage.

### 2.1 The Edge & Ingress Routing
* **Edge Proxy (Envoy):** Handles TLS termination and basic rate limiting.
* **API Gateway (Go-lang):** The central router that enforces tenant-level access control on the `project_id` provided in the URI.

### 2.2 The Backend Artifact Registry Service
* **Artifact Retrieval Service (Python/Flask):** A Python microservice that receives requests for project files, constructs the logical file path on the internal Volume, and streams the content back. This service runs deep inside the VPC.
* **Network-Attached Storage (NAS):** The physical storage layer (e.g., AWS EFS or an NFS mount) is logically partitioned. All tenant files are stored in a common directory structure but separated by their unique `tenant_id` and `project_id` on disk, in a highly predictable path (e.g., `/mnt/artifacts/tenant-A/proj-X/prod.tfstate`).

## 3.0 Identity, Tenant Isolation, and Secret Management
Tenant isolation is implemented primarily through mandatory JWT claims and database lookups.

### 3.1 Contractor Identity (OAuth 2.0 & Claims)
Contractors authenticate via their agency SSO. Their JWT contains two critical claims enforced by the API Gateway: `tenant_id` (the contractor's agency) and `clearance_level` (the maximum sensitivity of projects they can access).

### 3.2 Artifact Ownership & Path Construction (The Flaw)
When an authenticated user requests a file, the API Gateway performs an initial check: "Does this user's `tenant_id` match the owner of this `project_id`?" This initial check passes. However, the subsequent Flask Artifact Retrieval Service constructs the file path using the `project_id` from the URI and the `filename` from the request body, but **it completely ignores the authenticated user's `tenant_id` when generating the full file system path**. Instead, it relies on a cached local lookup of the project's owner, which is not verified against the current user's session.

## 5.0 Project Registry Schema (PostgreSQL)
The database tracks all projects. The critical flaw is that the Artifact Retrieval Service queries this table based on `project_id` alone, retrieving the sensitive `tenant_id` of the owner without checking the calling user's permissions.

```sql
-- Core Project Registry (The Metadata Lookup)
CREATE TABLE ia c_projects (
project_id VARCHAR(50) PRIMARY KEY, -- The URI Path variable
project_name VARCHAR(100) NOT NULL,
tenant_id VARCHAR(50) NOT NULL,    -- THE CRITICAL AUTHORIZATION FIELD (Retrieved in lookup)
clearance_level VARCHAR(10) CHECK (clearance_level IN ('LOW', 'HIGH', 'CRITICAL')),
is_active BOOLEAN DEFAULT TRUE
);

-- Core Artifact Storage Metadata
CREATE TABLE project_artifacts (
artifact_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
project_id VARCHAR(50) REFERENCES ia c_projects(project_id),
filename VARCHAR(150) NOT NULL, -- e.g., 'prod.env', 'main.tfstate'
s3_key VARCHAR(255) UNIQUE NOT NULL,
created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_project_tenant ON ia c_projects(tenant_id, project_id);
```

## 7.0 REST API Contracts (The Credential Exfiltration)
The attack uses a seemingly innocuous POST request (as file download APIs often require) to trick the application into reading a sensitive environment file belonging to a different, high-clearance tenant.

### 7.1 Intended Safe Payload (Legitimate Download)
A low-clearance contractor downloads a Dockerfile from their own low-tier project.

**Target URI:** `POST /api/v1/artifacts/proj-Y/download`
**Expected Request Payload:**
```json
{
"filename": "Dockerfile"
}
```

The attacker targets a critical project ID (`proj-X`) and requests the highly sensitive `prod.env` file. The Flask service finds the file on the NAS but fails on the stream due to a simulated error condition (e.g., a parsing issue), forcing the error handler to dump the file's content.

**Target URI:** `POST /api/v1/artifacts/proj-X/download`
*Note: `proj-X` belongs to `tenant-critical-A`.*
**Malicious Request Payload:**
```json
{
"filename": "prod.env",
"format": "BINARY" # Attacker adds a param to trigger the expected stream error
}
```

The attacker receives a non-200 status, but the error message contains the core secrets from the target tenant's environment file.
