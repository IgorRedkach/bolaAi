## 1.0 Executive Summary
CareSphere is a national health information exchange (HIE) platform. It acts as a translation and interoperability layer between modern consumer telehealth applications (e.g., mobile symptom checkers, remote patient monitoring apps) and legacy, on-premise hospital EMR systems (like Epic or Cerner).

To comply with the 21st Century Cures Act, the platform exposes a standardized FHIR R4 (Fast Healthcare Interoperability Resources) API to third-party developers. Behind the scenes, the gateway must translate these modern RESTful JSON queries into legacy HL7v2 pipe-delimited messages or proprietary SOAP XML payloads to communicate with older hospital mainframes over dedicated IPSec VPNs.

## 2.0 Comprehensive Network Topology & Integration Mesh
Handling electronic Protected Health Information (ePHI) requires defense-in-depth, zero-trust network boundaries, and rigorous audit logging.

### 2.1 The Ingress Layer & FHIR Facade
* **Google Cloud Apigee Edge:** Serves as the primary API Gateway. It enforces rate limiting, TLS 1.3 termination, and OAuth 2.0 token introspection. It provides the official `https://api.caresphere.health/fhir/v4/` base URL.
* **Istio Service Mesh:** Once traffic passes Apigee, it enters an Amazon EKS (Elastic Kubernetes Service) cluster managed by Istio. Every microservice communication is encrypted via mTLS.

### 2.2 The Core Microservices (Translation & Routing)
* **FHIR-to-HL7 Translator Service:** A Java Spring Boot application that takes a FHIR `Observation` or `DocumentReference` request and maps it to an HL7v2 `MDM^T02` (Medical Document Management) query.
* **On-Premise Connector Fleet:** Ephemeral Go-lang pods that maintain persistent, IP-whitelisted VPN tunnels directly into the private data centers of partner hospitals.

### 2.3 Legacy Infrastructure (The "Shadow" Debt)
* **Node.js Legacy Gateway (v1):** Before adopting the strict FHIR standard, CareSphere utilized a proprietary REST API (`/api/v1/`). While official documentation states this API was sunset in 2024, the underlying Node.js deployment was never physically torn down because two major legacy hospital networks refused to update their integration code. It remains accessible if a user knows the specific URI paths.

## 3.0 Identity, SMART on FHIR, and Authorization
Healthcare APIs require highly granular authorization. A podiatrist app should not have access to a patient's psychiatric records. CareSphere implements the SMART on FHIR authorization framework.

### 3.1 Delegated Authorization (OAuth 2.0)
* Patients log into their hospital portal and authorize a third-party telehealth app.
* The app receives a JWT scoped explicitly to the patient's ID and the required data type.
* **Example Scopes:** `patient/Observation.read` (allows reading lab results), `patient/Patient.read` (allows reading demographics).

### 3.2 The Policy Enforcement Point (PEP)
The Apigee API Gateway acts as the PEP. It inspects the JWT, parses the scopes, and ensures the requested FHIR resource matches both the scope and the `patient_id` bound to the token before routing the request to the EKS cluster.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The decommissioning of the legacy v1 Node.js gateway (Epic: HLTH-404) has been blocked by executive exception for 18 months. The gateway sits behind the primary WAF but bypasses the new SMART on FHIR policy enforcement logic. Tracked as RISK-EPHI-099.*

**Sub-system:** Legacy Node.js Gateway (`/api/v1/export/patients/{id}/clinical-notes`)

**The Deep Architectural Flaw:**
1.  **Improper Asset Management / Shadow API (Pattern 4.1):** The Apigee WAF rules were updated to protect `/fhir/v4/*`, but the routing rules still passively forward `/api/v1/*` requests to the legacy Node.js cluster. Because the v1 API is unmonitored and excluded from modern OpenAPI swagger definitions, security teams forgot it existed.
2.  **Broken Object Level Authorization (Pattern 1.1):** The legacy Node.js endpoint requires a valid JWT. However, unlike the modern FHIR gateway, it **completely fails to verify if the `patient_id` in the URL matches the patient bound to the JWT**. It only checks if the token signature is valid.
3.  **Improper Data Filtering (Pattern 2.1):** The modern FHIR `/DocumentReference` endpoint strictly filters out clinical notes tagged with the `PSYCH` (Psychiatric) sensitivity label unless a specialized break-glass scope is present. The legacy `/clinical-notes` endpoint has no such filtering; it blindly executes a `SELECT *` equivalent on the hospital's database and returns every physician note, including highly sensitive mental health records.

1.  **The Foothold:** An attacker registers for a legitimate telehealth app connected to CareSphere (e.g., a simple step-tracking app) and authenticates as Patient A (`pt_88192`). They receive a highly restricted JWT with the scope `patient/Observation.read`.
2.  **Discovery:** The attacker uses directory fuzzing tools (like FFuF or Burp Suite) and discovers the undocumented legacy path: `/api/v1/export/patients/pt_88192/clinical-notes`. They test it and realize the endpoint accepts their restricted JWT.

## 5.0 Data Representation: Modern FHIR vs Legacy Mainframe
The architectural flaw is exacerbated by how the two different gateway versions interact with the underlying hospital Electronic Medical Record (EMR) databases.

### 5.1 The Modern FHIR R4 Schema (DocumentReference)
In the modern implementation, a physician's note is mapped to the FHIR `DocumentReference` resource. The FHIR specification includes a robust `meta.security` array. The modern Java Spring Boot translator explicitly checks these tags and strips out resources tagged with `PSY` (Psychiatry) unless the querying application has a specialized, audited `break-glass` OAuth scope.

```json
// Secure FHIR Representation (Filtered by Modern Gateway)
{
  "resourceType": "DocumentReference",
  "id": "doc-99182",
  "status": "current",
  "type": {
    "coding": [{ "system": "http://loinc.org", "code": "11488-4", "display": "Consultation note" }]
  },
  "subject": { "reference": "Patient/pt_10001" },
  "meta": {
    "security": [
      { "system": "http://terminology.hl7.org/CodeSystem/v3-Confidentiality", "code": "R", "display": "Restricted" },
      { "system": "http://terminology.hl7.org/CodeSystem/v3-ActCode", "code": "PSY", "display": "Psychiatry discipline" }
    ]
  },
  "content": [ { "attachment": { "contentType": "text/plain", "data": "SGF0aWVudCBwcmVzZW50cyB3aXRoLi4u" } } ]
}
```

### 5.2 The Underlying Legacy Database Schema (SQL Equivalent)
The legacy hospital mainframes store these notes in flat, relational tables without native FHIR security tagging. The legacy Node.js gateway queries these tables directly.

```sql
-- Legacy Hospital Notes Table (Directly accessed by the v1 Shadow API)
CREATE TABLE clinical_notes_archive (
    note_id VARCHAR(50) PRIMARY KEY,
    author_provider_id VARCHAR(50),
    encounter_date DATE,
    department VARCHAR(50), -- e.g., 'ONCOLOGY', 'PSYCHIATRY'
    is_restricted BOOLEAN DEFAULT FALSE, -- Ignored by the v1 API
    raw_clinical_text TEXT NOT NULL
);
CREATE INDEX idx_patient_notes ON clinical_notes_archive(patient_id);
```

### Why this payload is critical for training a 3B model (Expanded Analysis):

1. **Shadow API / Deprecated Asset Detection (Pattern 4.1):**
    * **URI vs Standard Contract:** The model must be trained to flag requests where the URI path deviates from the officially declared specification (e.g., recognizing that `/api/v1/export` does not match the modern `/fhir/v4/` RESTful standard). 
    * **Header Fingerprinting:** The `x-legacy-router: v1-node-cluster-deprecated` header in the response is a massive contextual clue. The AI learns that organizations frequently leave internal debug or routing headers intact on forgotten infrastructure, acting as breadcrumbs for attackers.

    * **Scope vs Action Mismatch:** The model must decode the JWT to extract `{"sub":"pt_88192", "scopes":["patient/Observation.read"]}`. It must then compare this against the URI: `/patients/pt_10001/`. The discrepancy between the token's subject (`pt_88192`) and the requested resource (`pt_10001`), combined with a `200 OK` response, definitively proves the endpoint lacks object-level authorization.
    * Furthermore, the attacker requested `clinical-notes`, but their token was only scoped for `Observation.read` (e.g., step counts, heart rate). The API completely ignored the OAuth scope enforcement.

3. **Improper Data Filtering & ePHI Exposure (Pattern 2.1):**
    * **Semantic Payload Analysis:** The AI must inspect the response body and recognize the catastrophic failure of data masking. The presence of `"department": "PSYCHIATRY"` and `"is_restricted": true` alongside raw, plaintext clinical narratives indicates that the backend data layer is blindly dumping rows to the client.
    * **Size Anomalies:** The `content.size` of `5120480` bytes (~5.1 MB) for a single GET request is a classic indicator of a bulk data export. The AI learns that an endpoint designed for mobile apps (like `PedometerPlus`) returning 5MB of raw medical text is highly anomalous and signifies an architectural filtering breakdown.
