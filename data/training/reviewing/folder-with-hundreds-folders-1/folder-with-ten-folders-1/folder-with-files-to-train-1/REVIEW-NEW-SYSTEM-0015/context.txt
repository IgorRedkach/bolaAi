## 1.0 Executive Summary
NovaChain is a custodial Web2-to-Web3 bridge. It allows traditional retail investors to earn high-yield interest on stablecoins (like USDC) without needing to manage their own private keys or pay complex Ethereum gas fees. 

Users deposit USDC into their NovaChain account via a standard REST API. The NovaChain backend aggregates these deposits and pools them into audited Ethereum smart contracts to generate yield. When a user requests a withdrawal, the REST API validates their internal balance, signs a blockchain transaction from the platform's "Hot Wallet," and sends the USDC back to the user's external crypto address.

## 2.0 Comprehensive Network Topology & Web3 Integration
The architecture must seamlessly link highly scalable cloud microservices with the decentralized, asynchronous nature of the Ethereum blockchain.

### 2.1 The Web2 Cloud Plane (Ingress & State)
* **Cloudflare Bot Management:** Fronts the API to prevent basic volumetric DDoS attacks.
* **Node.js API Gateway (Express):** Handles user sessions, internal balance queries, and withdrawal requests.
* **PostgreSQL (The Ledger):** Acts as the internal Web2 source of truth for how much USDC each user technically "owns" within the aggregated pool.

### 2.2 The Web3 Transaction Plane (Execution)
* **Rust Transaction Signer:** A highly secure, isolated microservice. It receives approved withdrawal payloads from the Node.js API, signs the transaction using the Hot Wallet's private key (stored in AWS KMS), and broadcasts it to the blockchain.
* **RPC Provider (Alchemy/Infura):** The node infrastructure that transmits the signed transaction directly into the Ethereum mempool for miner/validator inclusion.

## 3.0 Identity, SIWE, and Authorization
Because this bridges Web2 and Web3, identity relies on cryptographic signatures rather than traditional passwords.

### 3.1 Sign-In with Ethereum (EIP-4361)
Users authenticate by signing a cryptographic nonce with their external Ethereum wallet (e.g., MetaMask). The API verifies this signature and issues a standard OAuth 2.0 JWT.
* The JWT contains the user's `account_id` and their verified external `wallet_address`.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: To improve user experience and reduce "Withdrawal Pending" complaints, the withdrawal state machine was refactored in Sprint 82 to broadcast to the blockchain synchronously before updating the database. Tracked as RISK-DEFI-007.*

**Sub-system:** Node.js API Gateway (`/api/v2/withdrawals/execute`)

**The Deep Architectural Flaw:**
    * *Step 1 (Check):* Query PostgreSQL. Does the user have >= 5,000 USDC? (Yes).
    * *Step 2 (Execute):* Call the Rust Signer to broadcast the 5,000 USDC transfer to the blockchain.
    * *Step 3 (Update):* Deduct 5,000 USDC from the user's PostgreSQL balance.
2.  **The Race Condition (Pattern 5.2):** Step 2 involves a network call to the Rust service and the Alchemy RPC node, which takes approximately 150-300 milliseconds. During this window, the user's PostgreSQL balance *has not yet been deducted*. The database lacks transactional row-locking (e.g., `SELECT ... FOR UPDATE`).

1.  **The Setup:** An attacker deposits exactly 5,000 USDC into their NovaChain account.
2.  **The Concurrency Strike:** The attacker writes a Python script using the `asyncio` library to send **50 identical withdrawal requests** to the `/api/v2/withdrawals/execute` endpoint at the exact same millisecond.
3.  **The Collision:** Because Node.js is asynchronous and handles requests concurrently without database-level mutex locks:
    * Thread 1 hits Step 1: Balance is 5,000. (Passes)
    * Thread 2 hits Step 1 (10ms later): Balance is *still* 5,000 because Thread 1 is currently waiting on the RPC network call in Step 2. (Passes)
    * Threads 3 through 50 also hit Step 1 and pass the balance check.
4.  **The Drain:** All 50 threads proceed to Step 2, instructing the Rust Signer to broadcast fifty separate 5,000 USDC transfers from the platform's Hot Wallet to the attacker's external address. 
5.  **The Result:** The attacker deposited 5,000 USDC but successfully withdrew 250,000 USDC, completely draining the platform's liquidity due to an API concurrency failure.

## 6.0 The Flawed Implementation (Node.js / Express)

```javascript
// File: controllers/withdrawalController.js
const db = require('../lib/postgres');
const rustSigner = require('../lib/rust_rpc_client');

// POST /api/v2/withdrawals/execute
exports.executeWithdrawal = async (req, res) => {
    const { amount_usdc } = req.body;
    const accountId = req.user.account_id; // Extracted securely from SIWE JWT
    const destAddress = req.user.eth_wallet_address;

    try {
        // The query reads the current balance but does NOT lock the row.
        // In a concurrent attack, 50 requests will all read "5000" simultaneously.
        const userRecord = await db.query(
            `SELECT usdc_balance FROM users WHERE account_id = $1`, 
            [accountId]
        );
        
        const currentBalance = parseFloat(userRecord.rows[0].usdc_balance);

        // STEP 1: The "Check" (Time of Check)
        if (currentBalance < amount_usdc) {
            return res.status(400).json({ error: "Insufficient USDC balance." });
        }

        // STEP 2: The Network Yield (The Race Window)
        // Calling the Rust microservice takes ~200ms. 
        // Node.js suspends this function and processes other incoming requests.
        // Concurrent requests for this user will easily pass the balance check above.
        const broadcastResult = await rustSigner.broadcastTransaction({
            asset: 'USDC',
            to: destAddress,
            amount: amount_usdc
        });

        // STEP 3: The "Use" (Time of Use / Update)
        // By the time this executes, the hot wallet has already sent the funds.
        // If 50 requests raced, the balance will be driven massively negative.
        await db.query(
            `UPDATE users SET usdc_balance = usdc_balance - $1 WHERE account_id = $2`,
            [amount_usdc, accountId]
        );

        // Log the successful broadcast
        await db.query(
            `INSERT INTO withdrawal_history (account_id, amount_usdc, destination_address, blockchain_tx_hash, status) 
             VALUES ($1, $2, $3, $4, 'BROADCAST')`,
            [accountId, amount_usdc, destAddress, broadcastResult.tx_hash]
        );

        res.status(200).json({ 
            status: "BROADCAST_SUCCESS", 
            tx_hash: broadcastResult.tx_hash 
        });

    } catch (error) {
        res.status(500).json({ error: "Internal transaction failure." });
    }
};
```
