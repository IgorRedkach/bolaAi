# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** GridCore Demand Response & SCADA Bridge
**Document Version:** 6.1.0 (FINAL)
**Classification:** CRITICAL INFRASTRUCTURE / NERC CIP COMPLIANCE SCOPE
**Domain:** Energy / Smart Grid / Industrial Control Systems (ICS)

## 1.0 Executive Summary
The GridCore platform manages Demand Response (DR) events for a regional electrical grid. During peak load events (e.g., extreme summer heat waves), the system automatically communicates with megawatt-scale commercial battery storage systems, smart factory controllers, and EV charging networks to strategically shed load and prevent localized blackouts.

Because this system bridges the public internet (where commercial assets reside) with the highly restricted Operational Technology (OT) network (where the SCADA systems control the actual grid), security is paramount. The platform relies on an API Gateway to sanitize inbound telemetry before it reaches the internal Java-based SCADA integration layer.

## 2.0 Comprehensive Network Topology & Ingress Routing
The architecture is designed to create a "demilitarized zone" (DMZ) between the cloud and the physical power grid.

### 2.1 The Cloud Ingress Layer
* **Cloudflare Enterprise WAF:** Acts as the first line of defense, enforcing strict geolocation blocking and volumetric rate limiting.
* **Kong API Gateway (DMZ):** Deployed in an AWS VPC. It handles mutual TLS (mTLS) termination, validates API keys for the commercial grid assets, and performs basic HTTP method filtering.

### 2.2 The IT/OT Bridge (Internal Kubernetes Cluster)
* **Grid Telemetry Service:** A Node.js microservice that processes simple JSON metrics (e.g., current kilowatt usage) from smart meters.
* **SCADA Command Bridge:** A legacy Java (Spring Boot) microservice. This is the most critical node. It receives complex "Grid State Reports" from massive industrial assets and translates them into DNP3 or Modbus TCP protocols used by the internal SCADA network. Because it must interface with legacy 1990s grid hardware, it utilizes Java Object Serialization for certain high-density state payloads.

## 3.0 Identity, Access, and NERC CIP Compliance
The North American Electric Reliability Corporation (NERC) mandates strict access controls for any system touching the Bulk Electric System (BES).

### 3.1 Asset Authentication (mTLS + Token)
Commercial assets (like a Tesla Megapack installation at a factory) must connect using an X.509 certificate signed by the GridCore private CA. They must also pass an `X-Grid-Auth` token in the HTTP header.

### 3.2 The WAF Authorization Policy (The Flaw)
To reduce the load on the internal SCADA bridge, the Kong API Gateway was configured with a custom Lua plugin to enforce authorization strictly at the edge. The plugin is configured to inspect the `X-Grid-Auth` token and validate it against a Redis cache *before* forwarding the request.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The SCADA Command Bridge relies on Java serialization for the legacy `GridStateReport` object. Epic: ENRG-311 was created to migrate this to Protocol Buffers (gRPC), but was deferred to Q3 due to budget constraints. Tracked as RISK-ICS-004.*

**Taxonomy Pattern:** 1.6 (HTTP Method Tampering) & 10.3 (Insecure Deserialization)
**Sub-system:** SCADA Command Bridge (`/api/v1/grid/assets/state-report`)

**The Deep Architectural Flaw:**
This attack relies on a discrepancy between how the API Gateway enforces security and how the backend Java application routes traffic.
1.  **HTTP Verb Tampering (Pattern 1.6):** The Kong Gateway's custom Lua authorization plugin was written with a fatal regex flaw. It explicitly applies the token validation logic only to `POST` and `GET` requests (e.g., `if request.method == "POST" then validate()`). If an attacker sends a `PATCH` request, the Lua script silently ignores it and allows the request to pass through the WAF directly to the internal network without verifying the `X-Grid-Auth` token.

1.  **Reconnaissance:** An attacker discovers the endpoint URL: `https://api.gridcore.energy/api/v1/grid/assets/state-report`. They send a standard `POST` request with an invalid token and are correctly blocked by the Kong Gateway with a `401 Unauthorized`.
3.  **The Deserialization Payload:** Using a tool like `ysoserial`, the attacker generates a malicious serialized Java object containing an Apache Commons Collections gadget chain designed to execute a bash command (e.g., opening a reverse shell). They base64-encode this payload.
4.  **The Execution:** The attacker sends the `PATCH` request with the base64-encoded payload in the body.

The first layer of the attack exploits a logic flaw in the Kong API Gateway's custom authentication plugin (written in Lua). The developer attempted to optimize performance by skipping authentication for CORS preflight (`OPTIONS`) requests, but mistakenly used an explicit "allow-list" of methods for authentication rather than enforcing it globally.

```lua
-- File: plugins/grid-auth/handler.lua
local GridAuthHandler = {
    VERSION  = "1.0.3",
    PRIORITY = 1000,
}

function GridAuthHandler:access(conf)
    local method = kong.request.get_method()
    
    -- The plugin ONLY enforces authentication on explicitly defined HTTP verbs.
    -- If an attacker sends a PATCH, PUT, or DELETE request, this block is entirely skipped,
    -- allowing the request to route directly to the backend IT/OT bridge unauthenticated.
    if method == "POST" or method == "GET" then
        local token = kong.request.get_header("X-Grid-Auth")
        
        if not token then
            return kong.response.exit(401, { error = "Missing Authentication Token" })
        end
        
        local is_valid = validate_token_against_redis(token)
        if not is_valid then
            return kong.response.exit(403, { error = "Invalid Asset Token" })
        end
    end
    
    -- Request passes to the upstream SCADA Bridge
end

return GridAuthHandler
```

### Why this payload is critical for training a 3B model (Expanded Analysis):

1. **HTTP Verb/Method Tampering Anomaly (Pattern 1.6):**
    * **Contract Deviation:** The AI model must learn to compare the expected RESTful API contract against the observed telemetry. The endpoint `/state-report` implies the submission of telemetry data, universally handled via a `POST` or `PUT`. The presence of a `PATCH` request carrying a massive, opaque payload is a high-confidence indicator of an attacker probing edge-routing rules and WAF logic.
    * **Authorization Discrepancy:** The model must identify that an invalid token (`INVALID_TOKEN_BYPASS`) resulted in the request being forwarded to the upstream server (as evidenced by the 30-second wait time), proving the WAF failed to drop the unauthenticated request at the edge.

2. **Java Serialization Magic Bytes Identification (Pattern 10.3):**
    * **Base64 Magic Headers:** The AI must be trained to recognize specific encoded magic bytes. In Base64, a serialized Java object universally begins with `rO0AB` (which decodes to the hexadecimal `AC ED 00 05`, the Java serialization stream header). 
    * **Semantic Payload Analysis:** Even without decoding the full payload, spotting `rO0AB` in an API endpoint expecting standard JSON or plain text acts as a definitive signature for an insecure deserialization attempt. 

3. **Execution Artifacts & Thread Blocking (Timeout Indication):**
    * **Latency as an IoC (Indicator of Compromise):** The AI must learn that a `504 Gateway Timeout` coupled with a massive `time` value (`30015` milliseconds) is not always a generic networking error. In the context of a deserialization attack, it is the primary behavioral signature of a successful interactive reverse shell. The spawned OS-level process (like `netcat` or `/bin/bash`) inherits the input/output streams of the parent Java thread, causing the HTTP request to hang indefinitely until the gateway's hard timeout limit kills the connection.
