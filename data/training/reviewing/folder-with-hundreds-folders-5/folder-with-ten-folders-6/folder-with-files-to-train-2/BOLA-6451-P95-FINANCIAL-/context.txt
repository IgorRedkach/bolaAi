# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** NexaBank Open Finance API
**Document Version:** 3.1.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Financial Services / Retail Banking
**Architecture:** ISO 20022 + REST/GraphQL over account ledgers
**Training Example ID:** BOLA-6451

## 1.0 Executive Summary
NexaBank Open Finance API is a financial services / retail banking platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v3/items endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 9.5 — Smart Cities and IoT Networks

## 3.0 Database Schema
```sql

-- Item table
CREATE TABLE items (
    item_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_item_tenant ON items(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 9.5 — Smart Cities and IoT Networks (Platform)

The `GET/PATCH/DELETE /api/v3/items/:id` endpoint accepts a `item_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-B629` can access objects owned by `ORG-B3CF`.

_Specific exploitation for Pattern 9.5:_ The `/api/v3/items` handler does not enforce tenant/owner boundaries for Pattern 9.5.
