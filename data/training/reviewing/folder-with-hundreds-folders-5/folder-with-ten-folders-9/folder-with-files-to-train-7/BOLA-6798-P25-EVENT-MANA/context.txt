# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** VenueCore Ticketing API
**Document Version:** 3.0.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Event Management / Ticketing
**Architecture:** REST + GraphQL + payment
**Training Example ID:** BOLA-6798

## 1.0 Executive Summary
VenueCore Ticketing API is a event management / ticketing platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v1/objects endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 2.5 — Critical Infrastructure interface exposure

## 3.0 Database Schema
```sql

-- Object table
CREATE TABLE objects (
    object_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_object_tenant ON objects(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 2.5 — Critical Infrastructure interface exposure (BAC)

The `GET/PATCH/DELETE /api/v1/objects/:id` endpoint accepts a `object_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-7B7B` can access objects owned by `ORG-3A0D`.

_Specific exploitation for Pattern 2.5:_ The `/api/v1/objects` handler does not enforce tenant/owner boundaries for Pattern 2.5.
