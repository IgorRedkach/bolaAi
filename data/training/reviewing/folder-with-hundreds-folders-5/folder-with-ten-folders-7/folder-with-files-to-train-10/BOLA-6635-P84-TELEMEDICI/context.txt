# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** TeleCare Consultation API
**Document Version:** 5.8.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Telemedicine / Remote Care
**Architecture:** FHIR + WebRTC + GraphQL
**Training Example ID:** BOLA-6635

## 1.0 Executive Summary
TeleCare Consultation API is a telemedicine / remote care platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v2/documents endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 8.4 — Resource exhaustion (DoS)

## 3.0 Database Schema
```sql

-- Document table
CREATE TABLE documents (
    document_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_document_tenant ON documents(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 8.4 — Resource exhaustion (DoS) (Exceptional)

The `GET/PATCH/DELETE /api/v2/documents/:id` endpoint accepts a `document_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-3758` can access objects owned by `ORG-0E1E`.

_Specific exploitation for Pattern 8.4:_ The `/api/v2/documents` handler does not enforce tenant/owner boundaries for Pattern 8.4.
