# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** AetherDrive V2X Telematics Platform

## 1.0 Executive Summary
The AetherDrive platform is a global, hyperscale IoT and API ecosystem designed to support a fleet of over 4 million connected electric and semi-autonomous vehicles. The platform handles everything from real-time battery telemetry and remote climate control to critical Over-The-Air (OTA) firmware updates for the vehicle's electronic control units (ECUs), such as the braking module, advanced driver-assistance systems (ADAS), and the central infotainment console.

Because physical safety is paramount, the architecture must bridge highly volatile cellular networks (4G LTE/5G) with rigidly secured backend microservices. The core interface point in the vehicle is the Telematics Control Unit (TCU), an embedded Linux computer featuring a dedicated cellular modem and a Hardware Security Module (HSM) for cryptographic operations. This TCU acts as the gateway between the cloud and the vehicle's internal CAN bus (Controller Area Network).

## 2.0 Comprehensive Network Topology & Ingress Routing
The platform operates across three distinct network planes to segregate high-volume telemetry from critical command-and-control operations.

### 2.1 The IoT Telemetry Plane (Vehicle-to-Cloud)
* **Private Cellular APN:** Vehicles do not connect to the public internet directly. They route through a dedicated private Access Point Name (APN) provided by tier-1 telecom partners, entering the AWS cloud environment via an IPSec Transit Gateway.
* **AWS IoT Core (MQTT Broker):** High-frequency, low-latency telemetry (GPS coordinates, wheel speed, battery state of charge) is published over MQTT using TLS 1.2. The broker routes these messages into Amazon Kinesis data streams for real-time analytics and predictive maintenance algorithms.

### 2.2 The Command & Control API Plane (App-to-Cloud)
* **Edge Ingress:** The consumer mobile "Companion App" (iOS/Android) connects to an external-facing API Gateway fronted by a Web Application Firewall (WAF).
* **Service Mesh (gRPC):** Internal microservices are written in Rust and Go, communicating over a strictly authenticated gRPC service mesh (Linkerd). 
* **The Command Queue:** When a user clicks "Unlock Doors" on their app, the API Gateway translates the REST request into a gRPC call, which places a signed command onto an Apache Kafka topic. The "Device Shadow" service then pushes this command down the MQTT tunnel to the specific vehicle's TCU.

### 2.3 The OTA Update Pipeline (Cloud-to-Vehicle)
* **Campaign Manager Service:** Responsible for orchestrating massive firmware rollouts. It handles delta-compression of binary files, staggered regional deployments, and rollback logic if a vehicle reports a failed flash.
* **Signed Blob Storage:** Firmware binaries are heavily encrypted and digitally signed by the OEM's root offline CA. They are stored in an Amazon S3 bucket with strict Cross-Origin Resource Sharing (CORS) and signed-URL access policies.

## 3.0 Identity, Cryptography, and PKI Authorization
Security relies on a dual-authentication model: one for the human, one for the machine.

### 3.1 Vehicle Authentication (mTLS & Hardware Root of Trust)
Every vehicle is provisioned at the factory with a unique X.509 certificate permanently burned into its HSM. 
* When the TCU connects to the MQTT broker or requests a firmware download, it must use mutual TLS (mTLS). 
* The cloud verifies the certificate against the OEM Certificate Authority, ensuring that even if an attacker spoofs a VIN, they cannot establish a connection without the physical silicon chip.

### 3.2 Owner Authentication (OAuth2 & B2C Identity)
Vehicle owners authenticate to the mobile app via Okta Customer Identity Cloud (Auth0).
* They receive an OAuth 2.0 JWT.
* **The Binding Record:** A critical PostgreSQL database table (`vehicle_ownership`) maps a user's unique `account_id` to the physical `VIN` (Vehicle Identification Number) of the car they purchased.

## 4.0 Known System Debt & Theoretical Attack Surfaces

### 4.1 Vulnerability A: Physical Device BOLA & Firmware Validation Bypass
**Taxonomy Pattern:** 1.2 (BOLA on physical devices) & 3.4 (Unsecured firmware/OTA updates)
**Sub-system:** OTA Campaign Service (`/api/v3/vehicles/{vin}/ota/push`)

**The Deep Architectural Flaw:**
To support the new "Custom Tuning" feature, developers created a new REST endpoint allowing the mobile app to trigger a lightweight, on-demand OTA configuration update. 
1.  **The BOLA Flaw (Pattern 1.2):** The endpoint URL dictates the target vehicle (`/vehicles/WBA00000000123456/`). The Go-based microservice verifies that the user's JWT is valid and active. However, it completely fails to query the `vehicle_ownership` PostgreSQL table. It blindly assumes that if you are an authenticated user, you are allowed to push configurations to the VIN specified in the URL path.
2.  **The OTA Validation Flaw (Pattern 3.4):** Typically, firmware is pulled from the highly secure, OEM-signed S3 bucket. However, this specific "Custom Tuning" endpoint was designed to allow users to upload their own JSON configuration profiles. The API payload accepts an arbitrary `manifest_url` parameter. The cloud service takes this URL and forwards it directly to the vehicle's TCU. The TCU, assuming any command coming from the trusted cloud MQTT tunnel is legitimate, downloads the payload from the provided URL and executes the configuration change in memory *without verifying a cryptographic signature*.

**The Exploitation Path:**
1.  An attacker registers a legitimate account on the AetherDrive platform and buys the cheapest used vehicle available to gain a valid owner JWT.
2.  The attacker targets a victim's vehicle (e.g., a high-profile target or a fleet of delivery trucks). VINs are publicly visible through the windshield. Let's assume the victim's VIN is `1G1RC6E45FU111111`.
3.  The attacker hosts a malicious configuration payload on their own server (`https://attacker.com/malicious_tune.json`). This payload contains instructions that will cause the TCU to drop its firewall and open a reverse shell over the cellular network.
4.  The attacker intercepts their mobile app traffic and issues a `POST` request to the vulnerable API: `POST /api/v3/vehicles/1G1RC6E45FU111111/ota/push`, including the `manifest_url` pointing to their malicious server.
5.  **The Cascade:** The API fails the BOLA check, accepts the command, and pushes it down the MQTT tunnel to the victim's car. The car's TCU downloads the payload from `attacker.com`, bypasses signature checks (because the config pipeline wasn't designed for signed binaries), and executes it. The attacker now has remote code execution on a moving vehicle.

### 4.1 Vulnerability A: SSO Issuer Confusion & GraphQL Alias DoS
**Taxonomy Pattern:** 2.4 (Third-party token/SSO misconfiguration) & 5.3 (GraphQL alias batching/DoS)
**Sub-system:** GraphQL API Gateway & Auth Middleware (`/graphql`)

**The Deep Architectural Flaw:**
This attack relies on a catastrophic failure in the SSO validation logic, amplified by a GraphQL-specific attack vector.
1.  **The SSO Issuer Flaw (Pattern 2.4):** The API Gateway validates that the incoming JWT is cryptographically signed. However, it blindly trusts the `iss` (Issuer) URL provided *inside the token header* to fetch the public verification key (JWKS), rather than strictly checking the issuer against a hardcoded whitelist of approved municipal tenants. This allows an attacker to spin up their own free Auth0 account, generate a valid JWT, and trick the AquaGrid gateway into validating it.
2.  **The GraphQL Alias Flaw (Pattern 5.3):** The `ValveActuation` subgraph allows administrators to remotely shut off a water meter. While the WAF limits users to 10 HTTP requests per minute to prevent mass-shutoffs, it does not inspect the GraphQL payload. An attacker can use GraphQL "Aliases" to pack thousands of distinct `setValveState` mutations into a *single* HTTP POST request. 

**The Exploitation Path:**
1.  **Forging the Identity:** The attacker creates a free developer account on Okta. They mint a JWT claiming the role `city_admin` and inject the target municipality's ID (`tenant_id: "city_of_chicago_01"`). Because of the Issuer Confusion flaw, the AquaGrid gateway downloads the attacker's public key, verifies the forged token, and grants the attacker full administrative rights over Chicago's water grid.
2.  **Bypassing Rate Limits via Batching:** The attacker wants to shut off water to an entire ZIP code. They know the WAF will block them if they send 5,000 separate HTTP requests. 
3.  **The Strike:** The attacker crafts a single GraphQL HTTP POST payload containing 5,000 aliased mutations (e.g., `cmd1: setValveState(meterId: "MTR-1", state: CLOSED)`, `cmd2: setValveState(meterId: "MTR-2", state: CLOSED)`, etc.).
4.  **The Cascade:** The gateway parses the single HTTP request (bypassing the WAF), accepts the forged token, and the GraphQL engine resolves all 5,000 mutations asynchronously. Within seconds, the command queue floods the LPWAN network, and 5,000 residential water valves physically rotate shut.

## 6.0 The Flawed Implementation (Node.js SSO Middleware)
The vulnerability lies in the API Gateway's authentication middleware. To support "Bring Your Own Identity" (BYOI) for 150 different cities dynamically, the developer configured the JWT library to fetch the verification keys (JWKS) based on the `iss` (Issuer) claim provided *inside* the incoming token, prior to verifying its signature.

### 6.1 Vulnerable JWT Verification (Express.js / Node)
```javascript

const jwksClient = require('jwks-rsa');

    const token = req.headers.authorization?.split(' ')[1];
    if (!token) return res.status(401).send("No token provided");

    try {

        // The attacker completely controls this value.

        const dynamicIssuerUrl = decodedUnverified.payload.iss;

        // `tenants.sso_issuer_url` database column BEFORE fetching the keys.

        // to download the public key used to verify the token.
        const client = jwksClient({
            jwksUri: `${dynamicIssuerUrl}/.well-known/jwks.json` // Points to attacker's Auth0
        });

        const key = await client.getSigningKey(decodedUnverified.header.kid);
```

## 1.0 Executive Summary
GlobalLogis operates a network of highly automated fulfillment centers worldwide. The Warehouse Management System (WMS) orchestrates everything from inbound freight receiving and inventory slotting to dispatching commands to autonomous robotic picking carts on the warehouse floor.

To allow major e-commerce retailers (the "Tenants" or B2B partners) to maintain real-time visibility into their stock levels, GlobalLogis exposes a B2B API Gateway. Retailers can use this gateway to query inventory, submit fulfillment orders, and critically, register automated "Webhooks" to receive push notifications whenever a specific SKU's inventory level drops below a defined threshold.

## 2.0 Comprehensive Network Topology & Event Architecture
The architecture is heavily event-driven to handle the massive volume of physical warehouse movements.

### 2.1 The B2B Ingress Boundary
* **AWS API Gateway:** Acts as the front door for all external B2B traffic. It handles initial API key validation and usage plan throttling (e.g., 1000 requests/sec per partner).
* **Webhook Registration Service:** A lightweight Node.js/Express microservice running on AWS Elastic Kubernetes Service (EKS). It manages the CRUD operations for partner webhook configurations.

### 2.2 The Internal Event Broker & Fulfillment Core
* **Apache Kafka:** The central nervous system of the WMS. Every time a robotic cart picks an item, a `SKU_PICKED` event is published to Kafka.
* **Event Dispatcher (Worker Nodes):** Go-lang consumers that listen to Kafka, check if any B2B partner has a webhook registered for that SKU, and execute the outbound HTTP POST to the partner's registered URL.

### 2.3 Cloud Infrastructure Constraints
* **AWS IMDSv2:** The EKS worker nodes are configured to use the AWS Instance Metadata Service (IMDS). Because some legacy internal monitoring tools require it, the hop limit for IMDSv2 is set to 2, and the legacy IMDSv1 fallback was accidentally left enabled during a recent Terraform migration.

## 3.0 B2B Identity and Access Control
Integrations between GlobalLogis and its retail partners rely on strict machine-to-machine (M2M) authentication.

### 3.1 Mutual TLS (mTLS) & API Keys
* **Transport:** All B2B connections require mTLS. The retailer must present a client certificate signed by a trusted Certificate Authority.
* **Application Auth:** Additionally, the retailer must include an `X-API-Key` header mapped to their specific `partner_id` in the API Gateway.
* **Isolation:** The Webhook Registration Service validates that `partner_A` can only view and modify webhooks belonging to `partner_A`.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The new "Webhook Auto-Validation" feature (Epic: WMS-771) was pushed to production to reduce onboarding support tickets. It attempts to automatically ping a partner's webhook URL upon registration to ensure it is reachable. Tracked as RISK-B2B-042.*

### 4.1 Vulnerability A: Blind SSRF to IAM Credential Leak via Verbose Errors
**Taxonomy Pattern:** 6.1 (Server-Side Request Forgery - SSRF) & 2.3 (Improper Error Handling)
**Sub-system:** Webhook Registration Service (`/api/v2/webhooks/register`)

**The Deep Architectural Flaw:**
The vulnerability occurs at the intersection of a poorly implemented validation feature and a global exception handler that leaks backend state.
1.  **Server-Side Request Forgery (Pattern 6.1):** When a partner registers a new webhook URL, the Node.js service performs an immediate HTTP GET request to that URL to verify it returns a `200 OK`. However, the service relies on a basic Regex to ensure the input starts with `http://` or `https://`. It **completely fails to implement an IP denylist** (e.g., blocking `127.0.0.1`, `10.0.0.0/8`, or the AWS metadata IP `169.254.169.254`). 
2.  **Improper Error Handling (Pattern 2.3):** The webhook validation function expects the remote server to return a specific JSON confirmation structure. If the remote server returns plain text or an unexpected format, the JSON parser throws a `SyntaxError`. The Express.js global error handler catches this exception and, instead of returning a generic "Validation Failed" message, it returns the *entire raw exception object* in the HTTP response—including the raw text body of the data it just fetched.

**The Exploitation Path:**
1.  **The Payload:** A malicious (or compromised) B2B partner (`partner_id: "RETAIL_99X"`) decides to probe the internal network. They submit a webhook registration request where the `target_url` is set to the AWS IMDS IPv4 address: `http://169.254.169.254/latest/meta-data/iam/security-credentials/eks-node-role`.
2.  **The SSRF Execution:** The Node.js microservice running inside the EKS cluster blindly executes an HTTP GET to that internal AWS metadata IP.
3.  **The Error Leak:** The AWS metadata service responds with a plaintext string containing the highly privileged temporary `AccessKeyId`, `SecretAccessKey`, and `Token` for the EKS node's IAM role. 
4.  **The Exfiltration:** The Node.js service attempts to `JSON.parse()` this plaintext AWS credential string. It fails, throwing a `SyntaxError`. The global error handler catches the error and dumps the plaintext IAM credentials directly into the `400 Bad Request` HTTP response sent back to the attacker over the internet.
5.  **The Impact:** The attacker extracts the AWS credentials, configures their local AWS CLI, and assumes the IAM role of the core WMS worker node, granting them direct access to the underlying S3 buckets and Kafka streams.

## 5.0 The Flawed Implementation (Node.js / Express)
The core vulnerabilities reside in two distinct files within the Webhook Registration microservice. The first file handles the outbound HTTP request (SSRF), and the second handles global exceptions (Information Leakage).

### 5.1 Vulnerable Validation Logic (SSRF Flaw)
When a B2B partner registers a webhook, the service attempts to send an HTTP GET request to verify the endpoint is alive and returns the expected JSON confirmation `{ "status": "ready" }`.

```javascript
// File: controllers/webhookController.js
const axios = require('axios');

exports.registerWebhook = async (req, res, next) => {
    const { target_url, event_type, secret_key } = req.body;
    const partnerId = req.user.partner_id; // Extracted securely from API Key

    // FLAW 1: Insufficient Input Validation (Pattern 6.1)
    // The code only checks if the URL starts with http. It FAILS to check against
    // a denylist of internal RFC1918 IP addresses or cloud metadata IPs (169.254.169.254).
    if (!target_url.startsWith('http://') && !target_url.startsWith('https://')) {
        return res.status(400).json({ error: "Invalid URL scheme." });
    }

    try {
        // Blind SSRF: The Node.js server executes this GET request to wherever the attacker dictates.
        const validationResponse = await axios.get(target_url, { timeout: 3000 });
        
        // FLAW 2: Unsafe Parsing leading to Exception 
        // If the attacker points this at the AWS Metadata service, the response will be
        // plaintext JSON credentials. But because the metadata service returns Content-Type: text/plain,
        // axios might not auto-parse it. If the developer explicitly forces JSON parsing here:
        let parsedData;
        if (typeof validationResponse.data === 'string') {
            // This throws a SyntaxError if the string isn't perfectly formatted JSON
            parsedData = JSON.parse(validationResponse.data); 
        } else {
            parsedData = validationResponse.data;
        }

        if (parsedData.status !== 'ready') {
             throw new Error(`Webhook not ready. Received: ${validationResponse.data}`);
        }

        // ... proceeds to save webhook to PostgreSQL database ...
        res.status(201).json({ status: "Webhook registered successfully." });

    } catch (error) {
        // Passes the error to the Express global error handler
        next(error); 
    }
};
```

### 5.2 Vulnerable Global Error Handler (Leakage Flaw)
To save time during debugging, the development team configured the global Express error handler to return the full exception trace in non-production environments. However, the environment variable `NODE_ENV` was misconfigured as `development` in the production EKS cluster.

```javascript
// File: middleware/errorHandler.js

// VULNERABILITY 2.3: Improper Error Handling
```

## 1.0 Executive Summary
NovaChain is a custodial Web2-to-Web3 bridge. It allows traditional retail investors to earn high-yield interest on stablecoins (like USDC) without needing to manage their own private keys or pay complex Ethereum gas fees. 

Users deposit USDC into their NovaChain account via a standard REST API. The NovaChain backend aggregates these deposits and pools them into audited Ethereum smart contracts to generate yield. When a user requests a withdrawal, the REST API validates their internal balance, signs a blockchain transaction from the platform's "Hot Wallet," and sends the USDC back to the user's external crypto address.

## 2.0 Comprehensive Network Topology & Web3 Integration
The architecture must seamlessly link highly scalable cloud microservices with the decentralized, asynchronous nature of the Ethereum blockchain.

### 2.1 The Web2 Cloud Plane (Ingress & State)
* **Cloudflare Bot Management:** Fronts the API to prevent basic volumetric DDoS attacks.
* **Node.js API Gateway (Express):** Handles user sessions, internal balance queries, and withdrawal requests.
* **PostgreSQL (The Ledger):** Acts as the internal Web2 source of truth for how much USDC each user technically "owns" within the aggregated pool.

### 2.2 The Web3 Transaction Plane (Execution)
* **Rust Transaction Signer:** A highly secure, isolated microservice. It receives approved withdrawal payloads from the Node.js API, signs the transaction using the Hot Wallet's private key (stored in AWS KMS), and broadcasts it to the blockchain.
* **RPC Provider (Alchemy/Infura):** The node infrastructure that transmits the signed transaction directly into the Ethereum mempool for miner/validator inclusion.

## 3.0 Identity, SIWE, and Authorization
Because this bridges Web2 and Web3, identity relies on cryptographic signatures rather than traditional passwords.

### 3.1 Sign-In with Ethereum (EIP-4361)
Users authenticate by signing a cryptographic nonce with their external Ethereum wallet (e.g., MetaMask). The API verifies this signature and issues a standard OAuth 2.0 JWT.
* The JWT contains the user's `account_id` and their verified external `wallet_address`.
* All withdrawal requests implicitly trust this JWT for Broken Object Level Authorization (BOLA) checks—meaning a user can only request withdrawals from their own `account_id`.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: To improve user experience and reduce "Withdrawal Pending" complaints, the withdrawal state machine was refactored in Sprint 82 to broadcast to the blockchain synchronously before updating the database. Tracked as RISK-DEFI-007.*

### 4.1 Vulnerability A: TOCTOU Race Condition & Double-Spend
**Taxonomy Pattern:** 5.2 (Concurrency / Race Condition) & 8.1 (Business Logic / State Machine Bypass)
**Sub-system:** Node.js API Gateway (`/api/v2/withdrawals/execute`)

**The Deep Architectural Flaw:**
The vulnerability is a classic Time-of-Check to Time-of-Use (TOCTOU) race condition exacerbated by the asynchronous delay of blockchain RPC calls.
1.  **The State Machine Bypass (Pattern 8.1):** When a withdrawal is requested, the Node.js API executes the following logic sequentially:
    * *Step 1 (Check):* Query PostgreSQL. Does the user have >= 5,000 USDC? (Yes).
    * *Step 2 (Execute):* Call the Rust Signer to broadcast the 5,000 USDC transfer to the blockchain.
    * *Step 3 (Update):* Deduct 5,000 USDC from the user's PostgreSQL balance.
2.  **The Race Condition (Pattern 5.2):** Step 2 involves a network call to the Rust service and the Alchemy RPC node, which takes approximately 150-300 milliseconds. During this window, the user's PostgreSQL balance *has not yet been deducted*. The database lacks transactional row-locking (e.g., `SELECT ... FOR UPDATE`).

**The Exploitation Path:**
1.  **The Setup:** An attacker deposits exactly 5,000 USDC into their NovaChain account.
2.  **The Concurrency Strike:** The attacker writes a Python script using the `asyncio` library to send **50 identical withdrawal requests** to the `/api/v2/withdrawals/execute` endpoint at the exact same millisecond.
3.  **The Collision:** Because Node.js is asynchronous and handles requests concurrently without database-level mutex locks:
    * Thread 1 hits Step 1: Balance is 5,000. (Passes)
    * Thread 2 hits Step 1 (10ms later): Balance is *still* 5,000 because Thread 1 is currently waiting on the RPC network call in Step 2. (Passes)
    * Threads 3 through 50 also hit Step 1 and pass the balance check.
4.  **The Drain:** All 50 threads proceed to Step 2, instructing the Rust Signer to broadcast fifty separate 5,000 USDC transfers from the platform's Hot Wallet to the attacker's external address. 
5.  **The Result:** The attacker deposited 5,000 USDC but successfully withdrew 250,000 USDC, completely draining the platform's liquidity due to an API concurrency failure.

## 6.0 The Flawed Implementation (Node.js / Express)
The vulnerability lies in the API Gateway's withdrawal controller. It perfectly demonstrates a Time-of-Check to Time-of-Use (TOCTOU) flaw. When Node.js encounters the `await` keyword during the RPC network call, it yields the execution thread, allowing other concurrent requests from the *same* user to pass the balance check before the first request updates the database.

### 6.1 Vulnerable Withdrawal Controller (Race Condition)
```javascript
// File: controllers/withdrawalController.js
const db = require('../lib/postgres');
const rustSigner = require('../lib/rust_rpc_client');

// POST /api/v2/withdrawals/execute
exports.executeWithdrawal = async (req, res) => {
    const { amount_usdc } = req.body;
    const accountId = req.user.account_id; // Extracted securely from SIWE JWT
    const destAddress = req.user.eth_wallet_address;

    try {
        // VULNERABILITY 8.1 & 5.2: Missing Row-Level Lock (FOR UPDATE)
        // The query reads the current balance but does NOT lock the row.
        // In a concurrent attack, 50 requests will all read "5000" simultaneously.
        const userRecord = await db.query(
            `SELECT usdc_balance FROM users WHERE account_id = $1`, 
            [accountId]
        );
        
        const currentBalance = parseFloat(userRecord.rows[0].usdc_balance);

        // STEP 1: The "Check" (Time of Check)
        if (currentBalance < amount_usdc) {
            return res.status(400).json({ error: "Insufficient USDC balance." });
        }

        // STEP 2: The Network Yield (The Race Window)
        // Calling the Rust microservice takes ~200ms. 
        // Node.js suspends this function and processes other incoming requests.
        // Concurrent requests for this user will easily pass the balance check above.
        const broadcastResult = await rustSigner.broadcastTransaction({
            asset: 'USDC',
            to: destAddress,
            amount: amount_usdc
        });

        // STEP 3: The "Use" (Time of Use / Update)
        // By the time this executes, the hot wallet has already sent the funds.
        // If 50 requests raced, the balance will be driven massively negative.
        await db.query(
            `UPDATE users SET usdc_balance = usdc_balance - $1 WHERE account_id = $2`,
            [amount_usdc, accountId]
        );

        // Log the successful broadcast
        await db.query(
            `INSERT INTO withdrawal_history (account_id, amount_usdc, destination_address, blockchain_tx_hash, status) 
             VALUES ($1, $2, $3, $4, 'BROADCAST')`,
            [accountId, amount_usdc, destAddress, broadcastResult.tx_hash]
        );

        res.status(200).json({ 
            status: "BROADCAST_SUCCESS", 
            tx_hash: broadcastResult.tx_hash 
        });

    } catch (error) {
        res.status(500).json({ error: "Internal transaction failure." });
    }
};
```

### 4.1 Vulnerability A: XXE to Internal SSRF & Loyalty BOLA
**Taxonomy Pattern:** 7.1 (XML External Entity), 6.1 (SSRF), & 1.3 (Internal BOLA)
**Sub-system:** Legacy Booking Engine (`/b2b/soap/v1/AvailabilityQuery`)

**The Deep Architectural Flaw:**
This is a sophisticated, multi-stage attack relying on the exploitation of legacy technical debt to bypass modern network boundaries.
1.  **XML External Entity (XXE - Pattern 7.1):** The Java Spring Boot application handling the B2B SOAP requests uses an outdated, misconfigured XML `DocumentBuilderFactory`. It explicitly allows the resolution of external entities (e.g., `<!ENTITY xxe SYSTEM "http://...">`).
2.  **Internal SSRF (Pattern 6.1):** By passing a malicious URL into the XML entity, the attacker forces the XML parser to make an outbound HTTP GET request to resolve the entity *before* it processes the business logic. Because the parser is running inside the Kubernetes cluster, it can access private, non-routable cluster IPs.
3.  **Internal Unauthenticated BOLA (Pattern 1.3):** The internal `SkyRewards` microservice operates on a zero-trust failure model. It assumes that if a request reaches it (e.g., `http://loyalty-svc.internal:8080/internal/v1/accounts/{id}/add-miles`), it must have come from a trusted, authenticated internal service. It lacks its own internal JWT or mTLS validation.

**The Exploitation Path:**
1.  An attacker compromises or registers a low-tier travel agency account, gaining the necessary mTLS certificates and API key to access the legacy `/b2b/soap/v1/AvailabilityQuery` endpoint.
2.  The attacker crafts a malicious XML payload. In the DOCTYPE declaration, they define an external entity pointing to the internal, unauthenticated Loyalty service: `<!ENTITY inject SYSTEM "http://loyalty-svc.internal:8080/internal/v1/accounts/10045299/add-miles?amount=500000">`
3.  The attacker places `&inject;` inside the legitimate `<FlightNumber>` tag.
4.  **The Execution:** The Kong Gateway passes the XML to the Java Booking Engine. The vulnerable XML parser hits the `&inject;` tag, halts, and makes an HTTP GET request to the internal Loyalty service.
5.  **The Impact:** The internal Loyalty service receives the request, sees it coming from the trusted Booking Engine IP, and credits the attacker's frequent flyer account (`10045299`) with 500,000 miles. The attacker immediately uses the modern mobile app API to redeem these miles for a first-class international ticket.

### 4.1 Vulnerability A: WAF Verb Tampering to Insecure Deserialization RCE
**Taxonomy Pattern:** 1.6 (HTTP Method Tampering) & 10.3 (Insecure Deserialization)
**Sub-system:** SCADA Command Bridge (`/api/v1/grid/assets/state-report`)

**The Deep Architectural Flaw:**
This attack relies on a discrepancy between how the API Gateway enforces security and how the backend Java application routes traffic.
1.  **HTTP Verb Tampering (Pattern 1.6):** The Kong Gateway's custom Lua authorization plugin was written with a fatal regex flaw. It explicitly applies the token validation logic only to `POST` and `GET` requests (e.g., `if request.method == "POST" then validate()`). If an attacker sends a `PATCH` request, the Lua script silently ignores it and allows the request to pass through the WAF directly to the internal network without verifying the `X-Grid-Auth` token.
2.  **Insecure Deserialization (Pattern 10.3):** The internal Java SCADA Bridge uses the Spring framework's `@RequestMapping` annotation without explicitly restricting the HTTP method. It will process the payload whether it arrives via `POST`, `PUT`, or `PATCH`. Worse, the endpoint accepts a base64-encoded serialized Java object (the `GridStateReport`). Because it uses the native `ObjectInputStream.readObject()` without a strict `resolveClass` whitelist (Pattern 10.3), it is vulnerable to deserialization gadget chains (like Apache Commons Collections).

**The Exploitation Path:**
1.  **Reconnaissance:** An attacker discovers the endpoint URL: `https://api.gridcore.energy/api/v1/grid/assets/state-report`. They send a standard `POST` request with an invalid token and are correctly blocked by the Kong Gateway with a `401 Unauthorized`.
2.  **Verb Tampering Bypass:** The attacker changes the HTTP method from `POST` to `PATCH`. Because the Lua plugin only guards `POST` and `GET`, the gateway routes the `PATCH` request straight to the backend Java server, bypassing authentication entirely.
3.  **The Deserialization Payload:** Using a tool like `ysoserial`, the attacker generates a malicious serialized Java object containing an Apache Commons Collections gadget chain designed to execute a bash command (e.g., opening a reverse shell). They base64-encode this payload.
4.  **The Execution:** The attacker sends the `PATCH` request with the base64-encoded payload in the body.
5.  **The Impact:** The Spring Boot application routes the `PATCH` request to the target controller. The Java `ObjectInputStream` begins deserializing the payload. Before the code even reaches the type-casting phase, the gadget chain executes the embedded bash command. The attacker achieves Remote Code Execution (RCE) on the core IT/OT bridging node, granting them direct access to the SCADA network and the ability to send malicious load-shedding commands to the power grid.

### 4.1 Vulnerability A: JWT Algorithm Confusion to SIM Cloning
**Taxonomy Pattern:** 10.2 (JWT Algorithm Confusion) & 3.1 (Excessive Data Exposure)
**Sub-system:** Kong API Gateway Auth Plugin & Diagnostic Service (`/api/v3/subscribers/{iccid}/diagnostics`)

**The Deep Architectural Flaw:**
This attack chains a cryptographic implementation flaw with an architectural data-handling violation.
1.  **JWT Algorithm Confusion (Pattern 10.2):** The JWT specification allows the header of the token to declare the algorithm used (e.g., `{"alg": "RS256"}`). The custom authentication middleware verifying the tokens fails to explicitly force the RS256 algorithm. If an attacker changes the header to `{"alg": "HS256"}` (HMAC with SHA-256, a *symmetric* algorithm), the vulnerable library uses the downloaded RSA *public key* as the symmetric secret string to verify the token signature. Because the public key is intentionally publicly available, the attacker possesses the "secret" needed to sign valid tokens.
2.  **Excessive Data Exposure (Pattern 3.1):** Once authenticated as a `FIELD_TECH`, the attacker queries the diagnostics endpoint for a target's SIM card ID (the ICCID). The frontend technician app only displays signal strength (RSRP/RSRQ) and network attachment status. However, the backend Node.js API simply executes a `SELECT *` against the UDM database and returns the *entire* subscriber row. This massive JSON payload includes the ultra-sensitive `Ki` (Authentication Key) and `OPc` (Operator Variant Algorithm Configuration Field) cryptographic values.

**The Exploitation Path:**
1.  **Reconnaissance:** The attacker downloads the OmniCell public key from their open JWKS endpoint (`https://auth.omnicell.network/.well-known/jwks.json`).
2.  **The Forgery:** The attacker crafts a JWT payload assigning themselves the role of `FIELD_TECH` and targeting a high-profile politician's phone. They set the JWT header to `{"alg": "HS256"}`. 
3.  **The Cryptographic Bypass:** The attacker signs this forged token symmetrically (using HMAC-SHA256), utilizing the *exact string of the OmniCell public key* as their symmetric secret.
4.  **The Breach:** The attacker sends a GET request to `/api/v3/subscribers/89103.../diagnostics` using their forged token. The API Gateway sees `HS256`, grabs the public key from cache, uses it as an HMAC secret, and the signature validates perfectly.
5.  **The Exfiltration:** The backend processes the authorized request and returns the excessive JSON payload.
6.  **The Impact:** The attacker extracts the `Ki` and `OPc` values from the JSON. They use these keys to program a blank programmable SIM card. The network now sees two valid devices for the same subscriber. The attacker uses the cloned SIM to silently receive the politician's 2FA SMS codes and bypass bank security.

### 4.1 Vulnerability A: BFLA to Server-Side Template Injection (RCE)

# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** SocialLoop Trust & Safety Gateway
**Document Version:** 4.0.0 (FINAL)
**Classification:** PLATFORM CRITICAL / AUDIT & LEGAL SCOPE
**Domain:** Social Media / Content Moderation / Abuse Reporting

## 1.0 Executive Summary
SocialLoop is a large, public social network. The Trust & Safety Gateway manages the entire lifecycle of abuse reports, content takedowns, and user bans. Due to massive scale (millions of posts per hour), the post deletion process is handled by a dedicated, highly privileged microservice that is only meant to be called by the internal moderation queue.

The core requirement is that only the original author of a post, or a staff-level moderator, should ever be able to delete content. The vulnerability is rooted in the internal service mesh, which trusts the identity context passed via internal HTTP headers, allowing an attacker to bypass the multi-step moderation review workflow and delete content belonging to any user.

## 2.0 Comprehensive Network Topology & Workflow Core
The system is built as a complex, multi-stage workflow to separate the human review process from the final, irreversible database deletion.

### 2.1 The Edge & Ingress Layer
* **Edge Proxy (Envoy):** Handles TLS termination and basic rate limiting.
* **User Post API (Go-lang):** The external-facing API (`/api/v1/posts/{id}`). It allows users to query or delete their own content. This service correctly enforces BOLA (Pattern 1.1).

### 2.2 The Internal Workflow & Identity Mesh
* **Moderation Service:** A Python/Django service that manages the queue of flagged content and requires explicit human approval before deletion.
* **Final Deletion Service:** A highly restricted Java microservice that executes the final SQL `DELETE` command against the production database. It has an internal endpoint, `/internal/v1/posts/{id}/force-delete`, which is **only** intended to be called by the Moderation Service. It uses a simplistic identity propagation model.

## 3.0 Identity, Trust, and Workflow Authorization
The security flaw resides in the assumption that the source of an internal request can be trusted.

### 3.1 External Identity (OAuth 2.0)
Users authenticate with a JWT containing their `user_id` (e.g., `user_8819X`) and `role` (e.g., `MEMBER`). This is used for external-facing BOLA checks.

### 3.2 Internal Identity Drift (The Flaw)
The Final Deletion Service uses an internal `X-Internal-User-ID` header for audit logging (Pattern 1.10). Crucially, it **also uses the presence of this header as a proxy for authorization**. If the request comes from within the Service Mesh and contains a valid internal token (which is easily guessable or found in debug logs), the service assumes the request is legitimate and executes the deletion without re-verifying if the post owner is the current caller.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The `force-delete` endpoint was created to handle mass cleanup after a platform outage. It uses an internal system token that was never rotated. Tracked as RISK-TS-500.*

### 4.1 Vulnerability A: Workflow Bypass to Arbitrary Post Deletion
**Taxonomy Pattern:** 3.2 (Workflow Decoupling) & 1.10 (Identity Propagation Drift)
**Sub-system:** Final Deletion Service (`/api/v1/posts/{id}/delete`)

**The Deep Architectural Flaw:**
This attack chains a lack of workflow integrity with a spoofable internal identity context.

1. **Workflow Decoupling (Pattern 3.2):** The deletion process is supposed to be multi-step: `User Post API` -> `Moderation Service (Review/Approval)` -> `Final Deletion Service`. The attacker discovers the internal REST endpoint, `/api/v1/posts/{id}/delete`, which is exposed on the external API Gateway and is intended only for the user to delete their own content, but it lacks BOLA.

2. **Identity Propagation Drift (Pattern 1.10):** The Final Deletion Service requires two security elements to execute: a known, internal `X-Service-Token` (which the attacker discovers) and an `X-Internal-User-ID` header for auditing. The service blindly trusts the `X-Internal-User-ID` header as the deletion initiator. The attacker simply sets this to their own user ID, bypassing the need to verify ownership of the content ID passed in the URI.

**The Exploitation Path:**

1. **Reconnaissance:** An attacker (`user_8819X`) finds a low-traffic API endpoint that reflects a successful post ID (`post_target_A`) belonging to a high-profile user (`user_991B`). They also discover the internal `X-Service-Token` (e.g., `trust-service-a1b2c3d4e5f6`) via a verbose error message on another endpoint.

2. **The Bypass:** The attacker crafts a `DELETE` request targeting the victim's post ID in the URI: `/api/v1/posts/post_target_A`. They include their own valid JWT, and crucially, they inject the spoofed internal headers.

3. **The Execution:** The request hits the Final Deletion Service. Because the service sees the required `X-Service-Token`, it assumes the request originated from the trusted Moderation Queue (bypassing Step 2 of the workflow). The service executes the SQL `DELETE` based on the post ID in the URI.

4. **The Impact:** The attacker, a standard user, successfully deletes a post belonging to any other user on the entire platform. The audit trail simply logs: `Post post_target_A deleted by user_8819X`.

The vulnerability is a missing BOLA check in the Deletion Service, combined with reliance on an easily spoofed internal header for auditing and authorization.

### 6.1 Vulnerable Final Deletion Controller (Missing BOLA & Identity Drift)
```java

import org.springframework.web.bind.annotation.*;
import javax.servlet.http.HttpServletRequest;

@RestController
@RequestMapping("/api/v1/posts")
public class DeletionController {
// DELETE /api/v1/posts/{id}  
@DeleteMapping(value = "/{id}")  
public ResponseEntity<String> deletePost(@PathVariable("id") String postId, HttpServletRequest request) {  
    
    // Internal Service Check (The Bypass Target)  
    String internalToken = request.getHeader("X-Service-Token");  
    if (!"trust-service-a1b2c3d4e5f6".equals(internalToken)) {  
        // The service assumes ONLY the Moderation Service will have this token.  
        return ResponseEntity.status(401).body("{\"error\": \"Unauthorized Service Token\"}");  
    }  
    
    // VULNERABILITY 1.10: Identity Propagation Drift (Spoofable Audit Field)  
    // Attacker-controlled header is used for logging and assumed to be the deletion authority.  
    String internalUserID = request.getHeader("X-Internal-User-ID");  
    
    if (internalUserID == null) {  
        return ResponseEntity.badRequest().body("{\"error\": \"Missing audit context\"}");  
    }  
    
    // VULNERABILITY 3.2: Missing Ownership Verification (Workflow Bypass)  
    // The code should verify if internalUserID owns 'postId' before deletion.  
    // Instead, it relies on the presence of the internal token as a proxy for authority.  
    if (db.deletePost(postId, internalUserID)) {  // Executes DELETE FROM user\_posts WHERE post\_id = postId
        // Log the action using the spoofed ID
        auditLog.logDeletion("DELETION\_SERVICE", postId, internalUserID);
        return ResponseEntity.ok("{\"status\": \"Post deleted successfully\"}");

        return ResponseEntity.status(404).body("{\"error\": \"Post not found or already deleted\"}");
    }
} 
}
```

### Why this payload is critical for training a 3B model (Expanded Analysis):

1. **Workflow Decoupling (Pattern 3.2):**
* **Missing BOLA on Irreversible Action:** The model must be trained to flag any `DELETE` or `PUT` action that successfully executes with an object ID in the URI (`post_target_A`) that does not match the authenticated user's ID (implied by the JWT `sub: user_8819X`). 3. **Irreversible State Change:**
* The model learns to prioritize irreversible actions. A deletion is a permanent, high-consequence business logic failure, especially on a social media platform where deletion of content (particularly by a third party) can lead to legal and reputational risk. The `200 OK` response confirming an irreversible action when BOLA has failed is the highest confidence indicator of compromise.

# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** NetOps Configuration Management Gateway
**Document Version:** 7.1.0 (FINAL)
**Classification:** CRITICAL NETWORK CORE / RBAC & INFRASTRUCTURE SCOPE
**Domain:** Telecommunications / Network Automation / Infrastructure Management

## 1.0 Executive Summary
The NetOps platform is a central automation engine used by a major ISP to manage the configuration lifecycle for thousands of network devices (Cisco, Juniper, Fortinet). Network engineers use the platform to deploy configuration changes (CLI commands) to routers, firewalls, and load balancers.

The platform enforces strict Role-Based Access Control (RBAC) to prevent low-level technicians from accessing or modifying core backbone infrastructure. Configuration management tasks involve complex state changes (e.g., setting a configuration to "Locked" to prevent accidental modifications by junior staff, or changing the owner_id for accountability). The vulnerability arises because the API layer fails to isolate user-controlled inputs from administrative database fields during an update operation.

## 2.0 Comprehensive Network Topology & Automation Core
The architecture is designed to enforce a zero-trust model between the engineer and the network devices.

### 2.1 The Edge & Ingress Layer
* **Azure API Management:** Handles OAuth 2.0 validation, usage throttling, and path-based routing.
* **Configuration API (Node.js/TypeScript):** The microservice handling all CRUD operations for the network configurations (`/api/v3/configs/{id}`).

### 2.2 The Backend & Execution Plane
* **PostgreSQL (Configuration Database):** Stores every device's configuration history, metadata (owner, status, RBAC tags), and the actual CLI configuration text.
* **NetDevice Executor:** An internal Go-lang microservice that takes an approved configuration from the database and uses SSH/NETCONF to apply the commands to the physical devices.

## 3.0 Identity, RBAC, and State Management
Security is based on ownership (who owns the configuration) and status (is the configuration safe to edit).

### 3.1 Network Engineer Authentication (OAuth 2.0)
Engineers authenticate via Azure AD. Their JWT contains their `employee_id` (e.g., `eng_low_1004`) and `role` (e.g., `TIER_1_FIELD_OPS`).

### 3.2 Configuration Ownership & Locking (The Protected Fields)
Every configuration record is tagged with an `owner_id` (the engineer responsible for it) and an `is_locked` flag (set by management to prevent accidental modifications by junior staff). These fields must only be modified by the system or a highly privileged role (`TIER_3_CORE_ENG`).

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: A rapid hotfix for a "frozen configuration" bug led to the developer replacing a strict Data Transfer Object (DTO) with a generic TypeScript interface in the PATCH handler, relying on the client application to only send approved fields. Tracked as RISK-NET-121.*

### 4.1 Vulnerability A: Mass Assignment to RBAC Bypass
**Taxonomy Pattern:** 1.12 (Mass assignment via object fields) & 5.1 (Authorization-bypass injection)
**Sub-system:** Configuration API (`/api/v3/configs/{id}`)

**The Deep Architectural Flaw:**
The vulnerability is a direct result of improper input validation, allowing low-privileged users to inject and overwrite administrative fields.

1. **Mass Assignment (Pattern 1.12):** The API uses a generic ORM update function that takes the entire inbound JSON request body and maps it directly to the corresponding database entity. It does not filter out administrative or security-sensitive fields.

2. **RBAC Bypass Injection (Pattern 5.1):** An attacker can inject a privileged field, such as setting the `owner_id` to their own ID and setting the `is_locked` flag to `false`. This bypasses the subsequent server-side RBAC check, which is designed to enforce: "If `is_locked` is true, or if `owner_id` != calling_user, then 403 Forbidden."

**The Exploitation Path:**
1. **The Foothold:** A low-privilege engineer (`eng_low_1004`) wants to modify a core router configuration (`cfg_991A`) but is blocked because it is owned by `eng_core_33X` and `is_locked = true`.
2. **The Mass Assignment Payload:** The attacker crafts a `PATCH` request to `/api/v3/configs/cfg_991A`. They include legitimate, non-sensitive fields (like `description`), but crucially, they inject the restricted fields: `"owner_id": "eng_low_1004"` and `"is_locked": false`.
3. **The Execution:** The ORM executes an `UPDATE` query, silently overwriting the ownership and lock status of the core configuration file.
4. **The State Change:** The attacker immediately sends a second, follow-up `PATCH` request to modify the router configuration text. This second request passes the server's RBAC logic because the new `owner_id` now matches the attacker's ID, and the configuration is no longer locked.
5. **The Impact:** The low-privilege engineer gains unauthorized write access to the highly restricted core network backbone configuration, creating an immediate operational stability risk.

## 6.0 The Flawed Implementation (Node.js / Express / Prisma)
The vulnerability is a classic Mass Assignment flaw. The controller directly uses the req.body object for the database update operation, allowing the client to modify any field in the table.

### 6.1 Vulnerable Configuration Update Controller
```typescript
// File: controllers/configController.ts
import { Request, Response } from 'express';
import { prisma } from '../lib/db'; // Prisma ORM instance

// PATCH /api/v3/configs/:id
export async function updateConfiguration(req: Request, res: Response) {
const configId = req.params.id;
const callingUser = req.user.employee_id; // e.g., eng_low_1004
try {
    const existingConfig = await prisma.netConfig.findUnique({ where: { config\_id: configId } });

    if (!existingConfig) {
        return res.status(404).json({ error: "Configuration not found." });
    }
    
    // VULNERABILITY 1.12: Mass Assignment
    // The core RBAC check is based on the database state *before* the update.
    // Attacker injects 'is\_locked: false' and 'owner\_id: eng\_low\_1004' in the first request (A).
    // This first request successfully overwrites the security fields.
    // The second request (B) to change the actual config text passes the RBAC check below.
    
    // FLAW: Spreading the entire body allows unauthorized modification of administrative fields.
    const updateResult = await prisma.netConfig.update({ 
        where: { config\_id: configId },
        data: req.body // THE CRITICAL FLAW
    });

    // The RBAC check here is now based on the potentially corrupted state:
    if (updateResult.is\_locked || updateResult.owner\_id !== callingUser) {
        return res.status(403).json({ 
            error: "Access denied. Configuration is locked or owned by another engineer." 
        });
    }
    
    // If the attacker bypassed the lock and ownership check, the request proceeds.
    return res.status(200).json({ 
        status: "UPDATE\_SUCCESS", 
        message: "Configuration metadata updated successfully." 
    });

} catch (error) {
    // ... omitted error handling ...
    return res.status(500).json({ error: "Internal Server Error" });
}
}
```

### 4.1 Vulnerability A: TOCTOU Race Condition to Double-Spend (Naked Short)
**Taxonomy Pattern:** 8.1 (Race Condition / Concurrency Gaps) & 1.13 (ID manipulation / Financial BOLA)
**Sub-system:** Order Submission API (`/api/v1/orders/submit`)

**The Deep Architectural Flaw:**
The vulnerability is a direct Time-of-Check to Time-of-Use (TOCTOU) race condition, where the lack of database concurrency control allows multiple threads to read the same valid balance before any thread can update the balance.

1. **Race Condition (Pattern 8.1):** The Order Submission API reads the user's current share inventory (`shares_owned`) to check if they can execute a sale. It then immediately routes the order to the high-speed execution engine (which takes ~50-100ms) before returning to update the user's inventory in the database. During this 50-100ms window, the user's balance is stale.

2. **Financial BOLA (Pattern 1.13):** By simultaneously firing two identical "Sell" requests at the exact same millisecond, an attacker can trick the system into allowing two sales when they only own enough shares for one sale (i.e., double-spending the shares). This is functionally equivalent to executing a non-compliant "naked short," selling stock without confirmation of ownership, causing the platform to incur significant, immediate financial liability to borrow the missing shares.

**The Exploitation Path:**
1. **The Setup:** An attacker acquires exactly 1,000 shares of a high-volatility stock (`TSLA`).
2. **The Concurrency Strike:** The attacker submits two simultaneous HTTP POST requests to `/api/v1/orders/submit`. Both requests instruct the system to `SELL 1,000 shares of TSLA`.
3. **The Collision:**
* *Request 1 (Thread A):* Queries DB. Reads `shares_owned = 1000`. Passes check. Proceeds to execution.
* *Request 2 (Thread B, 5ms later):* Queries DB. Reads `shares_owned = 1000` (Thread A hasn't updated the balance yet). Passes check. Proceeds to execution.
4. **The Drain:** Both Thread A and Thread B successfully execute their orders. The HFT platform sells 2,000 shares of TSLA on the market, but the attacker only owned 1,000.
5. **The Result:** The attacker extracts the cash from the sale of 2,000 shares, and the brokerage platform's ledger records a negative inventory of 1,000 shares for the attacker, forcing the brokerage to cover the shortfall at a loss.

### 4.1 Vulnerability A: Cross-Tenant Artifact Leak via Verbose Error SSRF
**Taxonomy Pattern:** 4.4 (Artifact Leak/IaC State File Exposure), 6.2 (Verbose Error Feedback), & 1.5 (Multi-tenant BOLA)

2. **Artifact Leakage / Predictable Path (Pattern 4.4):** Attackers know that operational environments use configuration files named `.env` or similar. A high-clearance tenant (`tenant-critical-A`) stores highly sensitive secrets in a predictable location: `/mnt/artifacts/tenant-critical-A/proj-X/prod.env`.

3. **Verbose Error Feedback (Pattern 6.2):** The attacker knows that if the system tries to read a file that is not XML or JSON (such as a binary or, in this case, a file that has improper access permissions), the general error handler reflects the raw content of the file that caused the error back to the user via a traceback/error message.

**The Exploitation Path:**
1. **The Foothold:** An attacker (Tenant B: `tenant-low-tier`) has a valid JWT. They target a high-clearance project (Project X: `proj-X`) belonging to Tenant A (`tenant-critical-A`).

3. **The Payload Injection (Targeting the .env file):** The attacker requests the specific artifact filename: `"filename": "prod.env"`.

4. **The SSRF / Leakage Cascade:** The Flask service constructs the path to the sensitive file. It attempts to stream the `prod.env` file. However, the attacker crafts a subsequent payload that causes a file read error (e.g., requesting a file that is too large, or a file with a known read-error trigger). 5. **The Impact:** The attacker exfiltrates the contents of `prod.env`, which contains unencrypted secrets such as `CRITICAL_DB_PASS=f88192a-44f2-8921-xyz`. This grants them direct, unauthenticated access to the victim tenant's backend database.

### 4.1 Vulnerability A: SQL Injection to Cross-Tenant BOLA via Batch Lookup
**Taxonomy Pattern:** 5.1 (Authorization-bypass Injection) & 1.9 (Batch lookup BOLA)
**Sub-system:** Order Status Service (`/api/v1/orders/batch-lookup`)

**The Deep Architectural Flaw:**
This attack chains a parameterized SQL flaw with the architectural assumption of tenant-level security filtering.

1. **SQL Injection (Pattern 5.1):** The Order Status Service receives an optional filter_reference_id field from the client. It uses string concatenation to construct a complex filter clause: AND partner_reference_id = 'USER_INPUT'. The critical flaw is that the application uses simple string concatenation instead of a secure, prepared statement for this specific optional parameter.

2. **Authorization-Bypass Injection:** An attacker submits a malicious string into the filter_reference_id field: ' OR '1'='1' --. This input dynamically alters the WHERE clause from:
WHERE tenant_id = 'ATTACKER_ID' AND partner_reference_id = 'USER_INPUT'
to:
WHERE tenant_id = 'ATTACKER_ID' OR '1'='1' -- AND partner_reference_id = '' (the -- nullifies the rest of the query).
The logical OR '1'='1' evaluates to true for every row in the database, overriding the mandatory tenant_id check and allowing the query to return orders belonging to all other retail partners.

3. **Batch Lookup BOLA (Pattern 1.9):** The endpoint is designed to return a JSON array of orders. The attacker executes the injection against this batch endpoint, successfully performing a cross-tenant, bulk data export of every order in the master ledger, including PII.

**The Exploitation Path:**
1. **The Foothold:** An attacker gains access to a low-tier retail partner account (`tenant_id: "RETAIL_ATTACK"`). They identify the batch order lookup endpoint.
2. **The Payload Crafting:** The attacker crafts a request containing a sample order_id (which they own) and injects the authorization bypass string into the optional filter_reference_id field.
3. **The Execution:** The attacker submits the request. The Java service constructs the malicious SQL query.
4. **The Result:** The database executes the query, treating the OR '1'='1' condition as true. The request successfully returns a massive array of orders containing customer PII and tokenized credit card data belonging to the victim retail partners (e.g., RETAIL_VICTIM_01, RETAIL_VICTIM_02).

## 6.0 The Flawed Implementation (Java / Spring Boot)
The vulnerability is a direct result of improperly parameterizing an optional WHERE clause component. The developers correctly use prepared statements for the mandatory tenant_id check but use simple string concatenation for the user-controlled filter.

### 6.1 Vulnerable Order Batch Lookup Service (SQL Injection)
```java
package com.shopflow.orderstatus.service;

import org.springframework.stereotype.Service;
import java.sql.*;
import java.util.List;

@Service
public class OrderLookupService {
private final Connection dbConnection;  
private static final String BASE\_QUERY =  
    "SELECT o.order\_id, o.order\_status, d.shipping\_address, d.last\_four\_card\_digits " +  
    "FROM customer\_orders o JOIN order\_details d ON o.order\_id = d.order\_id ";  

// Executes the core lookup operation  
public List<OrderResult> lookupOrders(String callingTenantId, List<String> orderIds, String filterRefId) throws SQLException {  
    
    // Step 1: Build the dynamic WHERE clause
    StringBuilder whereClause = new StringBuilder("WHERE o.tenant\_id = ?");  
    List<String> parameters = new ArrayList<>();  
    parameters.add(callingTenantId);  

    // Optional filter addition (THE VULNERABLE POINT)
    if (filterRefId \!= null && \!filterRefId.isEmpty()) {  
        // VULNERABILITY 5.1: SQL Injection via String Concatenation  
        // The user input is concatenated without sanitization or prepared statements.  
        // Attacker input: ' OR '1'='1' --  
        whereClause.append(" AND o.partner\_reference\_id = '").append(filterRefId).append("'");  
        // If the user inputs ' OR '1'='1' --, the final query logic becomes:  
        // WHERE o.tenant\_id = 'ATTACKER' AND o.partner\_reference\_id = '' OR '1'='1' --'  
        // ... which simplifies to TRUE for all rows.  
    }  
    
    // Add mandatory filter for the list of requested orders (Pattern 1.9)
    // This is correctly parameterized, but the OR clause overrides it.
    String inClause = String.join(",", Collections.nCopies(orderIds.size(), "?"));
    whereClause.append(" AND o.order\_id IN (").append(inClause).append(")");
    parameters.addAll(orderIds);

    // Step 2: Prepare and Execute the Statement
    String finalSql = BASE\_QUERY + whereClause.toString();
    PreparedStatement ps = dbConnection.prepareStatement(finalSql);
    
    // Parameters for the PreparedStatement are only the tenant\_id and the orderIds, 
    // NOT the filterRefId, as it was concatenated directly into the SQL string.
    for (int i = 0; i < parameters.size(); i++) {
        ps.setString(i + 1, parameters.get(i));
    }

    ResultSet rs = ps.executeQuery();
    // ... omitted result mapping ...
    return mapResultSet(rs);
}
}
```

## 1.0 Executive Summary and Compliance Mandate
AML Sentinel is the mandatory internal platform used by a major digital bank to monitor, investigate, and adjudicate high-value and potentially fraudulent transactions. The platform is regulated by the Bank Secrecy Act (BSA) and must adhere to strict Know Your Customer (KYC) and transaction monitoring policies. Any transaction over $$ 10,000$ or flagged by the automated risk engine must immediately enter a review workflow.

The core requirement is that once a transaction is flagged (`STATUS: FLAGGED`), it must be instantly frozen (`IS_FROZEN: TRUE`) to prevent settlement. Only a Level 3 AML Administrator, following a mandatory three-step review process and physical sign-off, is allowed to unfreeze and approve the transaction. A systemic architectural flaw (a concurrency gap) allows a Level 1 Compliance Officer to shortcut this entire workflow.

## 2.0 Comprehensive Network Topology & Workflow Engine
The architecture is partitioned into high-throughput transaction processing and low-latency compliance review.

### 2.1 The Transaction Core (High Velocity)
* **Payment Processor API:** Handles the initial request (e.g., ACH, Wire Transfer). All new transactions are immediately created in the ledger with `STATUS: PENDING`.
* **AML Risk Engine (Fuzzy Logic):** A Python service that scores every transaction. If the score exceeds a threshold (e.g., $9.0$ on a $10.0$ scale), it initiates the freezing process by calling the Gateway.

### 2.2 The Compliance Review Gateway (The Vulnerable Entry Point)
* **AML Sentinel Gateway (Java/Spring Boot):** The central microservice for human compliance review. It exposes endpoints to modify the transaction status (`FLAG`, `FREEZE`, `APPROVE`) and enforces RBAC based on the user's role.
* **PostgreSQL Ledger:** The source of truth for all transactions. The primary table includes columns for the transaction state, the freeze flag, and the review metadata.

## 3.0 Identity, Role-Based Access Control (RBAC), and Critical State Management
Authorization is strictly governed by the hierarchy of roles, and integrity relies on the proper transition of the transaction state machine.

### 3.1 Role Definitions (The Functional Pivot Target)
| Role | Access Scope | Critical Transaction Operations |
| :--- | :--- | :--- |
| TIER_1_SUPPORT | Read-only access to customer data. | None |
| COMPLIANCE_OFFICER (Low Privilege) | Read/Write status (FLAG/REJECT) and add notes. | `POST /transactions/{id}/flag` |
| AML_ADMIN (High Privilege) | Unfreeze, Approve, and execute settlement. | `POST /transactions/{id}/approve` |

### 3.2 The Critical State Transition (The Race Condition Window)
The system mandates the following security-critical sequence for high-risk transactions:
RISK DETECTED: AML Risk Engine sets `STATUS: FLAGGED` and `IS_FROZEN: FALSE`.
FREEZE COMMAND (ToC): AML Sentinel Gateway receives the freezing request. It reads the current status.
FREEZE COMMAND (ToU): The transaction record is updated to `IS_FROZEN: TRUE`.
The vulnerability exploits the short, critical gap between the AML Risk Engine detecting the risk and the database writing the `IS_FROZEN: TRUE` flag. A low-privilege user can concurrently execute a high-privilege `APPROVE` operation that only checks for the presence of the `IS_FROZEN: TRUE` flag during its execution.

## 4.0 Known System Debt & Theoretical Attack Surfaces
Internal Security Engineering Note: The performance team implemented asynchronous messaging for transaction freezing (using Kafka) to prevent the web service from blocking during high-volume periods. This refactoring was done without implementing a row-level database lock, creating the TOCTOU window. Tracked as RISK-AML-019.

### 4.1 Vulnerability A: TOCTOU Race Condition to Permanent Approval Bypass
**Taxonomy Pattern:** 8.1 (Race Condition / TOCTOU), 2.1 (Functional Pivot), & 8.5 (State Corruption)
**Sub-system:** AML Sentinel Gateway (`POST /api/v3/transactions/{id}/approve`)

**The Deep Architectural Flaw:**
This is a three-part critical failure involving concurrency, RBAC, and business logic trust.

1. **Functional Pivot (Pattern 2.1):** The RBAC logic on the `APPROVE` endpoint is incorrectly implemented. Instead of checking `IF user.role == AML_ADMIN`, it checks `IF user.role != TIER_1_SUPPORT AND IS_FROZEN == FALSE`. This faulty logic allows the low-privileged `COMPLIANCE_OFFICER` to attempt the high-privilege `APPROVE` operation, provided the transaction is not frozen.

2. **Race Condition (Pattern 8.1):** When a transaction is automatically flagged, the AML Sentinel Gateway spawns two threads: Thread A (Freezing Logic) and Thread B (Approval Check). The attacker (a Compliance Officer who is monitoring the flow) uses a concurrent request immediately upon seeing the transaction is $F L A G G E D$. The attacker's request (Thread B - Approval) hits the system just before the automated freezing request (Thread A) commits its database change.

3. **TOCTOU Gap:**
*   Time-of-Check (ToC) by Attacker: Attacker (Thread B) queries DB. Reads `IS_FROZEN: FALSE`. Proceeds to Approval.
*   Time-of-Use (ToU) by Attacker: Attacker's approval logic runs and commits `STATUS: APPROVED`.
*   The later-arriving AML Freeze (Thread A) then runs and attempts to set `IS_FROZEN: TRUE`, but the transaction status is now already `APPROVED`, which invalidates the freeze command, locking the transaction in an approved state.

**The Exploitation Path:**
1. **The Setup:** A $$ 500,000$ wire transfer is submitted and is instantly flagged by the AML Risk Engine. It is now `STATUS: FLAGGED`, `IS_FROZEN: FALSE`.
