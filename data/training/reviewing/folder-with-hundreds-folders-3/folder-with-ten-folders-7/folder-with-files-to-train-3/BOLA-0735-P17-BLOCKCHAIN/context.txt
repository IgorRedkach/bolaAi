# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** ChainVault DeFi API
**Document Version:** 2.6.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Blockchain / DeFi
**Architecture:** REST + Web3 + GraphQL indexer
**Training Example ID:** BOLA-0735

## 1.0 Executive Summary
ChainVault DeFi API is a blockchain / defi platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v3/objects endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 1.7 — Nested resources without parent authorization

## 3.0 Database Schema
```sql

-- Object table
CREATE TABLE objects (
    object_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_object_tenant ON objects(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 1.7 — Nested resources without parent authorization (BOLA)

The `GET/PATCH/DELETE /api/v3/objects/:id` endpoint accepts a `object_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-D97D` can access objects owned by `ORG-11D9`.

_Specific exploitation for Pattern 1.7:_ Nested endpoint `/api/v3/objects/:id/children/:childId` validates child exists but not that parent belongs to the caller.
