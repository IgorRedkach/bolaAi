# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** PowerGrid Customer Billing API
**Document Version:** 4.9.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Energy / Utilities / Smart Grid
**Architecture:** REST + GraphQL + SCADA bridge
**Training Example ID:** BOLA-0814

## 1.0 Executive Summary
PowerGrid Customer Billing API is a energy / utilities / smart grid platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v1/assets endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 5.2 — Resolver/graph traversal injection

## 3.0 Database Schema
```sql

-- Asset table
CREATE TABLE assets (
    asset_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_asset_tenant ON assets(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 5.2 — Resolver/graph traversal injection (Injection)

The `GET/PATCH/DELETE /api/v1/assets/:id` endpoint accepts a `asset_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-7AC7` can access objects owned by `ORG-7DFA`.

_Specific exploitation for Pattern 5.2:_ The `/api/v1/assets` handler does not enforce tenant/owner boundaries for Pattern 5.2.
