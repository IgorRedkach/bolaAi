# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** MetroPulse Traffic Orchestration
**Document Version:** 3.9.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Smart City / Traffic Management
**Architecture:** IoT edge + MQTT + GraphQL command plane
**Training Example ID:** BOLA-0854

## 1.0 Executive Summary
MetroPulse Traffic Orchestration is a smart city / traffic management platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v2/nodes endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 2.1 — Functional pivot (vertical/horizontal)

## 3.0 Database Schema
```sql

-- Node table
CREATE TABLE nodes (
    node_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_node_tenant ON nodes(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 2.1 — Functional pivot (vertical/horizontal) (BAC)

The `GET/PATCH/DELETE /api/v2/nodes/:id` endpoint accepts a `node_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-5B3C` can access objects owned by `ORG-3E59`.

_Specific exploitation for Pattern 2.1:_ User with `role=user` calls `GET /admin/nodes` — vertical escalation to admin endpoint.
