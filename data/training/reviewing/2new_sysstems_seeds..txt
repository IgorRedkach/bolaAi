# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** FinFlow Corporate Payment Gateway
**Document Version:** 4.4.0 (FINAL)
**Classification:** CRITICAL FINANCIAL / PCI-DSS / SOX COMPLIANCE SCOPE
**Domain:** Financial Services / B2B Payments / Wire Transfers

## 1.0 Executive Summary
FinFlow is a multi-tenant payment platform used by hundreds of corporations to manage their high-value treasury operations. It handles bulk payroll, vendor payments, and international wire transfers. Due to regulatory requirements (e.g., Sarbanes-Oxley/SOX), all high-value transactions require a minimum of two authorized signatories from the same corporation to approve the payment before it is released to the SWIFT network.

The platform relies on strict logical isolation: an employee from "Tenant A" must never be able to view or manipulate a payment belonging to "Tenant B."

## 2.0 Comprehensive Network Topology & Workflow
The architecture prioritizes data integrity and transactional isolation.

### 2.1 The Ingress Layer & API Gateway
* **Edge WAF:** Fronts the API, blocking common web attacks.
* **API Gateway (Node.js):** Handles all routing. It validates the OAuth 2.0 JWT and extracts the user's `tenant_id` from the token.

### 2.2 The Backend Core Services
* **Transaction Service (Java Spring):** The core engine managing the payment state machine (`DRAFT` -> `PENDING_APPROVAL` -> `APPROVED` -> `DISPATCHED`).
* **PostgreSQL Database:** The immutable ledger, where every payment record includes a mandatory `tenant_id` foreign key.

## 3.0 Identity, Access, and Approval Workflow
Security is based on multi-party authorization and tenant-scoped tokens.

### 3.1 Corporate Identity (OAuth 2.0)
Users authenticate via corporate SSO, and the JWT issued contains two critical claims: the user's ID (`sub`) and their corporate ID (`tenant_id`).

### 3.2 The Two-Step Approval Logic (The Bypass Target)
To execute a payment, the system requires two state transitions, both tied to the user's `tenant_id` and `role`:
Initiation: A user with role `PAYMENT_INITIATOR` creates the payment. State = `PENDING_APPROVAL`.
Approval: A user with role `PAYMENT_SIGNATORY` must call the approval endpoint. This is the critical step that is bypassed.
## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The core Spring service recently introduced a fast-track approval endpoint for small value payments that skipped some internal audit checks, assuming the API Gateway upstream was enforcing all BOLA/BAC rules. Tracked as RISK-FIN-044.*

### 4.1 Vulnerability A: Cross-Tenant BOLA on Payment ID & Workflow Decoupling
**Taxonomy Pattern:** 1.5 (Multi-tenant access) & 3.2 (Workflow decoupling)
**Sub-system:** Transaction Service (`PATCH /api/v4/payments/{payment_id}/approve`)

**The Deep Architectural Flaw:**
This attack chains a lack of multi-tenant BOLA enforcement with a state machine logic flaw.

1. Cross-Tenant BOLA (Pattern 1.5): The approval endpoint URL dictates the target payment (`/payments/PID-10045/`). The upstream API Gateway enforces that the token is valid, but the core Java service **completely fails to re-validate that the payment's internal `tenant_id` matches the JWT's `tenant_id`*. It blindly trusts the presence of a valid token.

2. Workflow Decoupling (Pattern 3.2): The approval endpoint forces the state transition from `PENDING_APPROVAL` to `APPROVED`. Because the attacker forces this state transition with a single API call, they successfully circumvent the business requirement for a two-user, multi-signature approval workflow.

**The Exploitation Path:**
The Setup: An attacker, working for Corporation A (`tenant_id: "CORP_A"`), creates a valid JWT.
Reconnaissance: The attacker obtains a target payment ID belonging to Corporation B (`tenant_id: "CORP_B"`) from a publicly visible log or a database leak (e.g., `PID-99201`, a $50M wire transfer).
The BOLA Attack: The attacker issues a `PATCH` request using their CORP_A token, but substitutes the target ID in the URL: `PATCH /api/v4/payments/PID-99201/approve`.
The Execution: The Java Transaction Service receives the request. It verifies the token signature (valid), but ignores the tenant ID mismatch. It executes the update: `UPDATE payments SET status = 'APPROVED' WHERE payment_id = 'PID-99201'`.
The Impact: The attacker, a low-level employee at Corporation A, has successfully and unilaterally approved a $50 million wire transfer from Corporation B's bank account, breaching strict SOX compliance and causing catastrophic financial loss.

### 6.1 Vulnerable Payment Approval Controller
```java

        return ResponseEntity.status(404).body("Payment not found.");

    // The code FAILS to enforce the boundary: 
    // if (!targetPayment.getTenantId().equals(callingTenantId)) { throw 403 }
```

# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** FirstResponse CAD Integration API
**Document Version:** 4.0.1 (FINAL)
**Classification:** CRITICAL PUBLIC SAFETY / CJIS COMPLIANCE SCOPE
**Domain:** Government / Emergency Services (911/E911) / Computer-Aided Dispatch (CAD)

## 1.0 Executive Summary
FirstResponse is the primary API for a next-generation Computer-Aided Dispatch (CAD) system, used by police, fire, and EMS agencies to create, update, and manage active emergency incidents. The API accepts authenticated requests from internal systems (e.g., automated crash detection sensors, smart street infrastructure, 911 call-takers) to instantly generate a dispatch event. Due to the life-critical nature of the system, the API is fronted by an authorization service that must achieve 99.999% reliability.

## 2.0 Comprehensive Network Topology & Workflow
The architecture prioritizes speed and redundancy, which, ironically, creates a security vulnerability during component failure.

### 2.1 The Ingress Layer & API Gateway
* **Edge WAF:** Fronts the API, blocking common volumetric attacks.
* **API Gateway (Node.js):** Handles routing and basic rate limiting. It calls the remote AuthZ Service for all requests.

### 2.2 The Backend Core Services
* **AuthZ Service (Python Django):** A standalone microservice responsible for token validation and user role checks. It relies on a low-latency database for session lookups.
* **Dispatch Service (Go-lang):** The core engine that validates and commits a new emergency incident record to the CAD database.
* **Audit Log Service (Rust):** An asynchronous service that receives critical action events (e.g., "incident created," "status changed") and writes them to a write-only immutable ledger.

## 3.0 Identity, Access, and Redundancy Logic
Authorization for incident creation is strictly reserved for authenticated dispatchers and trusted automated systems.

### 3.1 Authentication Workflow (The Failure Point)
When the API Gateway receives a request, it calls the remote AuthZ Service. The configuration dictates that if the AuthZ Service fails to return a response within 500ms, the API Gateway should assume the request is valid and allow it to proceed, prioritizing life safety over security enforcement.

### 3.2 Dispatch Integrity
All dispatch events committed to the database must contain the `source_user_id` for forensic accountability (CJIS compliance). The Dispatch Service relies on the AuthZ Service to supply this ID.

## 4.0 Known System Debt & Theoretical Attack Surfaces
*Internal Security Engineering Note: The AuthZ Service is currently being migrated to a new cloud region, causing transient network latency spikes of up to 700ms during peak load. The Dispatch Service has a known bug (BUG-LOG-004) where if the AuthZ Service fails to return a user ID, the Dispatch Service inserts a NULL/empty string, bypassing the Audit Log Service's validation rules.*

### 4.1 Vulnerability A: Fail-Open on Timeout & Insufficient Audit Logging
**Taxonomy Pattern:** 8.2 (Fail-Open on Timeout) & 7.3 (Insufficient Logging of Critical Actions)
**Sub-system:** API Gateway & Dispatch Service (`POST /api/v4/incidents/create`)

**The Deep Architectural Flaw:**
This attack chains a safety-critical design choice (Fail-Open) with a downstream forensic logging failure.

1. **Fail-Open on Timeout (Pattern 8.2): ** The API Gateway is configured with a 500ms timeout for the remote AuthZ service call. If the AuthZ service is under high load or experiences a temporary network partition, the API Gateway receives a 504 Gateway Timeout from the upstream load balancer. The Gateway's logic interprets this failure as "allow the request to proceed to save lives," failing open and allowing the request to continue *without* an authenticated user context.

2. **Insufficient Logging (Pattern 7.3): ** Since the request bypassed the AuthZ service, the user context (`source_user_id`) is missing. The Go-lang Dispatch Service inserts the incident record with a NULL `source_user_id`. The Rust Audit Log Service, which is only configured to log incidents where `source_user_id` is *not* NULL, silently ignores the transaction, creating an unlogged, unaccountable emergency event.

**The Exploitation Path:**

1. **The Setup:** An attacker prepares a malicious payload (e.g., a high-priority "Active Shooter" dispatch event at a target location).
2. **The Network Stress:** The attacker attempts to trigger the network latency window (e.g., by simultaneously sending 100 junk requests to the already stressed AuthZ Service's `/healthcheck` endpoint).
3. **The Fail-Open:** While the AuthZ service is temporarily timing out, the attacker sends their unauthenticated `POST /api/v4/incidents/create` request.
4. **The Execution:** The API Gateway allows the request to pass unauthenticated (Pattern 8.2). The Dispatch Service creates the high-priority incident with a NULL source user ID.
5. **The Impact:** Emergency services are dispatched to a false incident (a "swatting" attack). Because the `source_user_id` was NULL, the Audit Log Service silently fails to record the incident creation, leaving no forensic trace of the attacker's network origin, method, or intent (Pattern 7.3).

### 6.1 Vulnerable API Gateway Logic (Node.js)
The core logic defines the fail-open condition based on the upstream response code.

```javascript

const axios = require('axios');
const AUTHZ_SERVICE_URL = 'http://authz-svc.internal:8080/validate';

// VULNERABILITY 8.2: Fail-Open on Timeout/Failure
async function enforceAuthentication(req, res, next) {
const token = req.headers.authorization?.split(' ')[1];
// Default context if AuthZ fails  
req.userContext = { authenticated: false, userId: null, roles: [] };  

try {  
    // Axios call with a hard 500ms timeout  
    const authzResponse = await axios.post(AUTHZ\_SERVICE\_URL, { token }, { timeout: 500 });  
    
    if (authzResponse.status === 200 && authzResponse.data.isValid) {  
        // Success: Apply authenticated user context  
        req.userContext.authenticated = true;  
        req.userContext.userId = authzResponse.data.userId; // e.g., 'dispatch_a812'  
    }  
    
} catch (error) {  
    // If it's a network timeout or a 5xx error, it defaults to 'allow'  
    console.warn(\`AuthZ Service Failed to Respond (Error: ${error.code}). Failing Open.\`);  
    // The unauthenticated/null userContext is carried forward, allowing the request.  
}  

// Crucial safety check (designed to fail)  
if (!req.userContext.authenticated) {  
    // BUG: Developer decided not to block unauthenticated access here   
    // to prioritize availability during an AuthZ outage (Fail-Open policy).  
    // The unauthenticated request proceeds with req.userContext.userId = null.  
}  

next(); 
}
```

## 1.0 Executive Summary
ManuControl manages the API bridge between the corporate IT network (where scheduling and dashboard applications reside) and the Operational Technology (OT) network (where the physical robots, PLCs, and sensors operate). ## 2.0 Comprehensive Network Topology & Control Plane
The architecture implements a classic IT/OT segregation, with the flaw existing in the DMZ bridge.

### 2.1 The IT Network Boundary
* **Corporate Firewall:** Separates the standard office environment (laptops, phones) from the manufacturing DMZ.
* **Kubernetes Ingress (The Flaw):** The internal-facing Kubernetes cluster uses an Ingress Controller that was misconfigured to expose a high-privilege service to the entire corporate network instead of restricting it to internal IT-only CIDR blocks.

### 3.2 Modbus Protocol Mapping
To control the physical speed of the robotic arm, the PLC expects a single, 16-bit integer value written to a specific Modbus Register Address (`40001`).
*   **Register 40001:** Velocity (0 = stopped, 1000 = normal max speed).

### 4.1 Vulnerability A: Exposed Critical Interface & Modbus Injection
**Taxonomy Pattern:** 2.5 (Critical Infrastructure interface exposure) & 5.4 (Industrial protocol injection)
**Sub-system:** PLC Control Service (`PUT /api/v1/robotics/command/set_velocity?device_id={id}&velocity={val}`)

**The Deep Architectural Flaw:**
This attack chains a network misconfiguration with a core data integrity failure.

1.  **Critical Infrastructure Exposure (Pattern 2.5):** The Kubernetes Ingress Rule for the `PLC Control Service` was set to `host: ` and `path: /api/v1/robotics/`, accidentally exposing the control API to the entire internal corporate network. Because the service lacks authentication, any laptop connected to the corporate WiFi can reach the PLC control API bridge.

2.  **Industrial Protocol Injection (Pattern 5.4):** The Java controller blindly accepts the `velocity` query parameter. It converts the input (e.g., "5000") to an integer and embeds it directly into the binary Modbus packet destined for the physical PLC's register `40001`. The code fails to enforce a maximum bound (like `velocity <= 1500`) on the input, resulting in an injection of a physically dangerous command.

**The Exploitation Path:**

1.  **Reconnaissance:** An attacker gains access to the corporate visitor WiFi. They use basic network scanning tools to discover the internal Kubernetes IP address (`10.1.1.50`) and the unauthenticated `/set_velocity` endpoint.
2.  **Targeting:** The attacker identifies a high-power robotic arm (Device ID: `ARM-99182A`) on the factory floor.
3.  **The Injection:** The attacker crafts a request to set the speed far above the safe limit: `PUT /api/v1/robotics/command/set_velocity?device_id=ARM-99182A&velocity=5000`.
4.  **The Execution:** The unauthenticated request passes the exposed Ingress Controller. The Java service accepts the `velocity=5000`, converts it to the Modbus payload, and sends the dangerous command to the physical PLC.
5.  **The Impact:** The robotic arm attempts to execute the command at five times its designed maximum safe velocity, resulting in immediate physical equipment failure and a catastrophic safety incident on the factory floor (Pattern 5.4).

## 1.0 Executive Summary
CreditDecision is a private API used by banks and auto lenders to fetch pre-approval credit scores and eligibility checks instantly. The system integrates with major credit bureaus (Equifax, TransUnion, Experian) but caches the resulting scores and pre-qualifications for 30 days to avoid unnecessary bureau inquiries and associated costs.

The API is transactional: an application must first submit a full, verified consumer profile (name, SSN, address). * **Profile Submission Service (Node.js):** Receives the full consumer profile and generates the short-lived request_id in the database.

### 2.2 The Internal Service Mesh (The Flaw)
* **Credit Fetcher Service (Python):** An isolated microservice that takes the request_id, looks up the consumer's profile, executes the synchronous call to the external credit bureau API, saves the score, and updates the profile status to READY. This call takes 500ms-1200ms.

## 3.0 Identity, Context, and Transaction Scope

### 3.1 Authorization Scope (The Context)

This notification is done via an internal Kafka event, but the event structure only includes the request_id and the final score, omitting the original partner_id context. This context is meant to be re-read from the database, but a concurrency gap prevents this.

## 4.0 Known System Debt & Theoretical Attack Surfaces

4. **The Impact:** The GraphQL server crashes or becomes unresponsive. The single HTTP request causes a DoS for all users within the entire multi-tenant cluster.

# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** DataFeed Public GraphQL API
**Document Version:** 7.1.1 (FINAL)
**Classification:** CONFIDENTIAL / GDPR PII SCOPE
**Domain:** Social Media / Content Publishing / User Profiles

## 1.0 Executive Summary
DataFeed is a platform for publishing long-form content, organized into user-owned "Feeds." The core API must serve millions of public reads per second while rigorously protecting private user metadata. The platform utilizes a single, public GraphQL endpoint to optimize client-side data fetching.

The design relies on a multi-layered resolver structure: the root resolver handles the initial Post object retrieval (which is public), and subsequent nested field resolvers (like Post.ipAddress or Post.deviceType) must enforce granular authorization based on the requesting user's role (e.g., ADMIN, MODERATOR, or PUBLIC). The failure to apply this logic at the field level is the core architectural flaw.

## 2.0 Comprehensive Network Topology & Graph Architecture
The architecture is read-heavy and distributed across a global CDN.

### 2.1 The GraphQL Ingress
**Edge Ingress:** All traffic hits the /graphql endpoint, fronted by a Cloudflare CDN for caching public query results.
**Primary Router:** An Apollo Router routes queries to two core backend subgraphs.
### 2.2 The Backend Subgraphs
**Content Subgraph (Rust/Tonic):** Handles the main Post type, fetching its title, body, and publicly available data.
**Metadata Subgraph (Node.js/Prisma):** Handles sensitive fields like Post.author details and, crucially, the Post.metadata object. This subgraph performs a single, broad SELECT * against the underlying database for performance, assuming the upstream resolver will handle masking.
## 3.0 Identity, JWT, and Field-Level Authorization
Authentication is optional for most public queries but required for mutations and viewing private profiles.

### 3.1 Authorization Flow
Users are classified into three roles: PUBLIC (unauthenticated or standard user), AUTHOR (user viewing their own content), and ADMIN.
The JWT contains the user's user_id and their role.
The Field-Level Flaw: The Metadata Subgraph's resolver for Post.metadata retrieves all associated sensitive data from the database using a single call, then relies on conditional logic within the resolver to check the user's role before returning the data. The developer forgot to add this conditional check to two highly sensitive fields.
## 4.0 Known System Debt & Theoretical Attack Surfaces
Internal Security Engineering Note: The Metadata Subgraph relies on a broad SELECT * from a denormalized PII table for performance reasons. This pattern creates a high risk of sensitive field exposure if masking logic fails. Tracked as RISK-DF-301.

### 4.1 Vulnerability A: Excessive Data Exposure via Field-Level BOLA Bypass
**Taxonomy Pattern:** 3.1 (Excessive Data Exposure) & Field-Level BOLA Bypass
**Sub-system:** Metadata Subgraph Resolver (Post.metadata.ipAddress and Post.metadata.deviceType)

**The Deep Architectural Flaw:**
The flaw is a failure of granular, field-level access control (a form of BOLA on data attributes, not objects). The Metadata Subgraph's resolver over-fetches the data and then fails to mask two specific fields based on the requesting user's low PUBLIC role.
**Broad Fetching:** The Post resolver correctly finds a public post (e.g., post(id: 10001)). It then delegates the metadata field to the Metadata Subgraph. The Node.js service performs db.postMetadata.findUnique({ where: { postId } }), which executes a SELECT * equivalent. The database returns all PII, including ip_address and device_type.
**Missing Masking (Pattern 3.1):** The resolver logic contains a switch(user.role) block, but the implementation for two critical fields was incomplete. The resolver returns the full, unfiltered database row to the Apollo Router, which then passes the requested fields to the client.
**The Exploitation Path:**
An attacker (User A) authenticates as a standard PUBLIC user (or remains unauthenticated).
The attacker identifies a high-profile public post ID, P-10001. They know this post belongs to a high-value victim.
The attacker crafts a malicious query that includes both publicly visible fields (e.g., likes) and the two non-masked, highly sensitive metadata fields.
The Strike: The attacker executes the query:
query DataLeak {
  post(id: "P-10001") {
    title
    likes
    metadata {
      ipAddress # VULNERABLE FIELD
      deviceType # VULNERABLE FIELD
      lastModified
    }
  }
}
**The Cascade:** The query executes successfully with a 200 OK. The resolver, due to the missing role check on these specific attributes, returns the victim author's creation IP address and device fingerprint, enabling targeted phishing or identity tracking.

## 6.0 The Flawed Implementation (Node.js Resolver)
The vulnerability is a direct failure of field-level authorization within the PostMetadata type's resolver, which incorrectly assumes a field is safe to return if the user has a valid session.

### 6.1 Vulnerable Metadata Field Resolver
// File: metadataSubgraph/resolvers.js

// This resolver fetches the full PII row and attempts to mask fields dynamically.
const PostMetadataResolver = {
  
    // Resolver for the PostMetadata.ipAddress field
    ipAddress: (parent, args, context) => {
        // parent is the full row fetched from the database by the parent resolver
        
        // VULNERABILITY 3.1 & Field-Level BOLA Bypass: Missing Role Check
        // Correct implementation should be:
        // if (context.user.role === 'ADMIN' || context.user.role === 'MODERATOR') {
        //    return parent.created_at_ip_address;
        // }
        // return null; // Mask the field for public/standard users
        
        // FLAW: Returns the raw database field regardless of user role
        return parent.created_at_ip_address; 
    },
    
    // Resolver for the PostMetadata.deviceType field
    deviceType: (parent, args, context) => {
        // VULNERABILITY: This is a copy-paste error from ipAddress resolver.
        return parent.device_type;
    },

    // Resolver for the PostMetadata.moderatorNotes field (This one is correctly masked)
    moderatorNotes: (parent, args, context) => {
        if (context.user.role === 'ADMIN') {
            return parent.moderator_notes;
        }
        return null;
    },
    
    // ... other resolvers ...
};

module.exports = PostMetadataResolver;
