# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** ClaimsFlow Underwriting API
**Document Version:** 4.0.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Insurance / Claims Processing
**Architecture:** SOAP + REST + GraphQL facade
**Training Example ID:** BOLA-5511

## 1.0 Executive Summary
ClaimsFlow Underwriting API is a insurance / claims processing platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v2/entitys endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 9.5 — Smart Cities and IoT Networks

## 3.0 Database Schema
```sql

-- Entity table
CREATE TABLE entitys (
    entity_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_entity_tenant ON entitys(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 9.5 — Smart Cities and IoT Networks (Platform)

The `GET/PATCH/DELETE /api/v2/entitys/:id` endpoint accepts a `entity_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-68A1` can access objects owned by `ORG-DBA0`.

_Specific exploitation for Pattern 9.5:_ The `/api/v2/entitys` handler does not enforce tenant/owner boundaries for Pattern 9.5.
