# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** GrantFlow CRM API
**Document Version:** 5.9.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Non-Profit / Grant Management
**Architecture:** REST + Salesforce + GraphQL
**Training Example ID:** BOLA-5726

## 1.0 Executive Summary
GrantFlow CRM API is a non-profit / grant management platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v1/records endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 4.5 — Firmware update without signature validation

## 3.0 Database Schema
```sql

-- Record table
CREATE TABLE records (
    record_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_record_tenant ON records(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 4.5 — Firmware update without signature validation (Integrity)

The `GET/PATCH/DELETE /api/v1/records/:id` endpoint accepts a `record_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-BE3C` can access objects owned by `ORG-F518`.

_Specific exploitation for Pattern 4.5:_ The `/api/v1/records` handler does not enforce tenant/owner boundaries for Pattern 4.5.
