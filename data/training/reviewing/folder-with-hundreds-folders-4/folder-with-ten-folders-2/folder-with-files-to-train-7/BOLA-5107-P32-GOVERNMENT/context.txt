# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** FirstResponse CAD Integration
**Document Version:** 1.6.0 (FINAL)
**Classification:** SENSITIVE
**Domain:** Government / Public Safety
**Architecture:** REST + NIEM XML + GraphQL dispatch
**Training Example ID:** BOLA-5107

## 1.0 Executive Summary
FirstResponse CAD Integration is a government / public safety platform with a REST API. Resources are partitioned
by `tenant_id` and ownership is tracked via `owner_id`. The API uses JWT authentication
where the token encodes `sub` (user ID) and `tenant_id`.

## 2.0 Architecture
- **API:** REST (/api/v1/items endpoints)
- **Auth:** OAuth2 JWT with `sub` and `tenant_id` claims
- **Database:** PostgreSQL with logical tenant partitioning
- **Pattern under test:** 3.2 — Workflow decoupling

## 3.0 Database Schema
```sql

-- Item table
CREATE TABLE items (
    item_id    VARCHAR(50) PRIMARY KEY,
    owner_id         VARCHAR(50) NOT NULL REFERENCES users(user_id),
    tenant_id        VARCHAR(50) NOT NULL,
    status           VARCHAR(20) DEFAULT 'active',
    sensitive_data   TEXT,
    created_at       TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_item_tenant ON items(tenant_id);
-- NOTE: Application code does NOT use tenant_id in authorization checks

```

## 4.0 Vulnerability Context
**Pattern:** 3.2 — Workflow decoupling (Insecure Design)

The `GET/PATCH/DELETE /api/v1/items/:id` endpoint accepts a `item_id` in the URL path.
The backend handler queries the database by ID only, without filtering by `owner_id` or `tenant_id`.
An authenticated user from `ORG-0E19` can access objects owned by `ORG-9153`.

_Specific exploitation for Pattern 3.2:_ Multi-step workflow: `POST /api/v1/items/:id/submit` succeeds without completing the prior `/validate` step.
