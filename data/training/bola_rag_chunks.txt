# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** AetherDrive V2X Telematics Platform
**Document Version:** 5.1.2 (FINAL)
**Classification:** CRITICAL SAFETY / NHTSA COMPLIANCE SCOPE
**Domain:** Automotive / Connected Car (V2X) / Over-The-Air (OTA) Updates

## 1.0 Executive Summary
The AetherDrive platform is a global, hyperscale IoT and API ecosystem designed to support a fleet of over 4 million connected electric and semi-autonomous vehicles. The platform handles everything from real-time battery telemetry and remote climate control to critical Over-The-Air (OTA) firmware updates for the vehicle's electronic control units (ECUs), such as the braking module, advanced driver-assistance systems (ADAS), and the central infotainment console.

Because physical safety is paramount, the architecture must bridge highly volatile cellular networks (4G LTE/5G) with rigidly secured role-boundarykend microservices. The core interface point in the vehicle is the Telematics Control Unit (TCU), an embedded Linux computer featuring a dedicated cellular modem and a Hardware Security Module (HSM) for cryptographic operations. This TCU acts as the gateway between the cloud and the vehicle's internal CAN bus (Controller Area Network).

## 2.0 Comprehensive Network Topology & Ingress Routing
The platform operates across three distinct network planes to segregate high-volume telemetry from critical command-and-control operations.

### 2.1 The IoT Telemetry Plane (Vehicle-to-Cloud)
* **Private Cellular APN:** Vehicles do not connect to the public internet directly. They route through a dedicated private Access Point Name (APN) provided by tier-1 telecom partners, entering the AWS cloud environment via an IPSec Transit Gateway.
* **AWS IoT Core (MQTT Broker):** High-frequency, low-latency telemetry (GPS coordinates, wheel speed, battery state of charge) is published over MQTT using TLS 1.2. The broker routes these messages into Amazon Kinesis data streams for real-time analytics and predictive maintenance algorithms.

### 2.2 The Command & Control API Plane (App-to-Cloud)
* **Edge Ingress:** The consumer mobile "Companion App" (iOS/Android) connects to an external-facing API Gateway fronted by a Web Application Firewall (WAF).
* **Service Mesh (gRPC):** Internal microservices are written in Rust and Go, communicating over a strictly authenticated gRPC service mesh (Linkerd). 
* **The Command Queue:** When a user clicks "Unlock Doors" on their app, the API Gateway translates the REST request into a gRPC call, which places a signed command onto an Apache Kafka topic. The "Device Shadow" service then pushes this command down the MQTT tunnel to the specific vehicle's TCU.

### 2.3 The OTA Update Pipeline (Cloud-to-Vehicle)
* **Campaign Manager Service:** Responsible for orchestrating massive firmware rollouts. It handles delta-compression of binary files, staggered regional deployments, and rollrole-boundaryk logic if a vehicle reports a failed flash.
* **Signed Blob Storage:** Firmware binaries are heavily encrypted and digitally signed by the OEM's root offline CA. They are stored in an Amazon S3 bucket with strict Cross-Origin Resource Sharing (CORS) and signed-URL access policies.

## 3.0 Identity, Cryptography, and PKI Authorization
Security relies on a dual-authentication model: one for the human, one for the machine.

### 3.1 Vehicle Authentication (mTLS & Hardware Root of Trust)
Every vehicle is provisioned at the factory with a unique X.509 certificate permanently burned into its HSM. 
* When the TCU connects to the MQTT broker or requests a firmware download, it must use mutual TLS (mTLS). 
* The cloud verifies the certificate against the OEM Certificate Authority, ensuring that even if an attacker spoofs a VIN, they cannot establish a connection without the physical silicon chip.

### 3.2 Owner Authentication (OAuth2 & B2C Identity)
Vehicle owners authenticate to the mobile app via Okta Customer Identity Cloud (Auth0).
* They receive an OAuth 2.0 JWT.
* **The Binding Record:** A critical PostgreSQL database table (`vehicle_ownership`) maps a user's unique `account_id` to the physical `VIN` (Vehicle Identification Number) of the car they purchased.

**Sub-system:** OTA Campaign Service (`/api/v3/vehicles/{vin}/ota/push`)

**Implementation behavior:**
To support the new "Custom Tuning" feature, developers created a new REST endpoint allowing the mobile app to trigger a lightweight, on-demand OTA configuration update. 
1.  **The authorization-boundary Flaw (Pattern 1.2):** The endpoint URL dictates the target vehicle (`/vehicles/WBA00000000123456/`). The Go-based microservice verifies that the user's JWT is valid and active. However, it completely fails to query the `vehicle_ownership` PostgreSQL table. It blindly assumes that if you are an authenticated user, you are allowed to push configurations to the VIN specified in the URL path.
2.  **The OTA Validation Flaw (Pattern 3.4):** Typically, firmware is pulled from the highly secure, OEM-signed S3 bucket. However, this specific "Custom Tuning" endpoint was designed to allow users to upload their own JSON configuration profiles. The API payload accepts an arbitrary `manifest_url` parameter. The cloud service takes this URL and forwards it directly to the vehicle's TCU. The TCU, assuming any command coming from the trusted cloud MQTT tunnel is legitimate, downloads the payload from the provided URL and executes the configuration change in memory *without verifying a cryptographic signature*.

1.  An attacker registers a legitimate account on the AetherDrive platform and buys the cheapest used vehicle available to gain a valid owner JWT.
2.  The attacker targets a victim's vehicle (e.g., a high-profile target or a fleet of delivery trucks). VINs are publicly visible through the windshield. Let's assume the victim's VIN is `1G1RC6E45FU111111`.
3.  The attacker hosts a malicious configuration payload on their own server (`https://attacker.com/malicious_tune.json`). This payload contains instructions that will cause the TCU to drop its firewall and open a reverse shell over the cellular network.
4.  The attacker intercepts their mobile app traffic and issues a `POST` request to the ALTERNATE API: `POST /api/v3/vehicles/1G1RC6E45FU111111/ota/push`, including the `manifest_url` pointing to their malicious server.
5.  **The Cascade:** The API fails the authorization-boundary check, accepts the command, and pushes it down the MQTT tunnel to the victim's car. The car's TCU downloads the payload from `attacker.com`, bypasses signature checks (because the config pipeline wasn't designed for signed binaries), and executes it. The attacker now has remote code execution on a moving vehicle.

## 1.0 Executive Summary
AquaGrid is a multi-tenant, cloud-native Advanced Metering Infrastructure (AMI) platform used by over 150 local municipalities and county water districts across North America. The platform replaces manual water meter reading by deploying IoT-enabled "Smart Meters" to residential and commercial properties. 

These smart meters report hourly water consumption data via a Low-Power Wide-Area Network (LPWAN) such as LoRaWAN or NB-IoT. The AquaGrid platform aggregates this data for automated billing, detects residential pipe leaks, and critically, provides municipalities with the ability to remotely actuate physical shut-off valves at the meter (e.g., for non-payment or emergency main breaks) via a centralized GraphQL API.

## 2.0 Comprehensive Network Topology & IoT Edge
The architecture bridges low-power physical IoT endpoints with a high-availability multi-tenant cloud.

### 2.1 The Physical IoT Edge (Meters & Concentrators)
* **Smart Endpoints:** Battery-powered ultrasonic water meters with embedded LoRaWAN radios and motorized ball valves for remote shut-off.
* **Neighborhood Concentrators:** Pole-mounted gateways that aggregate LoRaWAN packets from thousands of local meters and backhaul the traffic to the AWS cloud via 5G cellular connections.

### 2.2 The Cloud Ingress & API Router
* **GraphQL Federation:** The core web interface for municipal administrators operates on a modern Apollo GraphQL Supergraph. It stitches together multiple underlying microservices (Billing, Telemetry, and Device Control).
* **Ingress Firewall:** AWS WAF is configured to block standard SQLi/XSS, but relies on the underlying application logic for complex rate limiting and authorization.

### 2.3 The SCADA / Device Control Microservice
* **Valve Actuation Service:** A highly restricted Go-lang microservice responsible for translating GraphQL mutation requests (e.g., `setValveState(CLOSE)`) into proprietary binary payloads that are queued and pushed down to the physical neighborhood concentrators.

## 3.0 Multi-Tenant Identity and Access Management (IAM)
Because AquaGrid serves 150 different municipalities (each acting as an isolated tenant), identity boundary enforcement is the most critical security control in the platform.

### 3.1 Delegated Authentication (SAML 2.0 & OAuth2)
To accommodate the IT requirements of different city governments, AquaGrid supports "Bring Your Own Identity" (BYOI). 
* A city IT administrator can configure AquaGrid to trust their specific Microsoft Entra ID (Azure AD) or Okta tenant.
* When a municipal worker logs in, they are redirected to their city's login page. Upon success, the identity provider issues a JWT signed by the city's private key.
* The AquaGrid API Gateway validates the JWT signature using the public JWKS (JSON Web Key Set) endpoint registered for that specific municipality.

### 3.2 Tenant Isolation Logic
The GraphQL router extracts the `tenant_id` and `role` from the verified JWT. Every subsequent database query and device command must strictly enforce that the user is only interacting with meters belonging to their specific `tenant_id`.

*Internal Security Engineering Note: The recent GraphQL migration (Epic: GRPH-202) vastly improved frontend load times but introduced complex query depth and batching challenges that have not been fully modeled for denial-of-service implications. Tracked as RISK-CITY-019.*

**Sub-system:** GraphQL API Gateway & Auth Middleware (`/graphql`)

**Implementation behavior:**
This attack relies on a catastrophic failure in the SSO validation logic, amplified by a GraphQL-specific attack vector.
1.  **The SSO Issuer Flaw (Pattern 2.4):** The API Gateway validates that the incoming JWT is cryptographically signed. However, it blindly trusts the `iss` (Issuer) URL provided *inside the token header* to fetch the public verification key (JWKS), rather than strictly checking the issuer against a hardcoded whitelist of approved municipal tenants. This allows an attacker to spin up their own free Auth0 account, generate a valid JWT, and trick the AquaGrid gateway into validating it.
2.  **The GraphQL Alias Flaw (Pattern 5.3):** The `ValveActuation` subgraph allows administrators to remotely shut off a water meter. While the WAF limits users to 10 HTTP requests per minute to prevent mass-shutoffs, it does not inspect the GraphQL payload. An attacker can use GraphQL "Aliases" to pack thousands of distinct `setValveState` mutations into a *single* HTTP POST request. 

1.  **Forging the Identity:** The attacker creates a free developer account on Okta. They mint a JWT claiming the role `city_admin` and inject the target municipality's ID (`tenant_id: "city_of_chicago_01"`). Because of the Issuer Confusion flaw, the AquaGrid gateway downloads the attacker's public key, verifies the forged token, and grants the attacker full administrative rights over Chicago's water grid.
2.  **Bypassing Rate Limits via Batching:** The attacker wants to shut off water to an entire ZIP code. They know the WAF will block them if they send 5,000 separate HTTP requests. 
3.  **The Strike:** The attacker crafts a single GraphQL HTTP POST payload containing 5,000 aliased mutations (e.g., `cmd1: setValveState(meterId: "MTR-1", state: CLOSED)`, `cmd2: setValveState(meterId: "MTR-2", state: CLOSED)`, etc.).
4.  **The Cascade:** The gateway parses the single HTTP request (bypassing the WAF), accepts the forged token, and the GraphQL engine resolves all 5,000 mutations asynchronously. Within seconds, the command queue floods the LPWAN network, and 5,000 residential water valves physically rotate shut.

## 1.0 Executive Summary
MetroPulse is a municipal traffic orchestration platform deployed across 4,500 interconnected intersections. It ingests real-time telemetry from edge sensors (induction loops, pedestrian cameras, LiDAR) to optimize traffic light timing, reduce congestion, and prioritize emergency vehicle routing (EVR). 

The system bridges low-latency edge computing (MQTT) with a cloud-native command plane. Traffic flow and spatial relationships are mapped dynamically using a Neo4j Graph Database, allowing the system to calculate cascading congestion effects in real-time.

## 2.0 Network Topology & Edge Boundaries
The architecture is divided into the Physical Edge, the Ingress Broker, and the Cloud Command Plane.

### 2.1 The Physical Edge (Intersections)
* **Hardware:** Each intersection is controlled by a hardened Edge Node (NEMA TS2 compliant controller).
* **Communication:** Nodes communicate with the cloud over dedicated 5G APNs (Access Point Names) provided by a major telecom carrier, isolating the traffic from the public internet.
* **Protocol:** Devices publish state and subscribe to commands via MQTT over TLS 1.2.

### 2.2 Cloud Ingress (AWS IoT Core)
* **MQTT Broker:** AWS IoT Core acts as the centralized message broker. It handles millions of pub/sub messages per minute.
* **Stream Processing:** Inbound telemetry is pushed to Amazon Kinesis Data Streams for real-time aggregation before being written to the Graph Database.

### 2.3 Cloud Command Plane & Web Portal
* **Microservices:** Kubernetes (EKS) cluster running Go microservices for traffic logic and Node.js for the GraphQL/REST API Backend-for-Frontend (BFF).
* **Graph Database:** A Neo4j Enterprise cluster models the physical city grid. Nodes represent intersections; Edges represent road segments with weights based on current congestion.
* **Human-Machine Interface (HMI):** A React-based web dashboard used by municipal traffic engineers at the Department of Transportation (DoT) control center.

## 3.0 Identity, Tenancy, and Authorization
Authorization is physically divided by municipal "Districts" (e.g., North District, South District).

### 3.1 Edge Node Identity (mTLS)
Every physical traffic controller is provisioned with an X.509 certificate linked to its unique hardware serial number (e.g., `node-hw-8819a`). AWS IoT Core strictly authenticates connections using Mutual TLS (mTLS).

### 3.2 Operator Identity (OAuth2 / OIDC)

* **Federation Router:** An Apollo Router written in Rust handles the execution of incoming GraphQL queries. 
* **Subgraphs:** The router delegates queries to dedicated microservices (Go and Java) running in Amazon EKS:
  * `Project-Subgraph`: Manages broad project structures (e.g., "Project F-X").

## 6.0 AWS GovCloud S3 Document Flow (The Impact)

### 6.1 Presigned URL Generation
AegisForge does not proxy heavy file downloads through the GraphQL router. Instead, it uses the **Valet Key Pattern**:
1. When a GraphQL query requests the `s3_download_url` field on a `Blueprint` object, the `Document-Subgraph` is invoked.

The `Document-Subgraph` **implicitly trusts** the upstream subgraphs. It assumes that if a user has successfully navigated the graph to request a `Blueprint`, the parent `Component` resolver has already verified the publication state and access rights.

# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** VitaStream Telehealth Data Lake
**Document Version:** 2.4.1 (FINAL)
**Classification:** HIPAA SENSITIVE / EPHI (Electronic Protected Health Information)
**Domain:** Healthcare / Telemedicine / Clinical Aggregation

## 1.0 Executive Summary
VitaStream is a high-performance clinical aggregation platform used by telehealth physicians. Because assembling a patient's complete medical history (labs, imaging reports, past encounters) from various siloed Electronic Health Record (EHR) systems takes 3–5 seconds, VitaStream implements an aggressive Edge Caching and Data Lake architecture to bring response times under 100 milliseconds.

The system relies on an AWS API Gateway sitting in front of a distributed Redis Cache cluster. If a clinical summary has been recently compiled, it is served directly from memory, completely bypassing the heavy backend FHIR (Fast Healthcare Interoperability Resources) data lake.

## 2.0 Network Topology & Caching Infrastructure
To achieve sub-100ms latency, the network intercepts read-heavy requests at the boundary.

### 2.1 The Edge & API Gateway
* **Ingress:** All web and mobile traffic hits the external API Gateway (`api.vitastream.health`).
* **Caching Middleware:** Before a request is routed to the backend microservices, an ElastiCache (Redis) lookup is performed.
* **Backend Data Lake:** A cluster of Python FastAPI microservices that query an Amazon S3 Data Lake and an Aurora PostgreSQL metadata database to assemble FHIR clinical documents.

### 2.2 The Cache Key Strategy
When the backend generates a Clinical Summary, the API Gateway caches the JSON response.
* **Cache Expiration (TTL):** 15 minutes.
* **Cache Key Formulation:** The caching middleware generates the Redis lookup key using a hash of the HTTP Method and the URI Path. 
  * *Example Key:* `SHA256("GET" + "/api/v2/patients/P-7712/clinical-summary")`

## 3.0 Identity and Access Control
VitaStream enforces strict HIPAA compliance regarding who can view a patient's data.

### 3.1 Authentication
Physicians authenticate via Okta using SAML 2.0, receiving an OAuth2 Bearer Token (JWT). The token contains their National Provider Identifier (NPI) and their assigned clinic.

### 3.2 Backend Authorization (The "Care Team" Check)
When the backend FastAPI service receives a request, it performs a strict "Care Team" check. It queries the PostgreSQL database to ensure that the requesting Doctor has an active, documented clinical relationship with the requested Patient ID. If no relationship exists, the backend returns a `403 Forbidden`.

* **REST API Layer:** Java Spring Boot microservices expose endpoints to the frontend dispatch dashboards. 

## 3.0 Identity, Tenancy, and Authorization

### 3.1 Authentication

* **Tenant Claim:** The resulting JWT explicitly contains the user's Organization ID (e.g., `tenant_id: "org_logistics_alpha"`).

### 3.2 Authorization Model
The Java Spring Boot API utilizes a centralized Data Access Object (DAO) pattern. Every SQL query querying vehicle data is supposed to append an `AND tenant_id = :tenant_id` clause, extracting the `tenant_id` from the Spring Security Context (populated by the JWT).

# ENGINEERING ARCHITECTURE SPECIFICATION
**System Name:** CartVantage Serverless Commerce
**Document Version:** 4.0.2 (FINAL)
**Classification:** PUBLIC / PCI-DSS SCOPE
**Domain:** Retail / E-Commerce / Order Management

## 1.0 Executive Summary
CartVantage is a massively scalable, serverless e-commerce backend built to handle extreme traffic spikes (e.g., Black Friday sales). It provides headless commerce APIs for web storefronts and mobile apps.

The architecture relies entirely on ephemeral AWS Lambda functions connected via Amazon EventBridge and API Gateway. State is persisted in Amazon DynamoDB. Payment processing is offloaded to Stripe, utilizing a decoupled asynchronous webhook and polling model to finalize orders.

## 2.0 Network Topology & Serverless Microservices
The system is decomposed into three isolated microservices, each with its own DynamoDB table and API Gateway route.

### 2.1 Cart Service (`/api/v1/cart`)
* **Function:** Manages the active shopping session. Users add/remove SKUs (Stock Keeping Units).
* **Data Source:** Reads base prices from the Product Catalog.

### 2.2 Checkout & Payment Service (`/api/v1/checkout`)
* **Function:** Bridges the CartVantage platform with the external Stripe API. 
* **Initialization:** Generates a Stripe `PaymentIntent` client secret so the frontend can render the credit card UI.
* **Completion:** Marks the internal order as `PAID` once the frontend confirms the Stripe transaction was successful.

### 2.3 Fulfillment Service (EventBridge)
* **Function:** Once an order is marked `PAID`, an EventBridge rule triggers the Warehouse Lambda function to pack and ship the physical goods.

## 3.0 Identity and Access Control
CartVantage supports both Guest checkout and Authenticated users. 

### 3.1 User Authentication
Registered users authenticate via Amazon Cognito. The API Gateway utilizes a Cognito Authorizer to validate the JWT and inject the `cognito:username` into the Lambda event payload. 
Cart IDs are strictly bound to the authenticated user ID.

## 4.0 Service Behavior Notes
System behavior, data contracts, and operational sequencing are described in subsequent sections.

## 6.0 Implementation Notes (Node.js Lambda Snippet)

The backend completely trusts the `order_total` provided in the HTTP request body instead of calculating it from the database catalog.

```javascript
exports.handler = async (event) => {
    const payload = JSON.parse(event.body);
    const userId = event.requestContext.authorizer.claims.username;

    // An operator can send {"order_total": 200} for a $2,500 cart.
    const amountToCharge = payload.order_total; 

    // Create the Stripe PaymentIntent
    const paymentIntent = await stripe.paymentIntents.create({
        amount: amountToCharge,
        currency: 'usd',
        metadata: { userId: userId, cartId: payload.cart_id }
    });

    // Save PENDING order to DynamoDB
    await saveOrderToDB(userId, payload.cart_id, paymentIntent.id, amountToCharge);

    return { statusCode: 200, body: JSON.stringify({ client_secret: paymentIntent.client_secret }) };
};
```

The final step verifies the payment succeeded, but fails to verify that the *amount paid* matches the true value of the goods being released.

```javascript
exports.handler = async (event) => {
    const payload = JSON.parse(event.body);
```

The core system was recently modernized. The web and mobile portals now consume a strict, GraphQL-inspired REST API (v3). ## 2.0 Network Topology & Gateway Routing
The architecture relies heavily on Kong API Gateway to abstract the complexity of the backend microservices.

### 2.1 Kong API Gateway (Ingress)
* **Modern Traffic:** Routes starting with `/api/v3/*` are sent to the newly rewritten Go-based microservices, which employ strict schema validation using OpenAPI 3.0 specs.
* **Legacy Traffic:** Routes starting with `/api/v1/*` or `/soap/` are routed to a monolithic Java EE application running on Apache Tomcat. 

### 2.2 Data Persistence
Both the modern Go microservices and the legacy Java monolith connect to the same central Oracle Database. This shared persistence layer ensures that updates from either API version are instantly reflected across the entire system.

## 3.0 Identity, Roles, and Authorization
Identity is managed via Azure Active Directory (Azure AD).

### 3.1 Bearer Tokens & Scopes
Employees log into the self-service portal and receive a JWT.

### 3.2 Endpoint Enforcement
The v3 microservices strictly enforce these scopes. If a standard employee attempts to modify their salary using the v3 API, the Go service throws a `403 Forbidden` because it checks for the `payroll:write` scope before applying the update.

The legacy Java code uses an older version of Apache Commons BeanUtils. It dynamically maps every key in the JSON payload to the corresponding setter method on the central `Employee` ORM entity.

```java
}
```

**Domain:** Critical Infrastructure / Energy Grid / Substation Control

## 1.0 Executive Summary
VoltGuard is a hybrid IT/OT (Information Technology / Operational Technology) platform. It allows regional grid operators to monitor substation telemetry and execute remote switching operations (e.g., opening/closing high-voltage breakers) without dispatching a technician in a truck.

To bridge the gap between cloud infrastructure and physical hardware, VoltGuard utilizes a Cloud-to-Edge architecture. A web-based Human-Machine Interface (HMI) talks to a RESTful API Gateway in AWS. This gateway communicates over a site-to-site IPsec VPN to an Edge Gateway located inside the substation DMZ, which translates the JSON payloads into DNP3 commands for the physical Programmable Logic Controllers (PLCs).

## 2.0 Network Topology & IT/OT Boundaries
Strict network segmentation is mandated by NERC CIP (North American Electric Reliability Corporation Critical Infrastructure Protection) regulations.

### 2.1 The IT Cloud Plane (Control Center)
* **Primary Web HMI:** Only accessible via the corporate Intranet/VPN. 
* **Cloud API Gateway:** Routes all frontend JSON requests to the backend Go microservices.
* **Vendor API (The Exposure Point):** A secondary, heavily restricted API path (`/vendor-api/`) intended for external maintenance contractors to upload diagnostic logs. 

### 2.2 The OT DMZ & Physical Substation Edge
* **Edge Gateway:** A hardened industrial PC sitting in the substation. It drops all traffic except verified payloads originating from the IT Cloud Plane over the IPsec tunnel.
* **The PLC Network:** Completely air-gapped from the internet. PLCs communicate via serial or local Ethernet using the DNP3 protocol.

## 3.0 Identity, Safety Logic, and Authorization
Controlling physical power grids requires strict identity verification and multi-step safety validations.

### 3.1 Operator Identity
Grid Operators authenticate using hardware MFA (YubiKey) via PingIdentity. They receive an OAuth2 JWT containing their role (`grid_operator` or `maintenance_tech`).

### 3.2 The Multi-Step Safety Interlock Workflow
To prevent accidental power outages or arc flashes, opening a live breaker requires a strict, three-step software workflow modeled in the API:
1.  **Validate Safety Interlock (`POST /api/v1/breaker/{id}/validate`):** The system queries physical sensors to ensure load levels are safe for switching. Returns a `validation_token`.
2.  **Acknowledge Warning (`POST /api/v1/breaker/{id}/acknowledge`):** The operator signs off on the hazard warning, submitting the `validation_token`. Returns an `execution_token`.
3.  **Execute Command (`POST /api/v1/breaker/{id}/execute`):** The final endpoint that actually sends the DNP3 `TRIP` command to the PLC.

### 7.2 The DNP3 Translation (Edge Gateway to PLC)
When the Edge Gateway receives the validated JSON payload from the Cloud API over the IPsec tunnel, it translates it into a DNP3 **Control Relay Output Block (CROB)**.

* **Protocol:** DNP3 (IEEE 1815) over TCP/IP (Port 20000)
* **Target Device:** RTU/PLC Node Address 14
* **Object Group:** 12 (Control Relay Output Block)
* **Variation:** 1
* **Point Index:** 04 (Mapped to physical relay controlling BRK-09-MAIN)
* **Control Code:** `LATCH_OFF` (Physically opens the breaker circuit)
